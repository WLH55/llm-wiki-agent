## 什么是 Wiki / Wikilink

**Wiki** 就是一个用纯 Markdown 文件组织的知识库，存放在 `wiki/` 目录下。没有数据库、没有服务器——所有内容都是 `.md` 文件。

**Wikilink** 是 `[[PageName]]` 这种语法，用于在页面之间创建链接。它**不是 AI 推理生成的**，而是在导入（ingest）时，Claude 作为代理在写 wiki 页面的"关联"部分时**手动写入**的。比如：

```markdown
## 关联
- [[Transformer]] — 架构基础
- [[AttentionMechanism]] — 核心组件
```

这些是**显式的、确定性的**链接。

---

## Wikilink（EXTRACTED 边） vs 图谱推断边（INFERRED 边）的区别

| | Wikilink / EXTRACTED | INFERRED（推断边） |
|---|---|---|
| **来源** | 页面内容中明确写的 `[[X]]` | Claude 读取 graph.json 后，基于语义理解补充的隐含关系 |
| **置信度** | 1.0（确定） | >=0.7（高置信）或 <0.7（AMBIGUOUS） |
| **颜色** | 灰色 `#B8C4C0` | 橙色 / 浅灰 |
| **生成方式** | `build_graph.py` 用正则提取 | Claude 在 `/wiki-graph` 阶段人工/半自动添加 |

举个例子：假设有一篇关于 GPT 的文章提到了 Transformer，但写 wiki 页面时忘了加 `[[Transformer]]` 链接。Wikilink 抓不到这个关系，但 Claude 看到两个节点的内容后能推断出"GPT 和 Transformer 应该有边"，这就是 INFERRED 边。

---

## 为什么区分多种边类型

因为**可信度不同**：

- **EXTRACTED**（确定）：页面里明确写了链接，100% 可靠
- **INFERRED**（推断）：AI 根据语义理解补的，可能不准但有用
- **AMBIGUOUS**（模糊）：低置信度推断，仅供参考

这样做的好处是：使用图谱时（比如查询扩展），可以选择只信任确定性边，或也包含推断边来获得更广泛的关联。

## 什么是 Louvain 社区检测

Louvain 是一种**图聚类算法**，自动把关系紧密的节点归为同一个"社区"（community）。

**和边的关系**：它以边为基础——如果 A、B、C 之间有很多边互相连接，它们会被归为同一社区。在可视化中，同一社区的节点颜色相同。

**实际作用**：帮你发现知识库中的"知识岛"——比如所有 AI/ML 相关的页面聚成一个社区，所有经济学相关的聚成另一个社区。如果发现某个社区和其他社区完全没有连接，说明知识库存在结构性缺口。

## 为什么会出现孤立页面和断裂链接

**孤立页面**（没有入站链接）：
- 导入时忘记在关联部分写 `[[链接]]`
- 新创建的实体/概念页面还没被其他页面引用

**断裂链接**（指向不存在的页面）：
- 写了 `[[SomeConcept]]` 但对应的 `wiki/concepts/SomeConcept.md` 还没创建
- 页面被删除但其他地方的引用没清理

这些都是知识库维护中的常见问题，`/wiki-lint` 就是用来检测这些的。

### 其他结构性问题

**孤立高入度节点**：被很多页面链接（入度高），但自己不链接到任何其他页面（出度为 0）。相当于"只被引用、不引用别人"的页面，可能是内容孤岛。

**孤立低入度节点**：几乎没人链接它（入度低），同时它也不链接别人（出度也低）。相当于"与知识库几乎脱节"的页面。

**碎片集群**：知识库中出现了一个小团体，它们互相链接，但与知识库的主体完全断开。相当于"自说自话"的一小撮页面。

## /wiki-lint 怎么更新

`/wiki-lint` **不会自动修复问题**，它只做检测并输出报告：

- 孤立页面、断裂链接、缺失 frontmatter
- Hub stubs（高度连接但内容太少的页面）
- 脆弱桥梁（两个社区之间只有 1 条边）
- 缺失实体（被 3+ 页面提到但没有独立页面）

它会问你是否保存报告到 `wiki/lint-report.md`。修复工作需要你自己或通过 `/wiki-ingest`、`/wiki-heal` 等命令来完成。

## 过时摘要 vs /wiki-refresh

**不是同一回事**：

- **过时摘要**（lint 检测的）：`raw/` 中的源文档被修改了，但 `wiki/sources/` 中对应的知识页面没更新。Lint 只是**发现**这个问题。
- **`/wiki-refresh`**：实际**执行刷新**——检测哪些源文档变了（SHA-256 哈希对比），然后重新导入这些源文档，更新对应的 wiki 页面。

流程是：lint 发现问题 -> 你决定是否 refresh -> refresh 执行更新。

## 适合团队使用吗

**当前设计偏向个人使用**，因为：
- 所有内容是本地 `.md` 文件，用 git 管理
- 没有多用户协作、权限控制
- AI 推理依赖 Claude Code 单用户会话

**适合的场景**：

| 场景 | 说明 |
|---|---|
| **个人知识管理** | 研究笔记、读书笔记、学习笔记 |
| **研究文献管理** | 论文导入（支持 arXiv、PDF）、构建引用网络 |
| **项目文档沉淀** | 把散落的文档整理成互联的知识网络 |
| **小团队知识共享** | 通过 git 共享 wiki 目录，团队成员各自导入、查询 |

**基本使用流程**：

```
1. 把文档放到 raw/ 目录
2. /wiki-ingest raw/xxx.md     -> 导入，自动生成知识页面和链接
3. /wiki-query "某个问题"       -> 查询知识库，获得综合回答
4. /wiki-lint                   -> 检查知识库健康
5. /wiki-graph                  -> 可视化知识网络
6. /wiki-refresh                -> 源文档更新后刷新知识库
```

本质上是一个**个人/小团队的 AI 辅助知识管理工具**，核心价值在于把散落的文档变成互联的知识网络，并利用 AI 进行语义理解和推断。

## 与 RAG 知识库的区别

| | 直接让 AI 读文档 | RAG 知识库 | 本项目 (Wiki) |
|---|---|---|---|
| **知识形态** | 原始文档，用完即丢 | 向量分块，黑盒 | 结构化 Markdown，人可读可编辑 |
| **持久性** | 无，每次对话重新喂 | 有，但你看不到里面存了什么 | 有，`wiki/` 就是全部知识 |
| **跨文档关联** | 靠 AI 临场联想 | 靠向量相似度匹配 | 显式 `[[链接]]` + 图谱推断边 |
| **积累性** | 无，喂 10 篇和喂 1 篇一样 | 有，但新增文档不改变已有结构 | 有，新文档会连接到已有知识 |
| **可审计** | 无法审计 | 无法审计 | 可以，git 版本控制每一行变更 |
| **上下文限制** | 文档多了放不下 | 分块检索绕过限制 | 查询时按需读取相关页面 |

### 直接让 AI 读文档的问题

假设有 50 篇论文，问"Transformer 和 RNN 在哪些场景下可以互补"：

- AI 一次读不完 50 篇
- 即使读了，下次对话又忘了
- 每次回答都是"一次性"的，没有积累

### RAG 的问题

RAG 解决了"读不完"的问题，但引入了新问题：

- **黑盒**：你不知道它检索了哪些片段，也不知道为什么选了这些片段
- **没有结构**：50 篇论文之间的关系是什么？RAG 不知道也不关心
- **不积累**：加第 51 篇论文，前 50 篇之间的连接不会因此改变
- **不可编辑**：你不能手动修正一个错误的关联

## 为什么要用这个工具

### 核心价值：复合知识

用一个具体例子说明：

```
第 1 天：导入了一篇 Transformer 论文
  -> 生成 [[Transformer]]、[[AttentionMechanism]] 等概念页

第 5 天：又导入了一篇 BERT 论文
  -> BERT 自动链接到 [[Transformer]]（因为基于它）
  -> [[Transformer]] 页面增加了 BERT 作为应用案例

第 10 天：导入了一篇 GPT-4 报告
  -> 连接到 [[Transformer]]、[[BERT]]、[[OpenAI]]
  -> 如果有矛盾（比如 GPT-4 说某个数据和之前论文不同），会被标记

第 15 天：问"注意力机制的演进路径"
  -> 查询命中的不只是单篇文档，而是整个网络
  -> [[AttentionMechanism]] -> [[Transformer]] -> [[BERT]] -> [[GPT-4]]
  -> 这条链路是之前逐篇导入时构建的，不是临场检索的
```

**这就是"复合知识"**——每新增一个来源，整个知识库都变得更丰富，而不是仅仅多了一堆文本。

### 什么场景值得用

**不值得用的场景：**
- 只需要一次性回答几个问题 -> 直接让 AI 读
- 文档量少（<10 篇）且不会增长 -> RAG 或直接读都够用
- 需要实时检索、高并发 -> 这是本地工具，不适合

**值得用的场景：**
- 持续学习某个领域，文档会不断增加
- 需要跨文档发现关联和矛盾
- 想要一个**你可以审阅、编辑、版本控制**的知识库
- 团队需要共享积累的知识（通过 git）
- 做研究、写综述、准备考试——需要知识之间产生连接

### 一句话总结

直接让 AI 读文档是**问答**，RAG 是**检索增强的问答**，这个工具是**知识积累与关联**。前两个回答问题，后一个构建知识网络。如果你的知识需求是一次性的，不需要这个工具；如果你在持续深入一个领域，它会越用越有价值。

## 为什么需要维护多种页面类型

用一个真实场景说明。假设你导入了一篇关于 GPT-4 的论文：

### source（源页面）

**为什么需要**：原始论文太长了，`raw/gpt-4-paper.md` 可能有 2 万字。你需要一个精炼的摘要——核心论点、关键引述、关联实体。这就是 `wiki/sources/gpt-4-paper.md`。

它还通过 `source_file: raw/...` 记录来源路径，这样 refresh 时才能做哈希对比检测过期。

### entity（实体页面）

**为什么需要**：假设你导入了 10 篇论文，其中 7 篇都提到了 OpenAI。如果没有 `wiki/entities/OpenAI.md`，OpenAI 的信息就散落在 7 个源页面里，互相重复、可能矛盾。

有了实体页面，OpenAI 的信息**集中在一处**，7 个源页面都通过 `[[OpenAI]]` 链接到它。查询时只需读一个页面就能了解这个实体的全貌。

### concept（概念页面）

同理，`[[Transformer]]`、`[[AttentionMechanism]]` 这些概念在多篇论文中反复出现。概念页面把分散的知识**聚合**起来。

### index.md（索引）

**为什么需要**：它是知识库的"目录"。query 工作流第 1 步就是读它来定位相关页面：

```
query 工作流：
1. 读取 wiki/index.md          -> 知道知识库有哪些页面
2. 根据问题关键词匹配          -> 定位到相关页面
3. 读取那些页面的内容           -> 生成回答
```

没有 index，query 就不知道知识库里有什么。

### overview.md（概览）

**为什么需要**：ingest 工作流第 2 步读它：

```
ingest 工作流：
2. 读取 wiki/index.md 和 wiki/overview.md 获取当前知识库上下文
```

它是一段**动态更新的综合描述**——概括知识库整体覆盖了什么领域、有什么盲区。Claude 导入新文档前先读它，才能知道新知识和已有知识的关系，才能发现矛盾。

### syntheses（综合页面）

query 之后如果用户选择保存回答，就存到这里。它的价值是**避免重复查询**——下次有人问类似问题，可以直接引用已有的综合页面。

### log.md（日志）

记录每次操作的历史。主要用于回溯：`grep "^## \[" wiki/log.md | tail -10` 就能看到最近做了什么。

### query 时到底读了哪些页面

根据 CLAUDE.md 的查询工作流：

```
1. 读 wiki/index.md          -> 定位相关页面
2. 读匹配到的 wiki 页面       -> 获取内容（sources/entities/concepts 都可能被命中）
3. 读 raw/ 原始文档           -> 对命中的 source 页面，补充原始细节
4. 生成回答
```

**不会直接读** overview、syntheses、log——但 index 里的条目会引导它找到所有类型的页面。

### 一句话总结

| 页面类型 | 存在的理由 |
|---|---|
| **source** | 原始文档的精炼摘要，避免每次都读 2 万字原文 |
| **entity** | 把散落在多篇文档中的实体信息聚合到一处 |
| **concept** | 同上，针对概念 |
| **index** | 知识库目录，query 的入口 |
| **overview** | 知识库全局摘要，ingest 时提供上下文 |
| **syntheses** | 缓存查询结果，避免重复计算 |
| **log** | 操作审计，回溯历史 |

核心逻辑是：**index 是入口，source/entity/concept 是内容，overview 是全局上下文，syntheses 是查询缓存，log 是操作日志。** 分开维护是为了让每个角色各司其职，查询时只读需要的部分。
