## 1. Requirements (Context)

- **In-Scope**:

  - `rag_ingestion.py` 解析调用点从 `asyncio.wait_for(asyncio.to_thread(...))` 换为新入口
  - 新增依赖 pebble、配置项 `PARSER_POOL_WORKERS`
  - 回归测试：超时杀进程后池可复用、崩溃隔离、成功路径
- **Out-of-Scope**:
  - `get_bytes`（MinIO 下载）/ `embed_texts`（外部 API）/ `persist_parser_images`（本地 IO）维持 to_thread
  - `dispatch.py` 与所有解析器实现零改动
  - 池的优雅关闭（pebble worker 为 daemon 进程，随进程退出；不加 dramatiq middleware）

## 2. Research Findings
- **事实与约束**:
  - `parse_document(filename, raw_bytes, engine, limits) -> ParseResult` 是同步纯函数，不碰 DB/session；`ParseResult`（pydantic）与参数均可 pickle
  - pebble 未安装（需加依赖 `pebble>=4.6.1`）；标准库 `ProcessPoolExecutor` 超时**杀不掉**子进程，必须用 pebble 的 `submit(..., timeout=N)`（到期 terminate worker 并抛 TimeoutError，池自动补进程）
  - `PARSER_TIMEOUT_SECONDS=300` 已存在，直接复用；`ParseErrorCode.TIMEOUT` 已存在
  - 现调用点已把 `result.error_code` 统一映射为 `TerminalTaskError`，子进程级失败（超时/进程死亡）收敛为失败 ParseResult 后无需特判分支
  - dramatiq worker 通过 fork 产生子进程 → **池必须懒创建**（首次解析时），禁止模块 import 时建池（否则 fork 继承导致池损坏）
  - Windows/macOS spawn：子进程重新 import `app.config`（读 .env）+ 解析库，冷启动 1~3s；Linux fork 近零成本
- **风险与不确定项**:
  - Linux fork 发生在多线程进程（EventLoopThread/reaper 存在）——理论上 fork+threads 有死锁风险；子进程只执行已加载的纯函数、不新增 import，实际风险低。若线上观察到死锁，缓解方案：加 after_process_boot 预热 middleware（本次不做）
  - spawn 模式下子进程不继承父进程运行时注册的测试引擎 → 超时/崩溃测试用独立可 import 的 fixture 目标函数测 pebble 语义，不伪造引擎
