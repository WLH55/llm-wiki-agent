## 1. Requirements (Context)

- **Goal**: 将任务队列从 Taskiq + Redis Stream + Transactional Outbox 自建投递层，迁移到 Dramatiq + Redis，砍掉自建投递复杂度，借鉴 WeKnora 的成熟框架兜底哲学。

- **In-Scope**:
  - 删除 `task_outbox` 表和 `outbox/` 整个目录（Outbox Publisher + Reaper）
  - 删除 fencing CAS（token/epoch/lease/heartbeat 字段和校验逻辑）
  - 删除心跳续租（`_heartbeat_loop`）、退避计算（`_retry_delay`）、`retry_run`
  - 删除 multimodal/low 队列，队列拓扑简化为 critical + default
  - Taskiq `RedisStreamBroker` 换成 Dramatiq `RedisBroker`
  - 同函数多 actor 注册（方案 C）实现 critical/default 队列路由
  - 自定义 `RunFailureMiddleware`（`after_process_message` 钩子标 Run failed）
  - 嵌入 worker 的简化版 Reaper（扫 span 心跳 + pending 过旧）
  - Span 心跳 API（`begin_span` / `end_span`），handler 各阶段调用
  - docker-compose 调整：删 outbox-publisher，合并 worker 容器
  - `processing_runs` 表字段清理（删 fencing 相关字段）
  - Alembic 迁移脚本

- **Out-of-Scope**:
  - handler 逻辑重写（仅调整 span 心跳调用，幂等策略调整留后续任务）
  - handler 幂等策略从"拒绝重做"改为"允许重做已完成步骤"（后续任务）
  - 前端 UI 适配
  - 性能压测

## 2. Research Findings

### 2.1 当前架构事实

**当前任务运行时三表分工**：
- `processing_runs`：任务运行账本（终态真相源）
- `processing_spans`：阶段观测层（诊断流水）
- `task_outbox`：可靠投递层（消息意图）

**当前 worker 拓扑**（docker-compose.yml）：
- `task-worker-shared`：`taskiq worker --workers 1 --max-async-tasks 14`（消费 default + critical + multimodal + low）
- `task-worker-critical`：`taskiq worker --workers 1 --max-async-tasks 2`（只消费 critical）
- `outbox-publisher`：独立进程，轮询 Outbox 投递到 Redis Stream

**当前 handler 行为**（`rag_ingestion.py`）：
- handler 是"从头重做 + 幂等检查"模式，不是"接管续跑"
- `document_process_handler`：幂等检查是"已有 chunks 则抛 `candidate_chunks_exist`"
- `rag_index_handler`：幂等检查是"已有 embedding 则抛 `candidate_chunks_indexed`"
- 两个 handler 的幂等检查都是**拒绝重做**，用户重试会被挡

### 2.2 WeKnora 架构事实

**WeKnora 的 housekeeping**（`knowledge_housekeeping.go`）：
- 嵌入主进程的 cron，每 5 分钟扫一次
- 扫描 `parse_status IN ('processing','finalizing') AND updated_at < cutoff` 的 knowledge 行
- 阈值 = max(1h, DocumentProcessTimeout) + 10min = 70min
- 两道防误杀关卡：span 心跳（`MAX(spans.updated_at)`）+ 队列探针（`HasQueuedTasksForKnowledge`）
- 动作：标 `parse_status='failed'`，不自动重投

**WeKnora 的 SpanTracker**（`knowledge_span_tracker.go`）：
- 事件驱动心跳：每个阶段的 `BeginStage` / `EndSpan` / `FailSpan` / `SkipSpan` 都调 `touchKnowledgeHeartbeat`
- `touchKnowledgeHeartbeat` 刷 `knowledge.updated_at`（root/stage 级），subspan/generation 不刷父行避免写放大
- housekeeping 扫描时读 `MAX(spans.updated_at)` 作为"最近活动时间"

**WeKnora 的普通任务没有 lease/fencing/续租**，靠 asynq 的 Timeout（2h）+ 死信回调 + housekeeping。

### 2.3 Dramatiq 框架事实

**Dramatiq Redis broker 崩溃重投**（`redis.py` 源码）：
- `DEFAULT_HEARTBEAT_TIMEOUT = 60000`（60s）
- worker 进程定期往 Redis 写心跳（用 `broker_id` 标识）
- worker 进程崩溃 -> 心跳停止 -> 60s 后未 ack 消息被 maintenance 过程放回队列
- 这是**进程级**机制，不是消息级

**Dramatiq Retries middleware**（`retries.py` 源码）：
- 重试时 `broker.enqueue(message, delay=delay)`，用原 message
- `message.queue_name` 是 frozen dataclass 字段，重试回原队列
- `throws` 选项：指定异常类型不重试，直接 `message.fail()` 进死信
- `max_retries` / `min_backoff` / `max_backoff` / `retry_when` 可配

**Dramatiq AsyncIO middleware**（`asyncio.py` 源码）：
- 每个 worker 进程 1 个 `EventLoopThread`（全局单例）
- worker 线程调 async actor 时，`run_coroutine_threadsafe` 提交协程到事件循环
- worker 线程阻塞等结果，事件循环继续跑其他协程
- 并发协程数 = `--threads` 数，和 Taskiq 的 `--max-async-tasks` 等价

**Dramatiq queue_name 固定**（`actor.py` 源码）：
- `message_with_options` 中 `queue_name=self.queue_name` 硬编码
- `send_with_options(queue_name="xxx")` 不会改变消息队列，会掉进 `options` 字典被忽略
- 方案 C（同函数多 actor 注册）是实现多队列路由的正确方式

**Dramatiq Middleware 生命周期钩子**（`middleware.py` 源码）：
- `after_process_boot`：worker 子进程启动后（子进程内）--用于启动 Reaper
- `after_process_message(broker, message, *, result=None, exception=None)`：消息处理后--用于失败回调
- `before_worker_shutdown`：worker 关闭前--用于停止 Reaper

### 2.4 风险与不确定项

1. **commit_success 失败的已知限制**：DB 临时故障导致 `commit_success` 失败时，业务可能已部分写入，但 Run 最终被 Reaper 标 failed。当前接受这个不完美。

2. **Span 心跳阈值与长阶段协调**：Reaper 5min 扫一次，span 心跳阈值 5min。如果 handler 某个阶段执行超过 5min（如 embedding 5K chunks），span 不刷新，Reaper 会误杀。需要 handler 在长阶段内部定期刷新 span。

3. **双写窗口**：删 Outbox 后，DB 提交后、入队前崩溃的窗口可能丢任务。靠 Reaper 扫"pending 且 created_at 过旧"兜底。

4. **Dramatiq Redis broker 心跳超时（60s）与 span 心跳的交互**：worker 进程崩溃后 60s，Dramatiq 重投消息。新 worker 调 `claim_run`，Run 状态是 running（旧 worker 领取过）-> CAS `status='pending'` 失败 -> 消息 ack 丢弃。Run 卡 running -> 5min 后 span 心跳超时 -> Reaper 标 failed。恢复延迟约 5-10 分钟。

5. **handler 幂等策略**：当前 handler 幂等检查是拒绝重做，用户重试会被挡。后续重写 handler 时调整。
