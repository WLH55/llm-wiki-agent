## 1. Requirements (Context)
- **Goal**: 让 Dramatiq 自动重试与死信（`throws`）真正生效：handler 抛瞬态错误时按 `max_retries=3` + 指数退避重试并**重跑 handler**；终态错误（`TerminalTaskError`）不重试直接进 DLQ；消息最终死亡（重试耗尽或 throws）时 Run 标 failed。
- **In-Scope**:
  - `executor.py`：异常冒泡（删除 `_handle_failure` 的 fail_run 行为）
  - `runtime.py`：新增 `release_run`（CAS running→pending）；`fail_run` 支持 pending 终态标记
  - `middleware.py`：`RunFailureMiddleware` 只在消息最终死亡时标 Run failed
  - `broker.py`：`RunFailureMiddleware` 注册位置调整（`before=Retries`）
  - 测试更新与新增（`test_task_executor.py` / `test_task_runtime.py`）
  - 文档同步（本 spec + 旧迁移 spec §8 + `task-queue-design.md` §4.3/§7）
- **Out-of-Scope**:
  - handler 幂等改造（T1 剩余部分）
  - Reaper 多副本去重（T5）
  - broker 惰性初始化（T4）
  - `max_retries` 等参数从 settings 读取
  - time_limit 取消后 release（默认保持现状）

## 2. Research Findings
- 事实与约束（均已对照源码核实）:
  1. `executor.py:178-193` 捕获全部异常并调 `_handle_failure` → 异常不冒泡，Retries middleware 不可见 → 重试/死信均不触发。
  2. `_handle_failure` 调 `fail_run`（CAS running→failed）→ 即使重投，`claim_run` 发现非 pending 返回 False → 重试被吸收。
  3. dramatiq `emit_after("process_message")` 按 `reversed(self.middleware)` 执行（`broker.py:111-117`）；默认 middleware 顺序 `[Prometheus, AgeLimit, TimeLimit, ShutdownNotifications, Callbacks, Pipelines, Retries]`；当前 `RunFailureMiddleware` append 在 Retries 之后 → 逆序时**先于** Retries 执行。
  4. `Retries.after_process_message`：throws 命中 → `message.fail()`；重试耗尽 → `message.fail()`；可重试 → `broker.enqueue(delay)` 且不置 failed。`MessageProxy.fail()` 置 `self.failed=True`（`broker.py:386-390`），`post_process_message` 据此 nack 进 DLQ（保留 7 天）。
  5. `add_middleware` 支持 `before=` 定位（`broker.py:119-161`）→ 可把 `RunFailureMiddleware` 插到 Retries 之前，逆序链中它在 Retries **之后**执行，能读到 `message.failed` 最终判定。
  6. `compute_backoff`（`common.py:38-55`）：`delay = min(min_backoff * 2^retries, max_backoff)`，jitter = [名义一半, 名义全额] 均匀随机；三次等待实际 ≈5-10s / 10-20s / 20-40s，总时长 ~70s。
  7. `fail_run` 目前仅支持 running→failed；重试耗尽时 Run 已被 release 回 pending → 终态标记需支持 `status IN (running, pending)`。
  8. Reaper pending 判定基于 `updated_at` 超 5min（`reaper.py`）：重试等待期由 `release_run` 刷新 `updated_at` 续命、不误杀；从未被 claim 的 pending `updated_at≈created_at`，入队失败/消息丢失仍覆盖（原基于 `created_at`，2026-08-06 优化为 `updated_at`，见 §5 Follow-up 补记）。
  9. 现有测试 `test_task_executor.py` 的 terminal/transient 用例断言需随行为变更更新：改为 `test_terminal_error_propagates_and_run_stays_running` / `test_transient_error_releases_run_and_propagates`（原旧名 `test_terminal_error_marks_run_failed` / `test_transient_error_marks_run_failed`，见 §5/§6）。
- 风险与不确定项:
  - 重试重跑 handler 后，handler 幂等改造（T1 剩余）未做：当前 handler 业务写全在 `commit_success` 单事务内，失败无部分提交，风险可控；重复 API 调用成本（embed）可接受。
  - time_limit（CancelledError）路径保持现状：Run 保持 running，重试消息被吸收，Reaper ~70min 后标 failed。

## 3. Innovate
### Option A（选定）：异常冒泡 + release_run + middleware 排序
- Pros: 与设计文档语义一致；不重复实现 Retries 判定逻辑；单一路径
- Cons: 依赖 middleware 顺序（`before=Retries`）；需改 5 处文件
### Option B：仅异常冒泡、不 release
- Pros: 改动最小
- Cons: 重投消息 claim 失败被吸收，重试仍无效（方案无效）
### Option C：RunFailureMiddleware 自算 retries/max_retries
- Pros: 不依赖 middleware 顺序
- Cons: 重复实现 Retries 判定逻辑（throws/retry_when/backoff 都要复刻），易漂移
### Decision
- Selected: A
- Why: `message.failed` 是 dramatiq 官方给出的"最终失败"信号；顺序问题用 `before=Retries` 一次解决。设计已在父线程审查 + 源码核实（等价于 grill-with-docs 的澄清环节），不另开 grilling 会话。
