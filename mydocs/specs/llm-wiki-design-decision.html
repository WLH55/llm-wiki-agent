从单人工具到团队平台的架构演进路径
01

澄清：真正的问题是什么

你描述的需求表面上是"升级 LLM Wiki 3.0"，但拆开后实际上包含了四个不同的问题，它们的优先级和复杂度差异巨大：

表面需求真正的问题
"编译过程黑箱，靠 AI 能力"编译质量的可控性和可审计性
"每次编译消耗 token"知识库规模增长时的边际成本控制
"从单人扩展到团队"多人协作的数据架构和权限模型
"开发用 MCP，非开发用 UI"同一套知识库的两种消费模式
你的 PLAN.md 没有解决前两个问题 你当前的升级计划（Phase 0-4）主要解决的是"加 UI"和"加向量检索"，但编译黑箱和 token 成本控制这两个核心痛点，在当前计划中几乎没有被触及。Mini Agent 能降低单次对话的 token，但不解决编译本身的 token 消耗。

一句话重新定义你的产品目标

不是"给单人工具加个界面"，而是：构建一个编译质量可控、token 成本可预测、同时服务开发者（MCP）和非开发者（UI）的团队级知识管理平台。

02

拆解：从事实出发

基本事实

事实含义
LLM 编译 1 篇文档产出 ~5-15 个页面编译成本随文档数线性增长，但产出页面数是非线性膨胀
每次编译需要 LLM 读取源文件 + 读取现有 wiki 页面wiki 越大，每次编译需要"回忆"的上下文越多，token 成本递增
团队成员 80% 的时间在查询，20% 在写入查询优化比编译优化对日常体验影响更大
知识有"热区"——20% 的页面被 80% 的查询命中不需要同等对待所有页面
AI 编译不可复现同一文档编译两次产出不同页面——这在团队场景下是严重问题

硬约束（不可妥协）

  • LLM 上下文窗口有上限——当 wiki 超过几千页时，不可能每次编译都把全量页面放进上下文。必须做增量。
  • Token 有成本——团队高频使用下，不能接受每次查询都消耗数千 token。需要缓存和分层。
  • 编译产物必须可审计——团队场景下，AI 编译错误会被所有人消费，必须有 diff 审核环节。
  • MCP 和 UI 共享同一份数据——开发者和非开发者看到的是同一个知识库，不存在两套系统。

软约束（可以挑战）

  • "编译必须在写入时完成"——可以改为异步编译、定时编译、或按需编译。
  • "向量搜索是检索的核心"——对小型知识库（< 500 页），分层元数据扫描可能就够了。
  • "Tauri 桌面应用"——团队使用场景下，内网 Web 部署可能比桌面应用更合适。
  • "4 种页面类型"——缺少 skills/（操作知识）和 references/（来源摘要）分类，影响检索精度。
03

暴露：你隐含了哪些假设

以下是你描述中隐含的、但可能经不起推敲的假设：

隐含假设挑战
"编译型"是唯一正确的知识管理范式 GBrain 证明了"检索型"在大规模知识库（14.6 万页）下也能工作。编译型在团队场景下有一个致命风险：编译错误会被所有人消费。检索型（存原始分块，查询时实时综合）在容错性上更优。
"知识库规模大 = 编译压力大" 规模大对编译的压力和对检索的压力是不同的。编译压力可以通过增量编译 + Tier 控制解决；检索压力需要分层策略 + 缓存。这是两个独立问题，不能用同一个方案解决。
"MCP 和 UI 是同一产品的两个入口" 它们的使用模式完全不同。MCP 是"提问→AI 回答"，用户不直接看 wiki 页面。UI 是"浏览→搜索→阅读"，用户直接消费编译产物。这意味着编译产物的质量对 UI 用户比对 MCP 用户更重要。
"知识图谱可视化是团队用户的刚需" 管理者可能只需要搜索和对话能力，不需要看图谱。图谱对"理清思路"有用，但这不是每个人每天都需要的功能。确认一下：你团队中，真正会花时间看图谱的人有几个？
"当前架构加个 UI 就能升级为团队产品" 当前 Python CLI 架构是为单进程单用户设计的。团队使用需要并发写入、权限控制、变更通知。这不是"加个 UI"能解决的，是架构层面的改造。
最危险的假设 "编译型"在单人使用下很好用，因为你自己能判断编译质量。但团队场景下，如果 AI 编译出了一个错误页面（比如把"微信支付退款"和"支付宝退款"混为一谈），这个错误会被所有团队成员消费且无人发现。编译型知识库在团队场景下的容错机制是当前方案中完全缺失的。

简化：去掉不必要的复杂性

结合 obsidian-wiki 和 GBrain 的研究，你的方案设计中有几处应该简化或重新考虑的地方：

简化 1：不要同时做"编译型"和"检索型"两套完整系统

你目前的方案本质上是混合的——既有编译（wiki 页面生成），又有向量检索。但两个都没做透。与其两边都平庸，不如明确哪一层是核心，哪一层是辅助。

建议：编译为主，检索为辅 你的核心差异化就是"编译型知识库"——obsidian-wiki 证明了这条路的价值。向量检索和混合搜索是你的检索辅助层，不是你的核心卖点。投入 70% 精力在编译质量和可控性上，30% 在检索能力上。

简化 2：Phase 0（Claude Code 代理）可以跳过

你当前的 Phase 0 是用 WebSocket 代理 Claude Code 对话。但在团队场景下，你不可能让每个团队成员都通过你的后端代理一个 Claude Code 进程。这个架构在单人使用时可行，在团队场景下完全不可扩展。

建议直接跳到 Mini Agent（你现有的 Phase 3），用 Anthropic SDK 直接调 API。省下的时间用在编译质量控制上。

简化 3：Tauri 桌面版在团队场景下不是最优解

你的 PLAN.md 同时规划了"Tauri 桌面版"和"Docker 内网部署"。对于团队使用，内网 Web 部署是自然选择——团队成员打开浏览器就能用，不需要每人装一个桌面应用。Tauri 桌面版只适合个人单机使用。

简化建议 团队版本 = Next.js 内网部署（Docker）。个人版本 = 可选 Tauri 打包。但优先做团队版本，因为团队使用是你的核心场景。

obsidian-wiki 有 ~40 个技能文件，GBrain 有 100+ CLI 命令。你不需要一次做完所有这些。按"团队知识库"的核心场景，MVP 只需要：

核心设计：编译型知识库的团队化改造

以下是我认为你应该重点设计的产品架构，解决你提出的所有问题。

设计决策 1：编译透明化——从黑箱到可审计流水线

这是你最核心的痛点。方案：

原始文档 → 分块 → LLM 提取知识 → 生成编译 Diff → 人类审核 → 确认写入 → 刷新索引 编译 Diff 示例： + 新增: concepts/refund-flow.md（从 refund-spec.pdf 提取） + 新增: entities/payment-system.md（从 refund-spec.pdf 提取） ~ 更新: concepts/payment-channel.md 新增章节"微信支付 V3 变化" 来源: refund-spec.pdf 第 12-15 页 跳过: entities/alipay-sandbox.md（tier: peripheral，跳过）

核心机制：

  • 编译预览（不是编译后直接写入）：每次编译产出 diff，在 UI 中展示增删改的页面内容，用户确认后才正式写入。这就是 obsidian-wiki 的 Staging 审核模式，但你有 UI 来承载。
  • 溯源面板：每个 wiki 页面的 UI 详情页显示"这条知识从哪个源文件提取、哪一段是 AI 推理的"。正文中用颜色标注 ^[extracted]（绿色）、^[inferred]（琥珀色）、^[ambiguous]（红色）。
  • 编译日志（只追加）：每次编译记录"什么时间、谁触发、处理了哪些文件、产出/更新了哪些页面、跳过了哪些页面及原因"。
  • 置信度分数：每个页面显示置信度（来源数量 × 来源质量），让团队成员一眼看到哪些知识可靠、哪些需要人工复核。

设计决策 2：成本控制——编译和查询两条线独立控制

Token 成本分两块，不能用同一个方案解决：

编译成本控制

Tier 分级（来自 obsidian-wiki）：core 总是更新，supporting 有新信息才更新，peripheral 跳过。这直接减少每次编译需要打开和处理的页面数。

SHA-256 增量：只编译内容真正变更的文件，mtime 变化但内容相同的跳过。

批量编译：团队场景下，不要求每次保存都立即编译。允许"攒一批文档 → 一键批量编译"，减少重复的上下文加载。

查询成本控制

分层检索（来自 obsidian-wiki）：元数据扫描 → 混合搜索 → 全文读取。低成本层先行。

查询缓存（来自 GBrain）：相似问题复用搜索结果。

Mini Agent 替代 Claude Code：系统提示从 10k+ token 降到 2-3k token，每次对话省 60%+。

Tier 影响检索排序：core 页面优先返回，大多数查询不需要打开 supporting 和 peripheral 页面。

设计决策 3：双通道服务——MCP 和 UI 共享编译产物

开发者和非开发者消费同一个知识库，但方式不同：

开发者通道（MCP）

在 Claude Code / Cursor 中使用，AI 助手调用 MCP 工具：

  • search_wiki — 混合搜索
  • get_page — 读取指定页面
  • list_pages — 列出页面（按类型/标签/层级）
  • get_graph — 获取页面关联关系
  • ingest — 触发编译
  • health_check — 知识库健康状态

开发者看到的是 AI 综合后的回答，不直接看 wiki 页面。

非开发者通道（UI）

浏览器访问内网 Web 应用：

  • 文档管理 — 浏览、搜索、阅读 wiki 页面
  • 知识图谱 — 力导向图可视化
  • AI 对话 — 自然语言查询知识库
  • 编译管理 — 查看编译 diff、确认/拒绝编译
  • 健康面板 — 断链/孤页/陈旧内容一览

非开发者直接浏览编译好的 wiki 页面，也通过对话间接消费。

关键设计原则 MCP 和 UI 消费的是同一份编译产物（wiki/ 目录下的 markdown 文件）。不存在"一套给 MCP 用的数据"和"一套给 UI 用的数据"。这确保了数据一致性，也让维护成本最低。

设计决策 4：知识图谱可视化——服务于人类理思路

你的需求是"图谱可视化可供人类理清思路"。这意味着图谱不只是 AI 搜索的辅助工具，更是一个人类导航工具。设计要点：

  • 全局视图 + 聚焦视图：全局看所有节点概貌，点击某节点后展开它的 1-2 跳邻域，让"相关概念"浮现出来。
  • 按类型着色：concept 蓝色、entity 绿色、source 灰色、synthesis 紫色、skill 橙色。一眼看出节点类型。
  • 按 Tier 调节大小：core 节点大、supporting 中等、peripheral 小。视觉上一眼看到知识"重心"在哪里。
  • 搜索联动：在图谱页面有搜索框，搜索后相关节点高亮，帮助用户定位"退款"相关知识分布在图谱的哪些区域。
  • 路径探索：选中两个节点后，显示它们之间的最短路径。帮助人类发现"这两个概念原来是通过那条链路关联的"。
图谱的边界 图谱可视化对 500 页以内的知识库效果最好。超过 500 页后，力导向图会变成一团意大利面。这时候应该用"搜索+聚焦"模式——先搜一个概念，再展开它的局部图谱，而不是展示全局。

设计决策 5：分类体系——在现有基础上扩展

你当前 4 类型 + 建议扩展：

类型说明状态
concept概念、理论、原理已有
entity人物、组织、工具、项目已有
source原始来源（不可变）已有
synthesis跨来源综合分析已有
skill操作知识、流程指南、排障手册建议新增
reference来源的忠实摘要（与 source 分离）建议新增
为什么 source 和 reference 要分开 当前你的 source 同时指代"原始 PDF"和"AI 生成的来源摘要"。这导致检索时"原文说了什么"和"原文本身"混在一起。把原始文件放 raw/（不可变），AI 摘要放 wiki/reference/（编译产物），两者通过 manifest 关联但物理分离。

决策：建议与下一步

核心产品定位

一句话定位 编译质量可控、成本可预测的团队级知识管理平台。

与 obsidian-wiki 的区别：有 UI、有审核机制、面向团队。
与 GBrain 的区别：编译型（不是检索型）、纯文件存储（不是数据库）、更轻量。
与当前版本的区别：编译透明化、成本可控、支持多人。

三个核心差异化（不要在这些上面妥协）

  1. 编译 Diff 审核——这是 obsidian-wiki 和 GBrain 都没有做好的环节。obsidian-wiki 编译后直接写入（无审核 UI），GBrain 不做编译。你有 UI 来承载审核流程，这是你的独特优势。
  2. 知识图谱可视化——面向人类理清思路，不只是给 AI 做搜索辅助。两个竞品都没有做好这个方向。
  3. 纯文件 + 服务层的轻量架构——数据可 Git 管理、可备份、可迁移，服务层提供团队协作能力。比 GBrain 的 Postgres 方案轻量得多，比 obsidian-wiki 的纯 CLI 方案实用得多。

你现在应该做的第一件事

不是开始写代码，而是定义编译 Diff 的数据结构。这个数据结构决定了你的编译管线、审核 UI、manifest 追踪、以及最终用户看到什么。它是一切的核心。

// 编译 Diff 数据结构草案
interface CompilationDiff {
  // 触发信息
  trigger: {
    type: 'manual' | 'batch' | 'auto';
    user: string;
    timestamp: string;
  };

  // 输入
  sources: Array<{
    file: string;
    contentHash: string;  // SHA-256
    changeType: 'new' | 'modified';
  }>;

  // 产出
  changes: Array<{
    action: 'create' | 'update' | 'skip';
    page: string;         // wiki 页面路径
    type: string;         // concept/entity/skill/...
    tier: string;         // core/supporting/peripheral

    // 如果是 create/update：
    diff?: {
      added: string[];     // 新增的内容段
      removed: string[];   // 删除的内容段
      modified: Array<{
        before: string;
        after: string;
      }>;
    };

    // 来源溯源
    provenance: {
      extracted: number;   // 0-1
      inferred: number;    // 0-1
      ambiguous: number;   // 0-1
    };

    // 如果跳过：
    skipReason?: string;   // "tier: peripheral" / "no new info" / ...
  }>;

  // 状态
  status: 'pending_review' | 'approved' | 'rejected';
}

需要进一步确认的问题

  1. 团队规模：你的团队有多少人？这决定了并发写入和权限模型的复杂度。5 人以下可以不做权限控制，5-20 人需要基础权限（谁能编译、谁能审核），20+ 需要完整 RBAC。
  2. 知识来源：团队的知识主要从哪里来？文档/Confluence/代码仓库/聊天记录？这决定了摄入管线的优先级。
  3. 图谱使用场景：你说的"理清思路"具体是什么场景？是新人 onboarding 时理解系统架构？还是做技术决策时看关联关系？还是日常浏览时探索知识？不同场景的图谱 UI 设计差异很大。
总结 你的产品应该站在 obsidian-wiki 的编译哲学和 GBrain 的工程实践之间——把"编译型知识库"做对（透明、可审计、成本可控），用轻量但成熟的工程实现（分层检索、Tier、增量编译、代码级图遍历），装进一个团队友好的 UI 里。不要在编译和检索之间摇摆不定，也不要在个人版和团队版之间同时做。先做团队的、编译型的、有审核的，这是你的核心差异化。
