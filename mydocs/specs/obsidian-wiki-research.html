01

项目定位与核心理念

obsidian-wiki（github.com/Ar9av/obsidian-wiki）是一个开源的知识管理框架，明确引用了 Andrej Karpathy 的"compile, don't retrieve"理念。它的核心观点是：wiki 是编译产物，AI agent 是维护者，Obsidian 只是查看器。

与传统 RAG（Retrieval-Augmented Generation）的区别在于：传统 RAG 在每次查询时从原始文档重新理解、重新提取，相当于"每次运行都重新编译"；而 obsidian-wiki 在摄入阶段就把原始文档编译成互相链接的结构化知识页面，查询时直接读取编译产物。这将昂贵的理解和综合工作从查询时转移到了摄入时。

核心哲学 传统 RAG：每次查询都在"重新发现知识"。obsidian-wiki：知识只编译一次，查询时直接消费编译产物。

项目本身是一个 Python 包（pip install obsidian-wiki），包含一个薄 CLI（457 行，纯 stdlib，零运行时依赖）和约 40 个技能文件（SKILL.md）。CLI 的作用只是将技能文件安装到各种 AI 编码工具（Claude Code、Cursor、Windsurf、Codex 等）的技能目录里。

02

与 Obsidian 的关系

Obsidian 是可选的查看器，不是运行时依赖。 项目自己的原话：

"The wiki is the artifact. The agent is the maintainer. Obsidian is the viewer."

整个仓库中不存在任何 Obsidian 插件代码——没有 Obsidian 的 manifest.json，没有 TypeScript，没有 import from 'obsidian'，没有继承 Plugin 类。它产生的就是一堆标准 markdown 文件。

Obsidian 提供的增值（可选）

  • 图谱视图：Obsidian 内置的图谱可视化可以渲染 [[wikilinks]] 为可视网络。项目的 graph-colorize 技能会写 .obsidian/graph.json 配置节点着色。
  • 导航浏览：wikilink 语法在 Obsidian 中原生可点击跳转。
  • 仪表盘视图：wiki-dashboard 技能创建 Obsidian Bases（.base）文件。
  • 社区插件：推荐 Dataview、Graph Analysis、Templater、Obsidian Git 作为可选增强。

项目不使用 Obsidian 做的事

Obsidian 从未被程序化地导入或调用，不存在任何 API 集成。项目的 .obsidian/ 目录只是 JSON 配置文件，Obsidian 打开 vault 时自动读取。

对我们的启示 知识库存为纯 markdown 文件 + JSON 配置，不依赖任何特定编辑器。我们的 Tauri 桌面应用可以直接读写这些文件，用户也可以用 Obsidian 打开同一个目录浏览。
03

使用方式与工作流程

obsidian-wiki 不是 Obsidian 插件，而是一个 CLI + "AI 技能"框架。工作流程完全不是"在 Obsidian 里写文档 → 自动编译"，而是反过来的——AI agent 写 wiki，用户用 Obsidian 看。

安装与配置

pip install obsidian-wiki
obsidian-wiki setup --vault /path/to/vault

CLI 把约 40 个技能文件安装到 AI 编码工具的技能目录里。之后在任何 AI 编码工具中通过自然语言或斜杠命令触发：

命令功能
/wiki-ingest摄入文档，编译进 wiki
/wiki-query 问题检索并综合回答
/wiki-update把当前项目的知识蒸馏到 wiki
/wiki-lint健康检查（断链、孤页、矛盾）
/wiki-capture --quick快速记录发现，暂存到 _raw/
/wiki-history-ingest claude挖掘 Claude Code 对话历史到 wiki
/wiki-synthesize发现跨来源的综合分析机会
/wiki-dedup检测和合并重复概念页面

关于自动编译

不存在自动编译。 没有文件监听器（无 fswatch / chokidar / inotify），没有守护进程，没有轮询。所有编译都是用户手动触发（调用技能）。

最接近"自动"的机制是 wiki-stop-capture.sh：它是 Claude Code 的"停止钩子"，当编码会话结束时，如果检测到有文件编辑或 4+ 次 shell 调用，会提示 agent 执行快速捕获，暂存到 _raw/。但这只是暂存原始草稿，不编译。另有 daily-update.sh（cron 每日 9 点运行）和 wiki-notify.sh（终端打开时提示 wiki 陈旧度），但这些只报告状态，不触发编译。

与我们的差异 我们设计的是"编辑-编译"两步工作流：用户编辑文档 → 保存 → 提示编译 → 用户确认编译。obsidian-wiki 是纯手动触发 + 增量追踪（delta tracking）。我们的方案用户交互更友好，obsidian-wiki 的方案更简单直接。
04

三层架构设计

层名称可变性类比内容
Layer 1 Raw Sources 不可变 源代码 原始文档：PDF、markdown、聊天记录、截图。永不被系统修改。存放于 OBSIDIAN_SOURCES_DIR
Layer 2 The Wiki LLM 维护 编译产物 互相链接的 Obsidian 兼容 markdown 文件。综合、交叉引用、可导航。存放于 OBSIDIAN_VAULT_PATH
Layer 3 The Schema 规则治理 构建系统 SKILL.md + 配置文件，定义分类、约定、页面模板和工作流
为什么这样设计 Layer 1 不可变保证了信息溯源——任何时候都可以回到原始文档验证编译产物的准确性。Layer 2 是 LLM 维护的"编译视图"，可以随时重新生成。Layer 3 是"宪法"，定义了编译规则。这三层分离使得系统具备可审计性：原始来源 → 编译过程 → 编译产物，每一层都可以独立验证。

05

六分类体系与设计原理

obsidian-wiki 的分类不是按"内容类型"分的，而是按知识的认知功能分的。每个目录回答一个不同的问题：

分类回答的问题认知功能示例
concepts/"这是什么？"抽象理解transformer-architecture.md
entities/"谁在做？用什么工具？"具象锚点andrej-karpathy.md
skills/"怎么做？"操作指导fine-tuning-llms.md
references/"原文说了什么？"来源忠实记录attention-is-all-you-need.md
synthesis/"跨来源的洞察是什么？"交叉推理scaling-laws-debate.md
journal/"什么时候发现了什么？"时间线追踪2024-03-15.md

为什么这样分类

第一，认知功能分离有利于检索精度。 当用户问"怎么部署？"，系统优先扫 skills/；问"Karpathy 说了什么？"，优先扫 entities/karpathy.md + references/。如果所有知识混在一起，检索就得全靠向量相似度去区分"概念解释"和"操作步骤"，这两者的语义空间非常接近但用途完全不同。分类本质上是给检索加了一层语义先验。

第二，分类决定了编译时的提取策略。 摄入同一篇论文时，concepts/ 提取的是抽象理论模型，entities/ 提取的是人物/工具/组织，skills/ 提取的是可复现的操作流程，references/ 做的是论文本身的忠实摘要。分类告诉 AI "你应该从这篇文档里提取什么维度的知识"。

重要性分级（Tier）

每个页面还有一个 tier 字段，分三级，控制更新和检索的优先级：

Tier更新规则检索优先级升降级条件
core 只要有一点相关就更新 最先返回 入链 ≥ 5 或标记为桥接页
supporting 有明确新信息时更新 标准优先 新建页面默认等级
peripheral 跳过除非来源主要就是关于它的 最后返回 入链 ≤ 1 且 90+ 天陈旧
Tier 的核心目的 控制 token 成本。当知识库从 20 页膨胀到 2000 页时，不可能每次摄入都更新所有相关页面。Tier 就是那个"谁先谁后、谁该跳过"的决策器。举例：新摄入一篇"微信支付 V3 接口升级指南"，退款流程（core）一定会被更新，支付渠道（supporting）有新信息才更新，支付宝沙箱配置（peripheral）不会被碰。
06

编译管线：从原始文档到 Wiki 页面

编译在 wiki-ingest 技能中完成，是一个 8 步流程：

Step 1: 读取来源 agent 直接读取原始文档 ├── Markdown / 纯文本 → 直接读取 ├── PDF → 分页读取；学术论文特殊处理（提取图表、LaTeX 公式、结果表格） ├── 长 PDF (30+ 页) → 可选 PageIndex 预处理（先建目录树，只读相关页） ├── 图片 → 视觉模型转录文字、描述结构、提取概念 ├── JSON / CSV / HTML → 解析结构后蒸馏 ├── 聊天导出 → ChatGPT / Slack / Discord 等，按主题聚类 └── 网页 URL → defuddle CLI 抓取干净 markdown（去广告/导航） Step 2: 提取知识 从来源中识别： ├── 关键概念（值得独立页面的想法） ├── 实体（人物、工具、项目、组织） ├── 论断（可归属于来源的声明） ├── 关系（类型化边：extends / implements / contradicts / derived_from / uses / replaces） └── 开放问题（来源提出的未解问题） 每个论断标记溯源： ├── extracted → 来源明确说的（无标记） ├── inferred → 推断的（^[inferred]） └── ambiguous → 来源矛盾或模糊的（^[ambiguous]） Step 3: 确定项目归属 判断知识是项目特有还是通用 → 路由到对应目录 Step 4: 规划更新 ├── 目标每次摄入 10-15 个页面 ├── 检查是否已存在（via index.md + glob） └── Tier 过滤：core 总是更新，supporting 有新信息才更新，peripheral 跳过 Step 5: 写入 / 更新页面 ├── 新页面：完整 YAML frontmatter + 结构化正文 ├── 已有页面：合并新信息（不是追加），解决矛盾 └── 置信度公式：base_confidence = 来源数量分 × 0.5 + 来源质量分 × 0.5 来源质量分：arXiv 论文 1.0 → 博客 0.5 → LLM 生成内容 0.3 Step 6: 更新交叉引用 确保 wikilink 双向可达 Step 7: 更新 manifest 和特殊文件 ├── .manifest.json → 记录来源哈希、时间戳、创建/更新的页面 ├── index.md → 页面目录（一行摘要 + 标签） ├── log.md → 操作日志（仅追加） └── hot.md → 近期活动缓存 Step 8: 刷新 QMD 索引 qmd update + qmd embed + 验证

摄入模式

模式行为
Append（默认）SHA-256 对比 manifest，只处理新增/修改的文件
Full无视 manifest，重新处理所有文件
Raw处理 _raw/ 中的草稿，提升为正式页面后删除草稿

支持的文档类型

直接支持的文件格式

格式扩展名处理方式
Markdown / 纯文本.md .txt直接读取
PDF.pdf分页读取；学术论文提取图表 + LaTeX 公式
JSON / JSONL.json .jsonl解析结构后蒸馏
CSV / TSV.csv .tsv解析行列后蒸馏
HTML.html提取文本内容

图片格式（需要视觉模型）

格式扩展名处理方式
PNG / JPEG / WebP / GIF.png .jpg .webp .gif转录可见文字、描述图表结构、提取概念（标记为 ^[inferred]）、标注歧义

图片是"一等公民"——截图、白板照片、幻灯片捕获、架构图都支持。

不支持的格式

视频和音频不支持 仓库中没有任何视频或音频文件摄入的处理逻辑。

聊天导出

支持 ChatGPT（conversations.json）、Slack（per-channel JSON）、Discord、Claude Code（~/.claude 历史）、Codex、Hermes、OpenClaw、Pi、Copilot 以及通用聊天日志（[timestamp] User: message 格式）。处理方式是按主题聚类蒸馏，不按源文件保留对话结构。

网页 URL

通过 /ingest-url <url> 摄入。使用 defuddle CLI 抓取干净 markdown（去除广告、导航栏、cookie 弹窗，token 消耗减少 40-60%），WebFetch 作为回退。付费墙或 JS 渲染页面创建 stub 页面。

09

增量追踪与变更检测

虽然 obsidian-wiki 不支持自动编译，但它的增量追踪机制很精巧，确保手动触发时只处理真正变更的内容。

.manifest.json — 摄入追踪清单

JSON 账本，记录每个摄入过的来源文件：

  • content_hash（SHA-256）— 文件内容的哈希值
  • modified_at — 文件的 mtime
  • pages_created / pages_updated — 该来源产生了哪些 wiki 页面

变更检测流程

Append 模式下，摄入时对比当前文件的 SHA-256 和 manifest 记录。只处理内容哈希变更的文件，仅 mtime 变化但内容相同的文件被跳过。wiki-status 技能可计算完整差异：New / Modified / Touched / Unchanged / Deleted。wiki-update 检查 manifest 的 last_commit_synced，只跑 git log <last>..HEAD 处理变更部分。

自动化钩子（非文件监听）

钩子触发条件行为
daily-update.shmacOS launchd 每日 9:00检查来源新鲜度，报告陈旧状态，不重摄入
wiki-notify.sh打开终端时wiki > 20 小时未更新时打印横幅提醒
wiki-stop-capture.shClaude Code 会话结束有显著工作时提示快速捕获到 _raw/
GitHub sync (hourly cron)每小时提交推送已编译内容到 GitHub
10

知识图谱实现方式

没有图数据库，没有图计算库。 图谱完全构建于 [[wikilinks]] + YAML frontmatter 的 relationships: 字段。图是编译知识的涌现属性，不是预建索引。

图谱数据来源

Wikilink（正文中）— 无类型，弱关系

就像网页里的超链接，只表示"这个页面提到了那个页面"。

退款流程中需要使用 [[支付系统]] 提供的接口，
并通过 [[风控引擎]] 进行风险评估。

没有说是什么关系——可能是 uses、depends_on、mentions。

Relationships（frontmatter）— 有类型，强关系

明确声明的类型化、有向关系。

relationships:
  - target: "[[支付系统]]"
    type: uses
  - target: "[[风控引擎]]"
    type: uses

每条边都有明确的语义类型。

7 种关系类型

类型含义示例
extends扩展 / 泛化Transformer 扩展了 Attention 机制
implements具体实现BERT 实现了 Transformer 架构
contradicts矛盾 / 反驳论文 A 的结论与论文 B 矛盾
derived_from源自 / 改编微信 SDK 源自微信支付 API
uses使用 / 依赖退款流程使用支付系统
replaces替代 / 废弃V3 接口替代了 V2 接口
related_to相关（兜底）弱关联的通用关系

谁写入关系边

  • wiki-ingest：编译时从源文本中提取类型化关系，当"源文本使方向和类型明确无误时"写入 frontmatter。
  • cross-linker：后续扫描所有页面，发现未链接的提及，通过上下文模式匹配推断关系类型（如"X extends Y"映射到 extends），补充写入。使用积分制评分候选链接（精确匹配 +4，共享标签 +2，跨分类 +2 等）。

图谱可视化

两条路径，均不依赖 D3、force-graph、sigma 等库：

  1. Obsidian 原生图谱视图（推荐）：Obsidian 自己渲染 wikilink 图谱，graph-colorize 技能配置 .obsidian/graph.json 的 colorGroups 按标签/分类着色节点。
  2. wiki-export 生成 HTML：自包含 HTML 文件，使用 vis.js（CDN 加载）做力导向布局。节点按标签聚类着色、大小按度排序、类型化边用不同颜色（绿=extends，蓝=implements，红=contradicts），虚线表示 inferred/ambiguous 边。

图谱分析（wiki-status insights 模式）

由 LLM 读取所有 frontmatter，在上下文中构建邻接结构，计算：

  • Hub 页：入链最多的锚点页面
  • 桥页：连接不同标签簇的节点（删除会导致图分裂）
  • 标签簇内聚度：标签组内实际链接数与最大可能链接数的比值
  • 意外连接：跨分类的 wikilink（按意外度评分）
  • 孤页建议：接近 hub 但没有入链的死端页面
  • 图谱增量：与上次快照的差异
  • Tier 建议：入链 ≥ 5 → 建议升级 core；入链 ≤ 1 且 90+ 天陈旧 → 建议降级 peripheral
局限性 图谱分析由 LLM 在上下文中完成，不是代码算法。对于大型图谱（2000+ 页面），LLM 可能在处理邻接表时遗漏节点、搞混方向、产生幻觉边。这正是我们项目应该用代码替代 LLM 做图计算的地方。

检索管线：分层递进的混合检索

wiki-query 技能实现了一个 5 步分层管线，每一层成本递增。核心设计哲学：能用便宜的方法就别用贵的。

Step 1: 查询分类 将用户问题分类为： ├── 事实查找（"X 是什么？"） ├── 关系查询（"X 和 Y 什么关系？"） ├── 路径 / 多跳查询（"X 怎么连接到 Y？"） ├── 综合查询（"关于 X 的所有知识"） └── 缺口查询（"知识库中关于 X 还缺什么？"） Step 2: 索引扫描（最便宜） 不打开页面正文，只读元数据： ├── 读 index.md（页面目录 + 一行摘要 + 标签） ├── Grep frontmatter 的 title / tag / alias / summary ├── 按 tier 排序：core > supporting > peripheral └── 选出 5-10 个候选页面 Step 2b: QMD 语义搜索（可选，中等成本） 如果配置了 QMD_WIKI_COLLECTION： ├── 跑混合 lex + vec 查询（BM25 + 向量） ├── 结果充当"预读章节摘要" ├── 如果 QMD 完全回答了问题 → 直接跳到 Step 5 └── 否则用 QMD 的排序文件列表指导后续 grep/read Step 3: 段落提取（中等成本） 只对候选文件执行： ├── grep -A 10 -B 2 "<query-term>" <file> ├── 拉取匹配位置周围 15-30 行上下文 └── 不读全文，只读关键段落 Step 4: 全文读取（昂贵，最后手段） ├── 只读前 3 个候选的完整内容（按 tier 排序） ├── 跟随最多一跳 wikilink（打开一个链接的目标页面） └── 对于关系查询：读取 relationships frontmatter Step 4b: 多跳图遍历（仅特定查询触发） ├── 仅对路径 / 多跳查询触发 ├── 或关系查询发现两页面无直接边时触发 └── 有界 BFS：最大 3 跳，60 页上限 Step 5: 综合回答 ├── 综合多个页面信息为连贯回答 ├── 标注引用来源 ├── 标注信任度（stale / disputed / unverified） └── 标注知识缺口（wiki 中信息不足的部分）

grep -A 10 -B 2 解释

grep 是文本搜索命令。-A 10 表示匹配行之后再显示 10 行，-B 2 表示匹配行之前再显示 2 行。效果是返回匹配位置周围的一小段上下文，比读全文便宜得多——一个页面可能 200 行，但 grep 只返回 15-30 行关键段落。

"最多一跳 wikilink" 解释

"一跳"就是沿着一个 [[wikilink]] 打开目标页面读一下。假设搜到了 退款流程.md，里面有 [[支付系统]] 这个链接：读 退款流程.md 是 0 跳，沿着链接去读 支付系统.md 是 1 跳，但不再继续沿着 支付系统.md 里的链接往下跳（2 跳不允许）。这是成本控制——允许无限跳会连锁打开几十个页面。

各层的互补关系

机制找到什么何时触发
索引扫描（frontmatter grep）元数据中提到查询词的页面总是（Step 2）
QMD 语义搜索（BM25 + 向量）概念相关但未必有精确词重叠的页面配置了 QMD 时（Step 2b）
段落 grep候选页面中讨论该主题的具体段落索引 / QMD 不确定时（Step 3）
全文读取完整页面内容用于深度综合最后手段（Step 4）
图遍历（BFS）页面之间的连接路径仅多跳 / 路径查询（Step 4b）

QMD 混合搜索引擎

QMD（Query Markup Documents）是一个独立的本地搜索引擎（github.com/tobi/qmd），obsidian-wiki 把它作为可选层集成。QMD 不是知识库本身，只是 markdown 文件的搜索索引——vault 始终是 source of truth。

集合架构

集合配置变量索引内容使用方
wikiQMD_WIKI_COLLECTION编译后的 wiki 页面wiki-query（检索）、所有写入技能（刷新）
papersQMD_PAPERS_COLLECTION原始来源文档wiki-ingest（摄入前查重）

三种搜索模式

模式CLI 命令行为权衡
quality qmd query 'lex:...\nvec:...' -c col -n 8 --files 完整混合：BM25 + 向量 + LLM 重排序 最佳相关性，CPU 最慢
balanced 同上 + --no-rerank 混合 BM25 + 向量，无重排序 结果良好，更快
fast qmd vsearch "..." -c col -n 8 --files 纯向量语义搜索 最快，可能漏精确匹配

Lex + Vec 查询结构

一次请求同时发两条查询线：

lex: IAP 退款 回调 签名 验证 失败         ← BM25 关键词匹配
vec: 支付系统退款通知的签名校验错误处理方法  ← 向量语义匹配
  • Lex（词汇查询）：BM25 关键词匹配。擅长精确匹配——文件名、错误信息、专有名词、代码片段。
  • Vec（向量查询）：语义搜索。即使页面里没有完全一样的关键词，语义空间接近的也能命中。注意：vec 查询中连字符 -term 被视为取反，应使用自然语言。

QMD 通过 RRF（Reciprocal Rank Fusion）融合两路结果。RRF 原理：某页面在 lex 排第 3、在 vec 排第 5，融合分数 = 1/(k+3) + 1/(k+5)（k 通常 60），按总分重排序。

访问方式

通过 QMD_TRANSPORT 配置：

  • MCP（默认）：通过 MCP 工具 mcp__qmd__query
  • CLI：直接运行本地 qmd 二进制文件

AI 组件

所有 AI 组件通过 node-llama-cpp 在本地运行 GGUF 模型，不调云端 API。具体 embedding 模型取决于用户在 QMD 安装中配置的 GGUF 模型。每次写入后执行 qmd update + qmd embed 刷新索引和向量。

优雅降级

每个使用 QMD 的技能都检查 QMD_WIKI_COLLECTION 是否设置。如果未设置或 QMD 不可用，技能降级为 Grep / Glob 在 markdown 文件上做关键词匹配——功能完全可用，只是在大 vault 上更慢、语义能力缺失。

图遍历与多跳检索

BFS 遍历流程（详细步骤）

第一步：构建类型化有向邻接表

一次 grep 提取所有文件的 relationships: 块：

grep -A 20 "^relationships:" <vault>/**/*.md

每个条目产生一条有向、类型化边 source --type--> target。同时加入反向边（标记为 (reverse)），因为"连接"是双向的。正文中的 [[wikilinks]] 只在需要补全路径时才作为无类型 related_to 边使用。

第二步：定位端点

从 Step 2 的索引扫描中找到端点页面。如果端点模糊，默认选择 tier: core 的候选。

第三步：有界 BFS

  • 最大深度：默认 3 跳，用户说"深度"可放宽到 4
  • 访问上限：累计访问的不同页面超过 ~60 个时停止，返回部分结果
  • 双端点查询（X 到 Y）：找到最短路径后继续找最多 2 条备选路径
  • 单端点查询（X 可达的所有节点）：收集深度限制内所有可达节点，按跳距分组

第四步：输出路径链

[[退款流程]] --uses--> [[支付系统]] --implements--> [[微信SDK]] --derived_from--> [[签名算法]]

每条边标注类型和方向（forward 或 reverse）。如果某跳回退到无类型 related_to 边，标记为弱链。

为什么用 BFS 而不是 DFS

BFS 的核心保证 BFS 找到的第一条路径一定是最短的。对知识图谱来说，最短路径通常就是最直接、最有意义的关联。

DFS 可能先钻进一条深层但不相关的路径（比如 退款流程 → 日志系统 → 日志存储 → 日志归档 → 合规审计 → 签名算法，6 跳），找到答案就停了，不会回头去找那条 2 跳的近路（退款流程 → 支付系统 → 签名算法）。BFS 按层展开，先找到最短路径。

环的处理

图中会出现环，且在实际知识库中环很常见。 例如：退款流程 → 支付系统 → 风控引擎 → 退款流程（风控引擎发现异常时调用退款接口）。

BFS 处理环的方式：记录已访问节点集合（visited: Set），不重复访问。每个节点最多访问一次，时间复杂度 O(V+E)。环不会造成死循环。

代码 BFS

visited 集合是确定性的数据结构，不可能"忘记"已访问的节点。每次运行结果完全一致。

const visited = new Set([startId]);
const queue = [{ nodeId: startId, path: [] }];
while (queue.length > 0) {
  const { nodeId, path } = queue.shift();
  if (nodeId === targetId) return path;
  for (const edge of graph.getEdges(nodeId)) {
    if (!visited.has(edge.target)) {
      visited.add(edge.target);
      queue.push({ nodeId: edge.target,
        path: [...path, edge] });
    }
  }
}

LLM BFS（obsidian-wiki 方式）

LLM 在上下文中推理时，可能：

  • 忘记某节点已访问过（上下文太长注意力分散）
  • 漏掉平行路径（只看到一条边就往下走）
  • 幻觉出不存在的边
  • 搞混边的方向
  • 跳层（提前跳到深层节点）
  • 不可复现（同一问题两次结果不同）

成本对比：代码 BFS vs LLM BFS

维度代码 BFSLLM BFS
正确性确定性保证概率性推理，可能出错
完整性保证找到所有 ≤ N 跳路径可能漏路径
复现性每次结果一致受随机性影响
速度毫秒级秒级（token 生成）
语义理解不理解边类型含义可以理解并做语义剪枝
成本几乎为零消耗 token + 推理能力
最优方案：结合两者 代码做 BFS 保证完整性和正确性 → 找到的路径交给 LLM 做语义过滤和自然语言表达。比如代码返回 5 条路径，LLM 判断其中 3 条和用户问题真正相关，然后用自然语言解释含义。

代码 BFS 与边类型

BFS 算法本身不理解 implements 等边的语义含义，但我们可以做增强：

  • 优先级搜索：先只走 extends / implements 强关系边，找不到再走 related_to 弱关系边
  • 类型过滤：用户问"X 依赖什么"时，只走 uses / implements 边
  • 路径评分：extends 权重 3，implements 权重 2，related_to 权重 1，按总权重排序

代码不理解语义，但知道权重差异，这就够做路径排序了。最终的自然语言解释交给 LLM。

搜索与图遍历的结合方式

核心原则：搜索在前，遍历在后。遍历只在特定查询类型时触发。

一句话总结 搜索解决"找到相关页面"（大海捞针找到点），遍历解决"找到页面之间的路径"（在点之间画线）。

不同查询类型的处理流程

查询类型示例触发的步骤
事实查找 "什么是 attention？" Step 1 → 2 → 2b → (3) → (4) → 5
关系查询 "Transformer 和 Attention 什么关系？" Step 1 → 2 → 2b → (3) → 4（读 relationships）→ 5
路径 / 多跳查询 "退款流程和 HMAC-SHA256 怎么连接？" Step 1 → 2（定位端点）→ 4b（BFS 遍历）→ 5
综合查询 "关于退款的所有知识" Step 1 → 2 → 2b → 3 → 4 → 5
缺口查询 "知识库中关于 X 还缺什么？" Step 1 → 2 → 2b → 5（报告未覆盖部分）

多跳查询的完整示例

假设知识库中有以下关系：

退款流程 --uses--> 支付系统
退款流程 --uses--> 风控引擎
支付系统 --implements--> 微信SDK
支付系统 --implements--> 支付宝SDK
微信SDK --derived_from--> 签名算法
签名算法 --implements--> HMAC-SHA256

用户问："退款流程和 HMAC-SHA256 有什么关系？"

// Step 1: 分类为"路径/多跳查询" // Step 2: 索引扫描定位端点 端点 A: 退款流程.md 端点 B: HMAC-SHA256（可能在 签名算法.md 中提及） // Step 4b: 有界 BFS 第 0 层: 退款流程 第 1 层: 支付系统(via uses), 风控引擎(via uses) 第 2 层: 微信SDK(via implements), 支付宝SDK(via implements) 第 3 层: 签名算法(via derived_from from 微信SDK) → 签名算法 --implements--> HMAC-SHA256 ← 命中！ // Step 5: 输出路径链 [[退款流程]] --uses--> [[支付系统]] --implements--> [[微信SDK]] --derived_from--> [[签名算法]] --implements--> [[HMAC-SHA256]] 路径长度: 4 跳（在 3 跳限制内找到连接 + 1 跳到目标）

摄入时的反向关系

在查询时，搜索找页面、遍历找路径。但在摄入时，关系是反向构建的：wiki-ingest 从源文本中提取类型化关系写入 frontmatter，cross-linker 后续发现缺失的链接并推断类型。图遍历后来行走的图，是编译知识的涌现属性，不是预建索引。

编译质量保障机制

溯源标记（Provenance）

每个编译页面的 frontmatter 中标注知识来源比例：

provenance:
  extracted: 0.72    # 72% 直接从来源提取
  inferred: 0.25     # 25% AI 推理
  ambiguous: 0.03    # 3% 不确定

正文中用内联标记：^[inferred]（琥珀色背景）和 ^[ambiguous]（红色波浪下划线）。

置信度评分

base_confidence = source_count_score × 0.5 + source_quality_score × 0.5
source_count_score = min(distinct_source_ids / 3, 1.0)
source_quality_score = avg(quality per source)
  arXiv 论文: 1.0
  同行评审: 0.9
  官方文档: 0.8
  技术博客: 0.5
  LLM 生成: 0.3

去重检测（wiki-dedup）

使用 Jaccard 相似度（标题 token 集合）+ 归一化编辑距离检测近似重复概念。阈值 0.75 为候选，0.90 为"几乎确定是同一概念"。合并后创建重定向 stub 页面。

健康审计（wiki-lint，13 项检查）

  • 断链（[[wikilink]] 指向不存在的页面）
  • 孤页（无入链的页面）
  • 陈旧内容（raw 比 wiki 新）
  • 矛盾检测（跨页面的冲突声明）
  • 置信度漂移（数学计算与实际标注不一致）
  • 类型化关系完整性
  • Frontmatter 必填字段检查
  • ……等 13 项

Staging 审核模式

当 WIKI_STAGED_WRITES=true 时，页面写入 _staging/ 目录供人类审核，更新写成 .patch.md 文件，不直接修改正式页面。

综合页面的强制要求

每个 synthesis 页面必须包含"最强反驳"章节。"A synthesis that can't name its own strongest objection hasn't earned its conclusion."

我们方案的差距

差距 1：缺少 skills/ 分类 项目定位是"工作知识库"，操作知识（怎么配置、怎么排查、怎么部署）恰恰是最高频的查询场景。现在这些知识混在 concept 或 source 里，检索时无法精准命中"怎么做"类问题。
差距 2：source 类型有歧义 我们目前 type: source 同时指代"原始文档"和"编译后的来源摘要"。obsidian-wiki 把这个拆得很干净——raw/ 目录存不可变原始文件，references/ 存编译后的摘要。
差距 3：分类只在元数据里 我们的 type 只是 frontmatter 字段，检索时得读文件才知道类型。obsidian-wiki 用物理目录做分类，元数据扫描层甚至不用打开文件，光看目录路径就知道知识类型。这是分层检索能低成本运行的基础。

我们的优势

优势 1：完整的用户界面 obsidian-wiki 没有 UI，完全依赖命令行和 AI 编码工具。我们有 4 页面完整 UI（对话、文档、图谱、搜索），用户体验远优于纯 CLI。
优势 2：内嵌向量库 我们计划用 LanceDB 内嵌向量库，零服务、文件级存储，比依赖外部 QMD 更自包含，部署更简单。
优势 3：代码级图遍历 我们用代码实现 BFS，比让 LLM 推理更可靠、更快、可复现。obsidian-wiki 的 LLM BFS 是明显的短板。
优势 4：检索评估体系 我们在 PLAN.md 中规划了 eval_retrieval.py（P@k、MRR、nDCG），obsidian-wiki 完全没有检索质量评估基础设施。

关键设计启示

以下是 obsidian-wiki 中值得我们借鉴的核心设计理念：

1. 分层检索优先于全量搜索

元数据扫描 → 混合搜索 → 段落 grep → 全文读取 → 图遍历，每一层只在上一层不够用时才启动。比每次都全量向量检索高效得多。

2. 物理目录结构服务于检索

分类不只是标签，而是物理目录。元数据扫描层甚至不用打开文件，光看目录路径就知道知识类型，这是低成本分层检索的基础。

3. Tier 分级控制 token 成本

core / supporting / peripheral 三级控制更新和检索的优先级。从 20 页到 2000 页的扩展性依赖于此。

4. 溯源标记建立信任链

extracted / inferred / ambiguous 三级溯源 + 置信度评分，让用户和 AI 都能判断知识的可靠程度。

5. 图遍历应该用代码实现

obsidian-wiki 让 LLM 做 BFS 是其最大短板。确定性算法应该用代码实现，LLM 只负责语义综合和自然语言表达。各司其职。

6. 编译产物应可审计

manifest.json 记录每个来源的 SHA-256 哈希和产出页面映射，支持 diff review（原始 vs 编译对比）、增量编译、覆盖率追踪。

7. 综合页面必须包含"最强反驳"

避免 AI 产生一面之词的综合分析。强制包含对立观点，提高知识质量。

8. 建议的分类调整

将 wiki/ 下按功能拆子目录（至少加 wiki/skills/ 和 wiki/references/），将 source 类型拆为 raw（不可变原始文件）和 reference（编译后摘要），考虑加 journal/ 追踪知识演变。

9. 增量编译基于内容哈希

SHA-256 对比，只处理真正变更的文件。仅 mtime 变化但内容相同的文件跳过。

10. 搜索和遍历各司其职

搜索解决"找到相关页面"（大海捞针找到点），遍历解决"找到页面之间的路径"（在点之间画线）。两者互补而非竞争。
