## 2. Research Findings

### 2.1 本项目现有架构底线（重设计必须显式决定保留或推翻）

| 决策 | 现状 | 出处 |
|---|---|---|
| 主键 | `BIGINT IDENTITY` + 对外 `public_id UUID` | models/base.py |
| 物理外键 | **全库不建**，应用层维护 | models/base.py:8 |
| 多租户 | 每表 `tenant_id`（partial index `WHERE deleted_at IS NULL`） | TenantMixin |
| 软删除 | `deleted_at`（content_chunks 除外，硬删） | TimestampMixin |
| 文档模型 | `sources → documents → document_revisions`（连接器/逻辑身份/不可变修订三层） | document.py |
| 向量 | `content_chunks.embedding halfvec` 内嵌列 + partial HNSW（按 dim 分区） | 001 迁移 |
| 关键词 | pg_search BM25（chinese_lindera）直接索引 `content_chunks.text` | 003 迁移 |
| 任务队列 | Dramatiq + Redis，DB 只有 `processing_runs`（账本）+ `processing_spans`（阶段树） | workers/ |

| 文件存储 | `document_revisions.storage_key` → MinIO 直连，DB 无资源表 | document.py |

### 2.2 WeKnora 知识库域概念对照与差距

| 领域概念 | WeKnora | 本项目 | 差距结论 |
|---|---|---|---|
| 知识库 | knowledge_bases（大量 JSONB 配置列内联） | knowledge_bases + kb_rag_configs + kb_wiki_configs | 本项目更规范化，**不建议**回退到 JSONB 大杂烩 |
| 文档条目 | `knowledges` 单表（file_*、parse_status、enable_status、custom_metadata、channel、pending_subtasks_count） | documents（逻辑身份）+ document_revisions（不可变版本+解析状态） | 本项目有版本/来源概念（更强）；WeKnora 有 enable_status、custom_metadata、finalizing 富化阶段（本项目缺） |
| 分块 | chunks：chunk_type(text/table/image)、parent/pre/next 链、metadata、relation_chunks、可编辑（source_content/content_revision/index_status/last_editor_id/context_header） | content_chunks：chunk_index、source_locator、text_sha256；不可编辑、硬删 | WeKnora 块能力显著更多 |
| 块修订 | chunk_revisions 表 | 无 | 缺 |
| 向量 | 独立 embeddings 表（source_id+source_type、dimension、halfvec、is_enabled、tag_id）+ content 冗余（BM25） | chunk 表内嵌 halfvec + BM25 直索引 text | 架构路线不同；本项目当前路线更省一次 JOIN |
| 向量库注册 | vector_stores（pgvector/ES/Milvus 可插拔） | 无（固定 pgvector） | 缺（是否需要待定） |
| 标签 | knowledge_tags + knowledge_tag_relations（多对多） | 无任何标签 | 缺 |
| 临时文档 | temporary_documents（会话内上传，过期清理） | 无（项目无 chat 会话） | 依赖 chat，暂 Out of Scope |
| Wiki 页面 | wiki_pages（in/out_links、chunk_refs、source_refs 均为 JSONB 数组；version 字段） | wiki_pages + wiki_page_links + wiki_page_document_refs + wiki_page_evidence_refs（实体化血缘，含证据引文 sha256 核验） | 本项目血缘更强；WeKnora 有 revisions/issues 两张配套表 |
| Wiki 修订 | wiki_page_revisions | 无（只有 version 乐观锁） | 缺 |
| Wiki 问题上报 | wiki_page_issues | 无 | 缺 |
| 数据源 | data_sources + sync_logs（独立日志表） | sources + processing_runs(run_type=source_sync) 承载 | 本项目统一账本路线（更强）；sync_logs 的分箱统计可由 runs 聚合 |
| 资源层 | storage_backends + resources + resource_bindings + resource_access_grants | 无（storage_key 直连 MinIO） | 缺统一资源注册/分享授权 |
| 任务队列 | task_pending_ops + task_dead_letters（DB 去重队列 + 死信） | Dramatiq+Redis（死信在 Dramatiq 重试落地，见 2026-08-06 spec） | 已有架构决策，**不采纳** DB 队列 |
| 处理追踪 | knowledge_processing_spans（单层，按 knowledge_id+attempt） | processing_runs + processing_spans（两级，含 idempotency_key/options_snapshot） | 本项目更强，**保留** |
| 检索日志 | 无（仅 audit_logs） | search_logs（脱敏+feedback+TTL） | 本项目独有，保留 |

### 2.4 任务表对照分析（processing_runs/spans vs WeKnora 任务三表）

> 背景事实（来自 2026-08-06 重试死信 spec + 2026-08-14 worker 复盘）：队列 = Dramatiq+Redis；重试 max_retries=3 + 指数退避；`release_run` CAS running→pending；`RunFailureMiddleware`（before=Retries）在消息最终死亡时标 Run failed；Reaper 每 300s 扫描（pending 看 updated_at>5min、running 卡死标 failed）；002 迁移已**刻意删除** fencing/lease 字段（execution_token/epoch/lease_expires_at/worker_id/heartbeat_at）。

| WeKnora 机制 | 本项目现状 | 借鉴结论 |
|---|---|---|
| `task_dead_letters`：死信 payload+last_error+fail_count 永久落库，可 SQL 手动重放 | Dramatiq DLQ 在 Redis，**TTL 仅 7 天且 payload 不落库**；Run 标 failed 后无法得知原始消息参数，重放只能靠人工调 API | ✅ **值得借鉴（最有价值的一项）**：新增 DB 死信归档表，RunFailureMiddleware 标 failed 时同步写入（run_id、task_type/scope、消息 payload、last_error、fail_count），解决 7 天过期与不可审计问题 |
| `knowledge_processing_spans.kind`（root/stage/subspan/generation） | spans 有 parent_span_id 树但无 kind，无法快速筛"LLM 调用类 span" | ✅ 低成本增强 |
| `knowledge_processing_spans.duration_ms` 物化耗时 | 由 finished_at-started_at 现算，聚合查询要全表算时间差 | ✅ 低成本增强 |
| `knowledge_processing_spans.error_detail`（完整堆栈原文） | spans 仅 error_code+error_message(≤1000)，堆栈只在日志里 | ✅ 建议采纳（配合死信表，排障不再翻日志） |
| `knowledge_processing_spans.input/output JSONB` | 仅 metrics 数值 | ⚠️ 可选：有膨胀风险，按阶段白名单写入（如 embed 的模型参数、生成 prompt 摘要），暂缓 |
| `task_pending_ops.claimed_at` 过期认领恢复（FOR UPDATE SKIP LOCKED） | 002 已刻意删除 lease/fencing，Reaper 兜底卡死 Run | ❌ **不采纳**：重新加回等于推翻 002 的架构决策；Dramatiq 负责投递、Reaper 负责恢复，职责已清晰 |
| `task_pending_ops.dedup_key` 批内去重 | runs.idempotency_key（partial unique）覆盖 API 级去重；单进程 -t 1 串行 | ❌ 不需要：并发模型不同 |
| `task_pending_ops` DB 队列本体 | Dramatiq+Redis | ❌ 架构不同，Q2 已决策不搬 |

**小结**：任务域表结构本身（runs 两级账本）优于 WeKnora 单层 spans，保留；可叠加的优化 = ①DB 死信归档表 ②spans 加 kind/duration_ms/error_detail 三列。是否纳入待 Q3 确认。

**反向分析：可删除的死字段（2026-08-20 代码扫描验证）**

判定标准：全仓（app + tests）无写入方且无读取方。`create_run` 仅两个调用点（rag_ingestion.py:178、document.py:163），二者均未传以下参数：

| 表.字段 | 证据 | 结论 |
|---|---|---|
| `processing_runs.retry_of_run_id` | 无调用方传值，无读取方（业务重跑 API 从未建成） | ❌ 死字段 |
| `processing_runs.attempt_no` | 恒为默认值 1；重试递增的是 **span** 级 attempt_no（runtime.py:231 是 span 创建） | ❌ 死字段（恒 1） |
| `processing_runs.idempotency_key` | 无调用方传值；001 的 partial unique 索引从未命中 | ❌ 死字段 + 死索引 |
| `processing_runs.effective_config_version` | 无调用方传值，无读取方（实际配置信息由 options_snapshot 承载） | ❌ 死字段 |
| `processing_spans.model_key` | 无写入方（grep 仅命中 kb_rag_configs.embedding_model_key，另一张表） | ❌ 死字段 |
| `processing_spans.input_tokens` / `output_tokens` | 无写入方（模型指标实际走 metrics JSONB） | ❌ 死字段 ×2 |

边界项（不算死，但新设计可斟酌）：`runs/spans.public_id`（当前无 API 消费，若任务域也 UUID 化则自然消失，见 Q10）；spans 的 `tenant_id/kb_id` 冗余（查询都走 run_id，可由 run 反查）。

原则：这些字段多为「为未建成的功能预埋」（API 幂等、业务重跑、配置血缘、模型观测）。新设计按 YAGNI 不携带，等功能真正落地时随功能迁移再加。
