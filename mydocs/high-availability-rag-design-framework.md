# 高可用 RAG 知识库设计思路框架

> 本文档是高可用 RAG 系统的五阶段全景设计框架，作为本项目 RAG 建设的目标蓝图。
> 配套阅读：[weknora-rag-design-survey.md](./weknora-rag-design-survey.md)（WeKnora 生产实现调研）

---

## 核心原则

**"垃圾进，垃圾出"（Garbage In, Garbage Out）**：数据源的清洗与重构质量，直接决定整个 RAG 系统的性能上限。

---

## 一、数据准备阶段（Data Preparation）— 决定系统的地基

### 1.1 数据加载与清洗（Data Loading & Cleaning）

**如何做**：利用文档加载器（如 Unstructured、PyMuPDF4LLM 等）将 PDF、Word、Markdown 等多源异构数据统一标准化，提取纯文本，同时抽取文档来源、页码、作者等关键元数据。

**设计考量**：
- **格式保留与清洗**：能否精准识别复杂的表格、版式、甚至扫描件图像（必要时引入 OCR 模块或多模态解析器）
- **信息无损**：如何保证排版混乱的文档转换后语义没有断裂

### 1.2 文本分块（Text Chunking）— 检索的最小单位

**如何做**：将整篇长文档切分成更小的文本块（Chunks），作为后续向量化的基本单位。常见有固定大小切分、递归字符切分、基于 Markdown/HTML 结构的切分，以及语义分块等。

**设计考量**：
- **块不是越大越好**：块过大导致向量压缩时信息稀释与损失，还会在生成阶段引发"大海捞针"（Lost in the Middle）效应
- **上下文碎片化冲突**：块切得太小会丢失周围重要背景。两种先进分块策略：
  - **父子文本块策略**：即"小块检索，大块生成"。索引和匹配时使用小的子块，但生成时自动将完整的父文档（或上一级段落）提供给大模型，确保上下文完整
  - **句子窗口检索（Sentence Window Retrieval）**：将文档拆分为单个句子作为节点来索引以获取极速高精匹配，但在元数据中关联其前 N 个和后 N 个句子，在送给 LLM 前利用后处理器将上下文扩展替换，从而兼顾精准度与丰富度

### 1.3 元数据增强（Metadata Enrichment）

**如何做**：在分块的同时，为文本块注入结构化的标签（如：文件名、章节路径、难度等级、创建时间、分类标签等）。

**设计考量**：
- 元数据是进行精准"非语义硬性过滤"的核心（如"只找 2025 年发布的文档"）。构建时必须设计统一的 Schema 规范，利用元数据建立起清晰的"实体地址"

## 二、索引构建阶段（Index Construction）— 建立知识的脑图

将清洗后的标准化数据，映射并固化到特定的检索结构中（向量、关键词或关系图谱）。

### 2.1 向量嵌入模型选型（Embedding Model）

**如何做**：通过嵌入模型将文本块转化为高维密集向量。

**设计考量**：
- 结合 MTEB 排行榜评估模型在"检索（Retrieval）"任务下的表现、支持的语言、模型大小以及向量维度（维度越高信息越丰富，但计算和内存资源消耗也呈指数级上升）
- 评估最大 Token 限制，确保文本分块的大小不会超出嵌入模型的窗口上限导致强制截断信息

### 2.2 向量数据库选型与部署（Vector Database）

**如何做**：选用如 Milvus、Qdrant、FAISS 等专门的向量数据库管理海量高维向量。

**设计考量**：
- **索引类型取舍**：追求 100% 召回用 FLAT（暴力检索，速度慢）；追求低延迟和高召回用 HNSW（基于图的索引，但极度消耗内存）；追求高吞吐用 IVF 系列（基于聚类，内存占用小）
- **写入与重建策略**：大规模离线批量一键构建索引（模式 A），还是线上实时业务边流入、边写入缓冲、边后台异步自动建索引（模式 B）

### 2.3 范式革新：图谱检索增强（GraphRAG）构建

**如何做**：传统 RAG 在跨文档联结、多跳推理（例如：查找 A 公司的母公司的投资对象）上表现极差。高级架构应考量引入知识图谱（如 Neo4j/NebulaGraph 等），抽取出实体（节点）和显式语义关系（边），构建层次化的实体-关系图。

**设计考量**：
- **图谱质量控制**：独立片段抽取容易引入主题无关性、逻辑不一致和结构碎片化问题。架构上需要设计如 MemGraphRAG 中提出的"全局记忆、模式过滤与冲突消解"机制，通过在入库时增加诊断与修正环（仲裁），从而过滤冗余，保障图的逻辑统一性

## 三、检索优化阶段（Retrieval Optimization）— 实现精准的知识召回

### 3.1 查询重构与翻译（Query Rewriting & Translation）

**如何做**：用户的原始提问往往过于口语化或含糊不清，并不适合直接用于向量匹配。利用 LLM 提前进行意图预处理：

- **多查询分解（Multi-query）**：将复杂问题拆解为多个具体的子问题分别检索，最后合并去重，防止漏掉关键证据
- **退步提示（Step-Back Prompting）**：抽象出更通用的背景原理，帮助模型奠定推理基础
- **假设性文档嵌入（HyDE）**：引导 LLM 先虚构出一个"完美假设性答案"，然后拿这个假设答案的向量去数据库搜索相似的真实文档，将"提问-文档"检索转化为更简单的"文档-文档"检索

### 3.2 智能查询路由（Query Routing）

**如何做**：当系统接入多个异构数据源（向量库、SQL 关系库、图数据库）时，通过"智能调度中心"决定如何分发查询。

**设计考量**：
- 通过 LLM 意图识别决策，还是通过语义向量相似度进行快速的无 LLM 路由，以在大并发下降低延迟和成本

### 3.3 多路混合检索与融合（Hybrid Search）

**如何做**：并行执行密集向量检索（懂同义词、泛化性强）与稀疏向量检索（如 BM25）（关键词精确匹配，用于锁死型号、代码和特定实体），并将结果集融合。

**设计考量**：
- **融合算法**：是使用不关心原始得分、只看两路排名的倒数排序融合（RRF）算法，还是使用需要先对得分归一化、再通过参数 α 进行调节的加权线性组合

### 3.4 重排序（Re-ranking）与上下文压缩（Context Compression）

**如何做**：
- **Re-ranking**：初步检索（召回）出来的数十个文档，利用高精度的特定重排模型（如 Cross-Encoder、ColBERT）进行精细化二次打分并重新排序，确保最相关的黄金证据排在最前面
- **Compression**：通过内容提炼或文档过滤器（如 ContextualCompressionRetriever），强力过滤掉多余的"文本噪音"，只将高浓缩的核心语义段送入 LLM，从而降低 Token 消耗并极大减轻幻觉

### 3.5 校正检索机制（Corrective-RAG）

**设计考量**：
- 系统不应盲目信任检索结果。引入自我反思循环：由一个检索评估器对检索到的内容进行"正确、不正确、模糊"分类。若正确则执行精炼，若不正确则认为知识库不足，主动触发"查询重写"并调用外部工具或 Web 搜索引擎拉取外部信息

## 四、生成集成阶段（Generation & Integration）— 最终答案的华丽蜕变

将前几步检索到的浓缩黄金证据（上下文）和原始问题融合进 Prompt 模板中，交付给 LLM 进行逻辑编排和生成。

### 4.1 提示工程（Prompt Engineering）

**设计考量**：设计严格的系统 Prompt，要求 LLM 必须严格基于上下文回答，并且在无法从上下文中找到依据时明确输出"不知道"，同时提供每一句断言的出处溯源（页码或来源标记），以此增加可信度，防止产生虚假幻觉。

### 4.2 格式化生成与工具调用（Formatted Generation & Tool Calling）

**设计考量**：
- 如果系统要跟下游业务对接，大模型必须输出结构化数据（如 JSON/XML）
- 在选型上，如果底座模型支持，应当优先使用原生的 Function Calling（Tool Calling），这比通过 Prompt 强行"请求"模型输出 JSON 的可靠性和意图识别准确度要高得多。若模型不支持，再回退到使用 Pydantic Output Parser 做 JSON Schema 注入和校验解析

## 五、系统评估与可观测性阶段（Evaluation & Observability）— 闭环持续优化

**一个不可评估的 RAG 系统是无法投入生产并持续迭代的。**

### 5.1 RAG 评估三元组（RAG Triad）理论

构建评估体系时，应围绕以下三个黄金维度进行量化：

- **上下文相关性（Context Relevance）**：评估检索器。召回的段落里，垃圾和噪音比例有多少？金标准证据是否被全部召回
- **忠实度 / 可信度（Faithfulness）**：评估生成器。LLM 吐出来的答案是否完全来自于上下文？有没有出现自我发挥的"幻觉"
- **答案相关性（Answer Relevance）**：评估端到端体验。最终的回答是否直接、完整、有效地解答了用户的原始问题

### 5.2 自动化工具链引入

- **LlamaIndex Evaluation**：深度集成于代码中，适合在开发阶段快速编写测试用例，对比两个不同检索策略（如常规分块 vs. 句子窗口）的性能表现
- **RAGAS**：支持无参考评估（在无标注标准答案时使用 LLM 充当裁判对三元组进行自动打分评估），是做大规模性能回归测试的利器
- **Arize Phoenix**：生产环境中的可观测性可溯源引擎。通过代码插桩捕获系统的调用轨迹（Traces），在 Web UI 中直观排查线上 Bad Case 并快速进行根本原因诊断（是检索不行、还是生成幻觉）

## 七、建议的演进路线

### P0：检索地基（当前 spec，已 Plan 待批准）
- 真 BM25（pg_search/ParadeDB）+ 加权 RRF（0.7:0.3）+ 阈值过滤 + 过检索 + nearby 上下文增强 + 嵌入标题前缀

### P1：MVP 核心闭环
- **生成集成**（chat + prompt + 溯源 + "不知道"兜底）— RAG 的 "G" 完全缺失，最该补
- **SearchLog 接入**（检索流程写入日志，评估/Boost 的数据基础）
- **检索侧 span 追踪**（线上 Bad Case 定位）

### P2：分块升级（另立 spec）
- 父子分块（小块检索、大块生成）
- heading-aware 结构化分块
- chunk 元数据增强（页码/章节路径下沉）

### P3：检索增强
- Rerank（Cross-encoder，放在生成流水线末段，只对 top-N 重排）
- 查询重构（HyDE/Multi-query）

### P4：评估闭环
- RAGAS 无参考评估（三元组）
- 检索质量回归测试集

### P5：高级能力
- GraphRAG
- 向量库可插拔（Milvus/Qdrant）
- CRAG 自我反思

## 八、关键设计决策参考（来自 WeKnora 生产实践）

| 设计点 | WeKnora 做法 | 启示 |
|---|---|---|
| 分块策略 | 三层策略链(auto/heading/heuristic)+父子分块+ContextHeader面包屑 | 策略链+降级机制比单一策略更健壮 |
| 向量库 | 11引擎可插拔双轨制(env-store/DB-store) | 适配层抽象，应用层不感知后端 |
| 嵌入 | 未区分query/passage task(对称模型bge-m3) | 对称模型不需要task区分，非对称模型(如Jina)需要 |
| 混合检索 | RRF加权0.7:0.3, 仅归一化向量分数 | RRF基于排名免疫尺度，BM25无需归一化 |
| Rerank | Cross-encoder+MMR去冗余+复合分数+阈值降级 | MMR解决结果冗余，复合分数平衡多信号 |
| 生成 | 双路径(chat_pipeline单轮/Agent Runtime多轮ReAct) | 简单QA用流水线，复杂推理用Agent |
| 引用回链 | 双层句柄系统(私有cN<->公共kb标签) | 模型只见短句柄，安全且token友好 |
| 评估 | 传统指标(Precision/Recall/BLEU/ROUGE)，无RAG Triad | 生产系统也未必上RAG Triad，传统指标+人工验收可起步 |
| 可观测性 | Langfuse(OTLP)+DB Span双层 | 摄入+检索双侧tracing，跨进程traceparent传播 |
