01

两个项目一句话定位

obsidian-wiki

"编译型知识库" — 把原始文档通过 AI 编译成互相链接的 wiki 页面，查询时直接消费编译产物。

核心隐喻：wiki 是编译产物，AI agent 是维护者，Obsidian 只是查看器。

形态：CLI + 40 个 AI 技能文件（SKILL.md），无 UI，纯 markdown 输出。

GBrain

"Postgres 原生的个人知识大脑" — 混合 RAG 搜索 + 知识综合层 + 自连线图谱，为 AI Agent 提供持久记忆。

核心隐喻："Search gives you raw pages. GBrain gives you the answer."

形态：完整 TypeScript 服务（Bun 运行时）+ Admin SPA + MCP 服务器 + CLI。

两者都受 Karpathy "compile, don't retrieve" 理念影响，但走了不同的路。obsidian-wiki 走纯编译路线（产物是 markdown 文件），GBrain 走数据库+搜索路线（产物是 Postgres 中的结构化行）。

03

知识编译 vs 实时检索

obsidian-wiki — 编译范式

写入时重：摄入 8 步流程（读取→提取→归属→规划→写入→交叉引用→manifest→索引），一篇文档产出多个 wiki 页面。

读取时轻：查询时直接读编译好的 wiki 页面，不需要重新理解原始文档。

延迟：摄入慢（每篇文档 10-15 页产出，需要 LLM 调用），查询快。

一致性：编译产物可能与原始文档不同步（需要手动重摄入）。

GBrain — 混合范式

写入中等：导入时分块 + 嵌入 + 自动提取实体/关系，但不做深度知识重组。

读取中等：混合搜索（向量+关键词+RRF）+ 可选 LLM 综合（gbrain think）。

延迟：摄入较快（分块+嵌入），查询需要搜索+可选综合。

一致性：数据库即 source of truth，无不同步问题。

obsidian-wiki 的"编译"比传统 RAG 多做了一步：不仅分块嵌入，还进行知识重组——同一信息按认知功能拆分到不同页面，跨来源信息综合到 synthesis 页面。这是它的核心创新，也是最消耗 token 的地方。

GBrain 不做知识重组（导入时保留原始文档的分块结构），但用更强的搜索能力弥补——混合搜索 + 图信号 + 重排序 + 两阶段检索，确保查询时能快速定位正确内容。它的"综合"发生在查询时（gbrain think），而非写入时。

权衡总结 编译范式（obsidian-wiki）：查询更快、更准、更省 token，但维护成本高、编译可能引入错误。检索范式（GBrain）：更实时、更可靠，但每次查询都要做搜索+综合，token 成本分散在每次查询中。

05

知识图谱实现

维度obsidian-wikiGBrain
存储方式wikilinks + YAML relationships（纯文件）Postgres edges 表（类型化有向边）
构建时机编译时 LLM 提取 + cross-linker 后续补充每次写入时零 LLM 调用提取（正则+启发式规则）
边类型7 种（extends/implements/contradicts/derived_from/uses/replaces/related_to）15+ 种（attended/works_at/invested_in/co_authored 等，面向人物/公司关系）
遍历算法LLM 在上下文中做 BFS（概率性，可能出错）SQL 递归查询（确定性代码实现）
可视化Obsidian 原生图谱 + vis.js HTML 导出Admin SPA 中的图谱视图
图谱分析Hub/桥页/聚类（LLM 计算，不可靠）回链查询/子图/路径查找（SQL，确定性）
图影响搜索遍历结果参与回答综合graph-signals 模块直接影响搜索排序分数

两者最大的区别在图谱构建方式。obsidian-wiki 用 LLM 从文本中提取关系边——精确但昂贵（每次摄入都消耗 token）。GBrain 用零 LLM 调用的启发式规则提取——便宜但受限于规则覆盖率（对人物/公司/事件关系很好，对抽象概念关系可能不足）。

图谱的不同目的 obsidian-wiki 的图谱服务于"多跳推理"——"退款流程和 HMAC-SHA256 有什么关系？"需要沿着 4 条类型化边走。GBrain 的图谱服务于"搜索增强"——相邻页面获得排序加分（graph signals），主要用于发现"这个人参加了哪些会议、投了哪些公司"。
06

分类体系与知识组织

维度obsidian-wikiGBrain
分类原则按认知功能（6 类：concepts/entities/skills/references/synthesis/journal）按知识领域（Schema Packs，15 种规范类型，可自定义）
物理组织目录即分类（concepts/ entities/ skills/ ...）Postgres brain_id 逻辑分区（多 brain 隔离）
多项目支持projects/ 子目录镜像分类结构多 brain 架构（每个 brain 独立的 search scope）
优先级机制Tier（core/supporting/peripheral）Source-tier Boost（不同来源类型的搜索权重提升）
生命周期draft → reviewed → verified → disputed/archived无显式生命周期
分类对检索的影响物理目录决定检索优先级（问"怎么做"先看 skills/）类型只影响 schema 验证和显示，不影响搜索路由

obsidian-wiki 的分类更功能性——同一信息按功能拆到不同目录（一篇论文 → concepts/ 提取概念 + entities/ 提取人物 + references/ 做摘要）。GBrain 的分类更领域性——人物是人物、公司是公司、会议是会议，不做拆分重组。

对 LLM Wiki 3.0 的启示 你的 4 类型系统（concept/entity/source/synthesis）已经接近 obsidian-wiki 的方向了。缺少的关键一块是 skills/（操作知识）——工作知识库中"怎么配置 X"、"怎么排查 Y"是最高频查询。
07

AI 集成方式

维度obsidian-wikiGBrain
AI 在哪里AI Agent 是唯一执行者——读来源、提取知识、写页面、更新链接全靠 AIAI 限制在特定环节——嵌入/综合/丰富/重排，搜索和图遍历用代码
LLM 提供商取决于宿主 AI 编码工具（Claude Code / Cursor / Codex 等）16+ 提供商（OpenAI/Anthropic/Google/Voyage/ZeroEntropy/Ollama/DashScope 等）
嵌入模型本地 GGUF（via QMD + node-llama-cpp）可配置（OpenAI/Voyage/本地 ollama 等）
MCP 集成QMD 通过 MCP 访问（可选）完整 MCP 服务器（30+ 工具，stdio/HTTP 双传输）
Agent 能力无自主 Agent（依赖宿主 AI 工具执行技能）Minions 子 Agent 队列 + 自主任务执行 + Shell 作业
离线能力无 QMD 时完全离线（grep/glob 回退）PGLite 模式完全本地，但嵌入需要 AI 提供商
Dream Cycle无（手动维护）24/7 cron 驱动的自动丰富/合并/去重/引用修复

obsidian-wiki 把 AI 当作"通用劳动力"——一切操作都是"提示 AI 做某事"。GBrain 把 AI 当作"专项服务"——嵌入是嵌入模块、综合是综合模块、重排是重排模块，各有明确边界。

obsidian-wiki 的致命弱点 因为一切都由 AI 执行，结果不可复现（同一摄入两次产出不同页面）、不可验证（没有代码逻辑可审计）、成本不可控（复杂文档可能产生大量 token 消耗）。GBrain 的代码逻辑确定性强，只在必须用 AI 的环节才用 AI。
08

各自的优缺点

obsidian-wiki

优点

  • 极度轻量：无数据库、无服务进程、无构建系统，只需文件系统
  • 可移植性：产出是标准 markdown，任何编辑器都能打开
  • 知识重组创新：编译时按认知功能拆分，查询精度高
  • 分层检索优雅：低成本层先行，省 token
  • Tier 机制：有效控制大 vault 的更新和检索成本
  • 溯源标记：extracted/inferred/ambiguous 建立信任链
  • 增量追踪：SHA-256 哈希确保只处理变更内容
  • 综合页面的"最强反驳"要求：提高知识质量

缺点

  • 结果不可复现：AI 编译相同文档两次产出不同
  • 编译可能引入错误：AI 提取/推理可能产生幻觉
  • 无 UI：完全依赖命令行和 AI 编码工具
  • 手动触发：用户需要记得"该更新 wiki 了"
  • LLM BFS 不可靠：图遍历用 LLM 推理，可能漏路径/搞混方向
  • 无评估体系：不知道编译质量如何、检索是否准确
  • 规模限制：纯文件操作，对 2000+ 页面的图谱分析性能不明
  • 不支持视频/音频

GBrain

优点

  • 搜索引擎极其成熟：30+ 模块，混合检索 + 重排 + 图信号
  • 确定性代码逻辑：搜索/图遍历/分块全用代码，可复现可审计
  • 完整评估框架：LongMemEval + 多种基准测试
  • Dream Cycle 自动维护：24/7 自动丰富/去重/修复
  • 代码智能：tree-sitter 37 语言语义分块 + 调用图
  • MCP 标准协议：30+ 工具，任何 MCP 客户端可消费
  • 多 LLM 支持：16+ 提供商，本地/云端灵活切换
  • 生产验证：14.6 万页面的实际部署
  • 零 LLM 图谱构建：启发式规则提取，成本为零

缺点

  • 复杂度极高：数百个 TS 文件，学习曲线陡峭
  • 重依赖：Postgres + Bun + pgvector，部署非平凡
  • 不做知识重组：原始文档分块存入，缺乏 obsidian-wiki 的认知功能拆分
  • 图谱类型受限：启发式规则主要覆盖人物/公司/事件关系，抽象概念关系弱
  • 面向个人/投资者场景：边类型（attended/invested_in 等）不通用
  • 无编译缓存思想：每次查询都做实时搜索+综合
  • Admin UI 简单：只是运维面板，不是用户友好的知识浏览器
  • 无溯源标记：不追踪知识的 extracted/inferred 来源
09

对 LLM Wiki 3.0 的具体建议

基于两个项目的分析，以下是 LLM Wiki 3.0 可以直接借鉴的设计决策：

一、从 obsidian-wiki 借鉴

建议 1：增加 skills/ 分类 当前 4 类型（concept/entity/source/synthesis）缺少操作知识分类。工作知识库中"怎么配置"、"怎么排查"是高频场景，应该单独分类以支持"怎么做"类查询的精准路由。
建议 2：借鉴分层检索策略 不要每次查询都做全量向量搜索。设计元数据快速扫描层（只读 frontmatter/标题/标签）→ 混合搜索层 → 全文读取层。低成本层先行，大多数查询在第一层就能回答。
建议 3：引入 Tier 机制 给每个 wiki 页面标注 core/supporting/peripheral 等级。core 页面检索时优先返回、摄入时总是更新；peripheral 页面检索时排后、摄入时跳过。控制知识库从 50 页膨胀到 500 页时的 token 成本。
建议 4：溯源标记 每个编译页面标注 provenance: {extracted: 0.7, inferred: 0.25, ambiguous: 0.05}。正文中推理性内容用 ^[inferred] 标注。让用户一眼看到哪些是原文说的、哪些是 AI 推理的。
建议 5：综合页面包含"最强反驳" synthesis 类型页面强制要求包含 "Strongest Objection" 章节。避免 AI 产生一面之词的综合分析。
建议 6：SHA-256 增量追踪 manifest 记录每个源文件的内容哈希。编译时只处理哈希变更的文件，mtime 变化但内容相同则跳过。

二、从 GBrain 借鉴

建议 7：搜索引擎模块化 GBrain 把搜索拆成独立模块（vector.ts / keyword.ts / rerank.ts / graph-signals.ts / dedup.ts / autocut.ts）。LLM Wiki 应该参考这种模块化设计，每个搜索环节可独立调参和测试。
建议 8：Graph Signals 影响搜索排序 不要把图谱和搜索完全分离。GBrain 的 graph-signals 模块让相邻页面获得搜索分数加成——如果用户在看"退款流程"，相关的"支付系统"页面应该在后续搜索中获得 boost。
建议 9：零 LLM 调用的图谱构建 GBrain 用启发式规则从 frontmatter 和正文中提取实体引用建边，不消耗 token。LLM Wiki 可以做类似实现：解析 wikilinks + 正则匹配 frontmatter relationships → 构建邻接表。LLM 只在需要推断隐式关系时才介入。
建议 10：评估框架从第一天就建 GBrain 有完整的评估命令（10+ eval 命令 + LongMemEval 基准）。你的 PLAN.md 已经规划了 eval_retrieval.py（P@k/MRR/nDCG），建议在 Phase 1 就实现——这会指导后续所有搜索和编译优化。
建议 11：查询缓存 GBrain 有语义查询缓存——相似的问题复用搜索结果。对于工作知识库场景（团队成员反复问类似问题），这能大幅节省重复搜索的成本。
建议 12：Dream Cycle 自动维护 GBrain 的 24/7 cron 自动做丰富/合并/去重/引用修复。LLM Wiki 可以做"每日健康检查"——检测断链/孤页/陈旧内容/重复概念，生成维护建议。

三、两者都没做好、LLM Wiki 有机会超越的地方

建议 13：用代码 BFS + LLM 语义过滤的组合 obsidian-wiki 用 LLM 做 BFS（不可靠），GBrain 用 SQL 递归查询（确定但缺少语义理解）。LLM Wiki 的最优方案：代码做 BFS 保证正确性 → LLM 对结果做语义过滤和自然语言解释。 各司其职。
建议 14：完整的用户界面是你的核心差异化 obsidian-wiki 无 UI，GBrain 的 Admin 只是运维面板。你已经设计了 4 页面 UI（对话/文档/图谱/搜索），这是面向终端用户的知识浏览器，两个竞品都没做到。保持并加强这个优势。
建议 15：Staging 审核模式 obsidian-wiki 有 _staging/ 目录让人类审核 AI 编译产出。LLM Wiki 应该做"编译预览"——编译完成后不直接写入正式 wiki，而是展示 diff 让用户确认。你的 PLAN.md 中"编辑-保存-提示编译-确认"的两步流程正是这个思路，很好。

推荐的借鉴优先级

根据你当前项目阶段（HTML 原型完成，即将进入 Next.js 开发），按实施优先级排序：

优先级建议来源原因
P0 评估框架（Phase 1 第一周实现） GBrain 没有评估就无法量化优化效果，一切后续工作都需要基准
P0 搜索模块化（vector + keyword + RRF + graph signals） GBrain 搜索是产品核心，模块化架构允许独立调参和迭代
P1 增加 skills/ 分类 obsidian-wiki 低成本改动，立即提升"怎么做"类查询的精准度
P1 Tier 机制 + 溯源标记 obsidian-wiki 控制规模扩展时的 token 成本，建立信任链
P1 SHA-256 增量追踪 obsidian-wiki 避免重复编译未变更的文档
P1 代码 BFS + LLM 语义过滤 两者结合 你已经计划用代码实现 BFS，再加语义过滤就是最优方案
P2 分层检索策略 obsidian-wiki 知识库规模大时节省 token，初期小规模影响不大

你的核心差异化在于：编译的知识质量（来自 obsidian-wiki 的理念）+ 成熟的搜索能力（借鉴 GBrain）+ 团队友好的 UI（两者都没有）。不用做到 GBrain 那么复杂（它有 100+ 命令），也不用像 obsidian-wiki 那么极简（它没有 UI），而是在两者之间找到"刚好够用、体验好"的甜点。

一句话总结 把 obsidian-wiki 的编译哲学（知识重组 + 分类 + Tier + 溯源）和 GBrain 的工程实践（模块化搜索 + 代码图遍历 + 评估框架 + 图信号），装进一个带精美 UI 的 Tauri 桌面应用里——这就是 LLM Wiki 3.0 的独特价值。
