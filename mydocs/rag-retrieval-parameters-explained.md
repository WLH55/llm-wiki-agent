## 各参数详解

### 1. RAG_TOP_K_EACH=20（每路融合候选数）

**概念**：每一路检索各自取多少条候选进入 RRF 融合。向量路取 20 条，BM25 路也取 20 条，然后交给 RRF 融合。

**为什么是 20**：最终用户看到的答案只需要 top 5（`limit` 默认 5），但每路不能只取 5 条——因为**融合前各路的排名会变化**。比如向量路排第 8 的 chunk 在 BM25 路可能排第 1，如果向量路只取 5 条就把它丢了。所以每路取宽一点（20 条），给 RRF 融合足够大的候选池。

> 注意：这个 20 实际上会被"过检索"机制放大（见参数 5），真正查数据库时取的不是 20 而是 `max(20×5, 50) = 100` 条，融合后再截断。

### 2. RAG_RRF_K=60（RRF 平滑常数）

**概念**：RRF 公式里的平滑常数 k：`score = weight / (k + rank)`，rank 从 1 开始。k 的作用是**压制排名靠前和靠后的分差差距**。

**为什么是 60**：RRF 原论文推荐值，也是 WeKnora 生产用的值。

| k 值 | 第 1 名 | 第 2 名 | 差距 |
|---|---|---|---|
| k=1 | 1.0/2=0.500 | 1.0/3=0.333 | 0.167 |
| k=60 | 1.0/61=0.0164 | 1.0/62=0.0161 | 0.0003 |

k=1 时第 1 名有绝对统治力（0.5 vs 0.33），k=60 时第 1 名和第 10 名的差距很小（0.0164 vs 0.0154）。**k 越大越"民主"**，排名靠后的 chunk 也有参与融合的机会；k 越小越"独裁"，排名靠前的绝对主导。60 是公认的平衡点，不是拍脑袋的。

### 3. RAG_VECTOR_THRESHOLD=0.15（向量相似度阈值）

**概念**：向量相似度分数 = `1 - cosine距离`，范围 0~1。低于 0.15 的结果不返回。

**为什么是 0.15**：
- 1.0 完全相同；0.8-1.0 高度相似；0.5-0.8 主题相关；0.15 几乎不相关但还有点沾边；0.0 完全正交

阈值 0.15 看起来很低，但这是**召回阶段的最低线**——宁可多召回一些让 RRF 融合来筛，也不在召回阶段就过滤太狠导致漏掉。如果设太高（比如 0.5），很多语义沾边但不够贴近的 chunk 会被丢掉，导致 RRF 融合池太小。WeKnora 生产也用 0.15/0.2，经验值。

### 4. RAG_KEYWORD_THRESHOLD=0.3（BM25 关键词阈值）

**概念**：BM25 分数低于 0.3 的结果不返回。

**为什么是 0.3 而不是 0.15**：
- 向量分数是相似度（0~1），0.15 = 几乎不相关但还有点沾边
- BM25 分数是相关性打分，0.3 = 查询词在文档中出现了但不是主要话题

BM25 阈值设得比向量高（0.3 > 0.15），是因为**关键词匹配天然更"硬"**——要么包含这个词要么不包含。低分 BM25 结果通常意味着只命中了一个无关词，价值很低。

### 5. RAG_OVER_RETRIEVE_FACTOR=5 / MIN=50 / CAP=500（过检索）

**概念**：过检索机制——数据库实际查的条数远大于最终需要的条数，融合后再截断。

```
实际查询数 = clamp(limit × 5, 50, 500)
```

| 用户要的 limit | 计算 | 实际查 |
|---|---|---|
| 5 | 5×5=25 | **50**（触底 clamp 到 50） |
| 10 | 10×5=50 | **50** |
| 50 | 50×5=250 | **250** |
| 200 | 200×5=1000 | **500**（触顶 clamp 到 500） |

**为什么要过检索**：让 RRF 融合有足够大的候选池。如果每路只取最终 limit 数量，很多在单路排名靠后但另一路排名靠前的 chunk 就被提前丢掉了，RRF 融合失去了意义。

- **MIN=50**：即使 limit=1 也保证候选池至少 50 条，否则过检索形同虚设
- **CAP=500**：防止 limit=1000 时数据库查 5000 条拖慢性能。500 是性能和召回率的平衡上限，WeKnora 用的也是 500

### 6. RAG_RRF_VECTOR_WEIGHT=0.7 / KEYWORD_WEIGHT=0.3（RRF 权重）

**概念**：`score = 0.7/(60+rank_v) + 0.3/(60+rank_k)`，向量路占 70%，BM25 路占 30%。

**为什么 7:3**：向量检索**语义理解强**（懂同义词、懂泛化），BM25 **精确匹配强**（锁死专有名词、代码、型号）。在日常 RAG 中，语义相似是主要判断标准，精确匹配是辅助。WeKnora 生产也用 0.7:0.3。如果知识库主要是技术文档/代码（精确匹配比语义更重要），可以改为 0.5:0.5。

## OVER_RETRIEVE vs TOP_K_EACH 的区别

容易混淆，关键在于**作用阶段不同**：

- `RAG_OVER_RETRIEVE_FACTOR=5`：控制**数据库实际查多少条**（粗筛池的大小）
- `RAG_TOP_K_EACH=20`：控制**粗筛池里取多少条进入 RRF 融合**（精筛池的大小）

### 用实际数字走一遍（limit=5）

```
数据库查询（第1层 - 过检索）
  │  实际查 = clamp(5 × 5, 50, 500) = 50 条
  ↓  返回 50 条粗筛结果

阈值过滤（第2层）
  │  向量路50条 → 过滤掉 <0.15的 → 剩 N 条
  │  BM25路50条 → 过滤掉 <0.3的 → 剩 M 条
  ↓  假设向量路剩15条，BM25路剩12条

RRF融合前截断（第3层 - TOP_K_EACH）
  │  向量路15条 → 取TOP_K_EACH=20 → 还是15条（没超20）
  │  BM25路12条 → 取TOP_K_EACH=20 → 还是12条
  │  （如果粗筛剩了35条 > 20，就只取前20条进融合）
  ↓  向量路15条 + BM25路12条 → RRF融合 → 27条

最终截断（第4层 - limit）
  │  27条 → 取limit=5条
  ↓  5条结果 + nearby增强
```

**50 是为了不漏，20 是为了不浪费，5 是给用户看的。**

很多时候阈值过滤后的结果不到 20 条，所以 TOP_K_EACH 其实很少真正截断——它更像一个**上限保护**，防止过检索在大 limit 时（比如 limit=100）融合池爆炸。

## nearby 上下文增强

### 解决什么问题

分块把文档切成小块，检索时命中的是一个**孤立的块**。但有些信息是跨块的——比如：

```
块 3: "该产品支持 5G 网络，最高带宽可达 10Gbps。"
块 4: "但需要注意的是，在极端高温环境下带宽会降低至 1Gbps。"
块 5: "建议在环境温度 0-40°C 范围内使用。"
```

用户问"产品在高温下的带宽是多少"——向量检索命中**块 4**（"极端高温环境"语义最匹配）。但只返回块 4 不够，因为没有块 3 的上下文，你不知道"降至 1Gbps"是相对于"10Gbps"的。

### 怎么做

对检索命中后的**top-N 条结果**，每条都去数据库查它的**前一个块和后一个块**（`chunk_index ± 1`，同一个文档同一版本），塞进结果的 `context` 字段：

```python
hit.chunk_index = 4
hit.text = "但需要注意的是，在极端高温环境下带宽会降低至 1Gbps。"
hit.context = [
    RetrievalResult(chunk_index=3, text="该产品支持5G...10Gbps", match_type="nearby"),
    RetrievalResult(chunk_index=5, text="建议在0-40°C...", match_type="nearby"),
]
```

这样 LLM 看到的就不只是一个孤立的块，而是"命中块 + 前后各一个块"的**3 块连读**，语义更完整。

### 为什么只对 top-N 做

每条都要多查 2 个块，全做成本太高。只对**最终截断后的 top-N**（默认 5 条）做增强，这 5 条才是真正送给 LLM 的。

### 为什么是 chunk_index ± 1 而不是父子分块

父子分块（parent-child）需要在分块阶段就建立父子关系（小块索引、大块生成），改动大。nearby 用现有的 `chunk_index` 字段就能做，**零表结构改动**，是轻量替代方案。未来做父子分块升级后，nearby 可以和父子分块共存或被替代。

## 全流程串起来看

```
用户问"产品高温带宽"
    │
    ↓  embedding（向量化查询）
    │
    ├──── 向量路: 过检索取50条 → 阈值≥0.15过滤 → 取top20
    │
    ├──── BM25路: 过检索取50条 → 阈值≥0.3过滤 → 取top20
    │
    ↓  RRF 加权融合（0.7:0.3, k=60）
    │
  融合结果 ~40条 → 截断到limit=5
    │
    ↓  nearby增强：每条取chunk_index±1
    │
  5条结果，每条带前后相邻块 context
    │
    ↓  送给 Chat Pipeline → LLM 生成答案 + 引用回链
```
