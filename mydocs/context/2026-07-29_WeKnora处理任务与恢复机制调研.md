# WeKnora 处理任务与恢复机制调研

> 调研日期：2026-07-29<br>
> 本项目基线：`cf0723501cbcabf352127156b38fed95fbe0f60a`<br>
> WeKnora 基线：`a24567a9516ccf800f0ba9199bc48a9baaba3494`<br>
> 状态：Research Active；字段删除、Redis、Run/Span 与两阶段激活修订已于 2026-07-29 批准；Worker 运行时与并发模型仍待审批

## 1. 结论摘要

1. `processing_runs` 与 `processing_spans` 足以保存任务的权威状态、心跳、错误、阶段进度和审计历史，不应再由 Redis 保存第二套任务进度。
2. `processing_runs` 是运行账本和控制面记录，不是队列或互斥锁本身。当前项目仍使用 Redis + RQ 投递任务，并已批准使用 Redis 短期租约锁和删除墓碑，因此“取消 Redis checkpoint”不等于“Redis 只能用于队列”。
3. MVP 已批准取消 Wiki Redis checkpoint。Map 中间结果只在单次 Worker 执行期间保存在内存；失败或进程退出后，从同一 Active Chunk Set 重新执行 Map。
4. 如果真实数据证明长文重算成本不可接受，应新增显式、可审计的持久化产物设计，例如 PostgreSQL 元数据 + MinIO 对象；不建议重新把跨运行恢复依赖放进带 TTL 的 Redis 缓存。
5. WeKnora 也没有持久化 Wiki Map 结果。它将待办操作迁移到 PostgreSQL，Redis 只承担 Asynq 队列、短期互斥锁和删除墓碑；Map/Reduce 结果保存在当前 Go 进程内存，失败后按 PostgreSQL 待办行重新执行。
6. 已批准继续删除 `document_revisions` 的 4 个运行摘要字段和 `processing_runs.model_key`。新共享 Chunk 架构没有产生恢复这些字段的理由。
7. 新架构原本存在一个比 Redis 更重要的可用性风险：若先切换 `active_revision_id`、再异步生成 embedding，向量检索会在 embedding 失败或未完成期间失去该文档的可用向量。现已批准“候选 Revision 两阶段激活”消除此窗口。

## 2. 四类状态的职责边界

| 状态/产物 | 权威位置 | 保存内容 | 不保存内容 |
|---|---|---|---|
| 文档内容是否可成为生效版本 | `document_revisions.status` | `pending` / `processing` / `ready` / `failed` | 某次尝试的错误、起止时间 |
| 一次可独立调度任务的状态 | `processing_runs` | 目标、配置快照、整体状态、心跳、错误、起止时间 | 阶段明细、完整模型输出 |
| Run 内阶段与展示进度 | `processing_spans` | 阶段状态、时间、模型、token、数值指标、简短错误 | Map 完整结果、正文、Prompt |
| 队列投递和自动重试 | Redis + RQ | 待执行 Job、延迟重试、Worker 消费 | 业务状态真相、长期审计历史 |

因此，用户看到的“处理中 12/20 批”可以由 `processing_spans.metrics` 的 `total_batches`、`completed_batches` 和 `retry_count` 表达；`processing_runs.heartbeat_at` 用于判断任务是否卡死。Redis 不需要再保存一份可查询进度。

## 3. Redis checkpoint 是否必要

### 3.1 当前方案实际解决的问题

当前 Spec 中的 Redis checkpoint 保存 manifest、批次完成标记和 Map 结果，唯一额外价值是：Worker 崩溃后可以跳过已经完成的昂贵 LLM Map 批次。

它不负责以下事项：

- Run 的 `pending/running/succeeded/failed/cancelled` 状态；
- Worker 心跳与卡死判断；
- 阶段错误和 token 指标；
- 最终 Wiki 页面、引用和证据；
- 原始 chunk 正文。

这些都已经由 PostgreSQL 或最终业务表负责。

### 3.2 保留 Redis checkpoint 的代价

- PostgreSQL 与 Redis 同时保存“进行到哪里”，需要定义双写顺序和冲突恢复规则。
- checkpoint 通过 TTL、驱逐或 Redis 故障丢失后仍必须支持全量重算，因此它不能简化正确性，只能优化成本。
- 新 Run 复用旧 Run checkpoint 时，必须严格核对 Revision、chunk 指纹、分块配置、Prompt、模型和运行选项；任一漏项都会复用错误结果。
- Map 结果可能较大，会让 Redis 从队列基础设施变成半持久化产物存储，并产生 AOF、容量隔离、清理和运维要求。
- MVP 尚无真实长文成本数据，无法证明这部分复杂性值得。

### 3.3 批准方案

MVP 采用“无跨运行 Map checkpoint”：

1. `wiki_generate` Run 创建后由 RQ 投递。
2. Worker 从 PostgreSQL 读取目标 Revision 的完整 Chunk Set，确定性生成批次 manifest，但不持久化 manifest。
3. 每个批次的 Map 结果保存在当前 Worker 内存；阶段进度写入 `processing_spans.metrics`。
4. 单个 LLM 请求的瞬态错误在当前 Worker 内有限重试。
5. Worker 退出或自动队列重试时，重新执行该 Run 的全部 Map；最终页面尚未提交，不会产生部分业务结果。
6. 全部 Reduce 成功后，在同一事务中提交页面、页面版本、文档引用和证据引用。
7. 真实监控证明重算成本不可接受后，再审批持久化中间产物；不提前为假设成本增加第 16 张表。

### 3.4 Redis 仍然保留的职责

Redis 仍作为 RQ 的队列后端，负责 Job 投递、延迟重试和 Worker 消费；同时保存可丢失的同 KB Wiki 租约锁和文档删除墓碑。若将来改为 PostgreSQL 队列或其他 Broker，才可以进一步讨论完全移除 Redis。

“取消 Redis checkpoint”只取消业务进度和 Map 结果缓存，不取消队列或短期协调。租约和墓碑不得成为唯一业务副本；最终 Wiki 提交仍以 PostgreSQL 中的删除状态、Active Revision、Run 状态和页面版本为准。

## 4. WeKnora 的实际设计

### 4.1 PostgreSQL 保存待办与失败事实

WeKnora 的 migration `000041_task_queue_and_wiki_indexes.up.sql` 明确将旧 `wiki:pending:<kbID>` Redis List 迁移为 PostgreSQL `task_pending_ops`，理由是 Redis TTL 在 4 万文档规模下会丢任务。

`task_pending_ops` 保存：

- `task_type + scope + scope_id`：任务类型与作用域；
- `op + dedup_key + payload`：待执行操作与去重标识；
- `fail_count`：批处理内失败次数；
- `enqueued_at + claimed_at`：入队与预留认领信息。

超过重试上限后，记录进入 `task_dead_letters`。这说明 WeKnora 将不可丢失的排队事实和失败事实放在 PostgreSQL，而不是 Redis。

### 4.2 Redis 只承担短时协调

WeKnora 的 Wiki 处理仍使用 Redis/Asynq，但 Wiki 业务层只额外使用：

- `wiki:active:<kbID>`：60 秒 TTL、20 秒续租的 KB 级互斥锁；
- `wiki:deleted:<kbID>:<knowledgeID>`：1 小时删除墓碑；
- Asynq 队列本身。

Lite 模式没有 Redis 时，互斥锁退化为进程内 `sync.Map`，任务可在 goroutine 中执行。这再次证明 Redis 不是 Wiki 结果的事实存储。

WeKnora 的租约值固定为 `"1"`，续租和释放没有校验持有者；旧 Worker 在租约过期后可能误续租或删除新 Worker 的锁。本项目只采纳短期协调边界，不复制该实现：锁值必须包含 Run 身份和随机 execution token，续租与释放使用 Lua 原子比较；失锁 Worker 必须丢弃结果。

### 4.3 Map/Reduce 不做跨运行 checkpoint

WeKnora 的 `ProcessWikiIngest`：

- 从 `task_pending_ops` Peek 一批文档操作；
- 使用 `errgroup.SetLimit` 并行执行文档级 Map；
- Map 结果保存在当前进程的 `docResults`、`slugUpdates` 和 `WikiBatchContext`；
- Reduce 后才删除成功消费的待办行；
- 失败操作递增 `fail_count`，保留待办行供下一批重做；
- 没有将完整 Map 输出写入 Redis 或 PostgreSQL checkpoint。

WeKnora 选择“允许重算，保证待办不丢”，而不是“保存每个中间结果”。本项目要求完整遍历长文、精确证据和事务提交，正确性要求更高，但这并不自动推出必须保存 Redis checkpoint。

### 4.4 Run/Span 与自动重试

WeKnora 没有独立的通用 `processing_runs` 表；`knowledge_processing_spans` 的 `(knowledge_id, attempt)` 同时承担一次业务处理尝试和 Span 树。

- 用户主动 reparse 创建新的 `attempt`；
- Asynq 自动重试沿用 payload 中的同一 `attempt`；
- 相同阶段重入时复用阶段 Span，而不是创建新的业务 attempt；
- 依赖关系由代码中的 `StageDependencies` DAG 定义，不由数据库顺序字段表达；
- Span 支持 `pending/running/done/failed/skipped/cancelled`；
- 并行能力来自 Worker 池和 `errgroup`，与 Run/Span 层级无关。

这个边界适合迁移到本项目：自动队列重试仍属于同一个 Run；只有一个终态 Run 之后的人工或系统业务重跑才创建新 Run。

## 5. 已批准字段删除复核

### 5.1 `document_revisions` 删除 4 个字段

删除：

- `error_code`
- `error_message`
- `processing_started_at`
- `processed_at`

理由：Revision 是内容快照和可生效状态，不是某次处理尝试。一次 Revision 可以经历多次处理 Run；如果在 Revision 上保存错误和时间，只能保存“最近一次”，既覆盖历史，又与 `processing_runs` 重复。

保留 `document_revisions.status` 不冲突。它回答“这份内容快照能否成为 Active Revision”，而 `processing_runs.status` 回答“某一次处理尝试是否成功”。

### 5.2 `processing_runs` 删除 `model_key`

一个 `wiki_generate` Run 可能在 Map、Reduce、摘要、实体消歧阶段使用不同模型，甚至回退模型。“主要模型”没有稳定定义。

具体调用模型保存在 `processing_spans.model_key`；Run 的复现配置由 `options_snapshot` 和配置版本表达。因此继续删除 `processing_runs.model_key`。

## 6. Run/Span 进一步评估

### 6.1 自动重试与业务重跑（已批准）

批准语义：

- RQ 自动重试：同一个 `processing_run` 在 `running` 与 `pending` 间切换，并为再次执行新增 Span；不递增 `attempt_no`。
- 自动重试耗尽：该 Run 进入 `failed`。
- 用户点击“重试”或系统在终态后发起重跑：创建新 Run，填写 `retry_of_run_id`，`attempt_no + 1`。

当前执行失败但仍将由 RQ 自动重试时，Run 从 `running` 回到 `pending` 并清空 `heartbeat_at`；下一次 Worker 取得任务后再次进入 `running`。`started_at` 始终保留该 Run 第一次实际执行时间，Run 级错误字段只记录最终失败摘要。

这样 Run 表示一次用户可识别、可取消、可审计的处理尝试，队列的网络抖动重投不会制造多条业务运行记录。

### 6.2 `processing_spans.status`（已批准）

状态采用 `pending/running/succeeded/failed/skipped/cancelled`，`started_at` 改为可空。`cancelled` 表示阶段本身没有失败，而是由于用户取消、Run 取消或上游失败而停止；`skipped` 只表示配置或输入决定的主动跳过。这样 UI 和排障可以区分“本阶段出错”“主动不执行”和“本阶段未获执行机会”。

### 6.3 `processing_spans.sequence_no`（已批准删除）

删除全局 `sequence_no` 及 `UNIQUE(run_id, sequence_no)`：

- Run 内允许并行创建 Span，全局序号会引入分配竞争；
- 序号不能表达依赖，容易被误用成串行顺序；
- 固定阶段展示顺序应来自应用阶段注册表；
- 动态同级 Span 可用 `created_at, id` 稳定排序；嵌套关系由 `parent_span_id` 表达。

WeKnora 也把阶段顺序放在代码 `AllStages`，把依赖放在 `StageDependencies`，数据库 Span 表不保存全局顺序号。

## 7. Active Revision 两阶段激活（已批准）

原提交定义为：`document_process` 完成共享 chunks 后立即切换 `documents.active_revision_id`，随后独立运行 `rag_index` 和 `wiki_generate`。

当 KB 启用向量检索时会出现以下窗口：

1. 新 Revision chunks 已成为 Active；
2. 旧 Active chunks 被删除；
3. 新 chunks 的 embedding 尚未生成或生成失败；
4. 向量检索只能过滤到 Active Revision，却找不到该文档的有效向量。

这不会破坏 BM25，但会造成该文档的向量召回暂时或持续不可用。它与“新版本失败时继续使用旧成功版本”的产品预期不一致。

已批准改为“两阶段激活”：

- `document_process` 先生成候选 Revision chunks，Revision 可进入 `ready`，但暂不切换 Active；
- 若 RAG 未启用向量，立即切换；
- 若启用向量，先对候选 chunks 完成 `rag_index`，成功后再原子切换 Active 并删除旧 chunks；
- `wiki_generate` 不作为切换门槛，仍在激活后独立运行；
- embedding 失败时旧 Active Revision 和旧向量继续服务。

因此，`document_process` 负责产生 `ready` 候选版本；未启用向量检索时直接激活，启用时由候选版本的 `rag_index` 成功触发激活。候选 embedding 失败不影响旧 Active Revision；Wiki 在激活后独立生成且不是激活门槛。

## 8. Worker 运行边界与并发模型（2026-07-30 补充调研）

### 8.1 当前项目的真实执行边界

当前 `backend` 与 `worker` 容器复用同一个 backend 镜像和同一份 `app` Python 包，但入口不同：

- API 容器运行 `uvicorn app.main:app`；
- Worker 容器运行 `python -m app.workers.worker`。

因此，代码位于 `backend/app/parsers` 不代表它由 API 进程执行。正式上传链路是：

1. API 的 `parsers/api/routes.py` 读取上传文件并调用 `parsers/service/document.py`；
2. API 校验请求、上传 MinIO、创建 `documents.status=pending` 记录并提交 RQ Job；
3. 独立 Worker 从 Redis 的 `parse` 队列消费 Job；
4. Worker 的 `workers/parse_document.py` 从 MinIO 读取原文件，并通过 `asyncio.to_thread` 调用 `parsers/service/dispatch.py`；
5. dispatch 在 Worker 进程的线程中调用 `parsers/implementations/*` 的具体 Parser；
6. Worker 继续分块、调用 embedding、写 chunks 并更新状态。

API 会导入 parser 注册表用于格式、引擎和上传参数校验，但不会在正式上传请求内逐页解析 PDF。当前 API 仍会把上传文件完整读入内存，并同步调用 `upload_bytes` 写 MinIO；这部分尚未做到流式、非阻塞上传，不能表述为“上传 API 完全不会阻塞”。

### 8.2 消息异步与协程异步不是同一概念

当前 RQ 实现满足的是业务架构异步：API 将 Job 写入 Redis 后即可返回，任务由 Worker 稍后执行。标准 RQ Worker 的 Job 执行模型仍是串行的：一次领取一个 Job，等待其函数结束后再领取下一个。

`workers/queue.py` 使用 `asyncio.run(parse_document_task(doc_id))`，只是在当前 Job 内创建 event loop 以运行协程；RQ 不会把第二个 Job 放进同一 event loop。因此：

- 当前可以在一个 Job 内使用 `await`、`asyncio.gather` 或 `asyncio.to_thread`；
- 当前不能靠 `asyncio.run` 让一个 RQ Worker 同时消费多个 Job；
- 增加标准 RQ 的任务级并发主要依靠增加 Worker 进程或实例。

消息队列的“异步”表示生产者与消费者在时间上解耦，不等于消费者必须使用 Python `async/await`，也不等于所有排队任务同时执行。

### 8.3 WeKnora 如何消费 100 个并发任务

WeKnora 使用 Go + `hibiken/asynq`。它在同一个应用进程中启动 Asynq Server，默认配置 `Concurrency=32`，并允许通过 `WEKNORA_ASYNQ_CONCURRENCY` 修改。100 个任务同时入队时，单实例最多运行 32 个任务处理 goroutine，其余 68 个继续留在 Redis 排队；槽位释放后再取下一个任务。

WeKnora 配置六个加权队列：

| 队列 | 权重 | 用途 |
|---|---:|---|
| `critical` | 6 | 高优先级任务 |
| `default` | 3 | 文档处理等默认任务 |
| `low` | 1 | Wiki、摘要、删除等低优先级任务 |
| `multimodal` | 1 | OCR 与图片理解 |
| `graph` | 1 | 图谱抽取 |
| `question` | 1 | 问题生成 |

这些队列共享同一个 32 槽位 Worker 池。权重只影响下一个任务的选择，不能抢占已经运行的长任务，也没有为某个队列预留独占容量，所以它是调度隔离而不是真正的资源隔离。

WeKnora 还有第二层 Job 内并发：Wiki Map 和 Reduce 阶段分别使用 `errgroup.SetLimit`，默认各限制为 10。这个设计提高 I/O 吞吐，但也意味着全局 Job 并发与单 Job 内部并发会叠加，必须同时受 LLM 限流、HTTP 连接池和数据库连接池约束。

### 8.4 对本项目的含义

本项目的文档流水线同时包含两类工作：

- I/O 等待型：MinIO、Embedding/LLM HTTP、异步 PostgreSQL、远程解析服务；适合协程并发；
- 阻塞或 CPU/内存密集型：本地 PDF/DOCX/OCR、部分分块与格式转换；需要受限线程池、进程池或独立资源队列，不能直接阻塞 event loop。

如果目标是让一个 Python Worker 进程同时运行多个独立 Job 协程，标准 RQ 不是原生匹配的运行时。`arq` 是一个基于 Redis、原生执行 `async def` Job 的候选框架，可以在单进程内配置多个并发协程 Job；它目前只是候选，不是已批准方案。不得通过自行改造 RQ 的取队列循环来重新实现超时、重试、取消、崩溃恢复和优雅停机。

无论最终选择 RQ 还是 async-native 队列，都继续遵守已批准的数据边界：`processing_runs` 是权威任务事实，Redis Job 可以重建；自动队列重试沿用同一个 Run；任务 payload 只传 Run 身份，Worker 运行时从 PostgreSQL 读取配置与目标。

### 8.5 尚未批准的 Worker 决策

以下内容仍处于 Research，不得进入实现：

1. 保留 RQ 并通过多个进程扩容，还是切换到 async-native Python 队列；
2. 若切换，选择 `arq`、Taskiq 或其他运行时；
3. 单 Worker 的 Job 并发上限，以及 Parser、Embedding/LLM、数据库写入各自的资源并发上限；
4. 队列只做优先级调度，还是为文档、Wiki、同步等任务建立独立容量池；
5. Worker 容器数量、每容器进程数、故障影响范围与横向扩容方式。
