## 1. 三表协作的整体流程

这套设计本质是 **Transaction Outbox + Lease-based 执行（ADR-0018 fencing）** 模式。

### 三张表的职责分工

| 表 | 角色 | 一行代表什么 | 数据量级 |
|---|---|---|---|
| `processing_runs` | 任务运行账本（终态真相源） | 一次可独立调度、可审计的业务处理 | 每个业务操作 1 行 |
| `processing_spans` | 阶段观测层（诊断流水） | Run 内一个可观测阶段或单次 Worker 执行尝试 | 每个 Run N 行 |
| `task_outbox` | 可靠投递层（消息意图） | 一条待发布到 Redis Stream 的消息意图 | 每个 Run 1~N 行 |

### 完整生命周期

```
用户/API 请求
    │
    ▼
┌─────────────────────────────────────────────────┐
│  DB 事务（原子写入）                              │
│  1. INSERT processing_runs（Run 行）              │
│  2. INSERT task_outbox（Outbox 行，存 run_id）     │
└──────────────────────┬──────────────────────────┘
                       │ 事务提交
                       ▼
┌─────────────────────────────────────────────────┐
│  Outbox Publisher（独立进程，轮询 DB）             │
│  每 0.5s 扫 task_outbox 表                        │
│  SKIP LOCKED 批量领取 → 发消息到 Redis Stream      │
│  成功 → mark_outbox_published                     │
│  失败 → release_outbox_claim（延后重试）           │
└──────────────────────┬──────────────────────────┘
                       │ Redis Stream
                       ▼
┌─────────────────────────────────────────────────┐
│  Task Worker（独立进程，消费 Stream）              │
│  收到消息 → claim_run（原子 CAS 去重）              │
│  领取成功 → start_worker_attempt（新建 Span）       │
│  执行 Handler → 心跳续租（每 15s）                  │
│  成功 → complete_run     │  失败 → retry_run/fail_run │
└──────────────────────┬──────────────────────────┘
                       │
                       ▼
              Reaper（兜底，每 30s）
              找"卡住的 Run 且没有未发布 Outbox"
              → 补一条 Outbox
```

## 2. processing_runs —— 任务运行账本

这是核心表，一行 = 一次可独立调度、可审计的业务处理。字段按职责分六组。

### 2.1 身份与隔离

| 字段 | 类型 | 作用 | 代码出处 |
|---|---|---|---|
| `id` | Integer PK | 内部自增主键，用于表间外键关联 | `runtime.py` `create_run_with_outbox` 先 `db.add(run)` 再 `flush()` 拿到 `run.id` |
| `public_id` | UUID | 对外稳定 ID，给 API、日志、排障用 | 避免暴露内部自增 ID |
| `tenant_id` | FK | 多租户隔离 | `rag_ingestion.py` handler 里用它做租户校验 |
| `kb_id` | FK | 知识库归属 | 标识这个 Run 属于哪个知识库 |

**租户校验示例**（`rag_ingestion.py`）：
```python
if document.tenant_id != context.identity.tenant_id:
    # 拒绝跨租户访问
```

### 2.2 流程语义

| 字段 | 作用 | 说明 |
|---|---|---|
| `run_type` | 流程类型 | 目前 `document_process` / `rag_index`。`tasks.py` 的 `RUN_HANDLERS` 注册表按它路由到 handler。`executor.py` 的 `queue_name_for_run` 还按它决定投到哪条 Redis Stream |
| `scope_type` | 处理目标类型 | 如 `revision`，配合 `scope_id` 使用 |
| `scope_id` | 处理目标 ID | `scope_type="revision"` 时就是 `DocumentRevision.id`。让一张账本表能承载多种业务对象 |
| `parent_run_id` | 编排链 | `rag_ingestion.py` 里 `document_process` 成功提交时派生出 `rag_index` Run，`parent_run_id = context.run_id`，形成编排树 |
| `retry_of_run_id` | 业务重跑链 | 指向被重跑的旧 Run（详见第 9 节） |
| `attempt_no` | 业务重跑序号 | 同一业务重跑链里的序号（详见第 9 节） |

### 2.3 触发与幂等

| 字段 | 作用 | 说明 |
|---|---|---|
| `trigger_type` | 触发来源 | `manual` / `on_ingest` / `schedule` / `retry`，纯审计用 |
| `status` | 状态机 | `pending / running / succeeded / failed / cancelled`，Worker 协调的核心 |
| `idempotency_key` | 幂等去重键 | 防止 API 重试或重复消息为同一请求重复创建 Run（详见第 10.1 节） |
| `effective_config_version` | 配置版本号 | 标识这条 Run 基于第几版配置跑的（预留，当前未传值） |
| `options_snapshot` | JSONB 配置快照 | 存分块策略、批次预算、输出语言等非敏感运行选项（详见第 10.2 节） |
| `requested_by_user_id` | 手动触发者 | 系统任务为空 |

### 2.4 错误摘要

| 字段 | 作用 | 说明 |
|---|---|---|
| `error_code` | 机器错误码 | 只在进入失败终态时写，`fail_run` 做了 `error_code[:50]` 截断 |
| `error_message` | 错误摘要 | `fail_run` 做了 `error_message[:1000]` 截断 |

> **注意**：自动重试途中的错误不写这里，而是写到 `processing_spans`；只有 `fail_run` 把 Run 打成终态 failed 时才落到 Run 上。

### 2.5 执行租约（fencing，ADR-0018，最关键的一组）

| 字段 | 类型 | 作用 | 代码出处 |
|---|---|---|---|
| `execution_token` | UUID | 当前执行权的凭证。`claim_run` 时生成新 token 写入 | `runtime.py` 第 86 行 `token = uuid4()` |
| `execution_epoch` | Integer | 单调递增的执行代号，每次原子领取 `+1`。fencing token 的核心 | `runtime.py` 第 103 行 `execution_epoch + 1` |
| `lease_expires_at` | DateTime | 租约到期时间 = 领取时间 + lease_seconds(900s) | `runtime.py` `claim_run` |
| `worker_id` | String | 持有租约的 Worker 标识 `host:pid:lane` | `tasks.py` 第 77-80 行 `worker_identity()` |

**提交时五条件全匹配**（`runtime.py` `_current_lease_predicate`，第 126-136 行）：

```python
ProcessingRun.id == lease.run_id                    # 1. 是这个 Run
AND ProcessingRun.status == "running"               # 2. 还在运行态
AND ProcessingRun.execution_token == lease.token   # 3. token 匹配
AND ProcessingRun.execution_epoch == lease.epoch   # 4. epoch 匹配
AND ProcessingRun.lease_expires_at > now            # 5. 租约未过期
```

任意一条不满足，UPDATE 命中 0 行，提交失败，`executor.py` 抛 `LeaseLostError`。

### 2.6 时间线

| 字段 | 作用 | 代码出处 |
|---|---|---|
| `started_at` | 第一次被 Worker 实际执行的时间 | `func.coalesce(started_at, claim_time)` 保证自动重试不覆盖 |
| `heartbeat_at` | 运行中最近心跳 | `executor.py` `_heartbeat_loop` 每 15s 调 `renew_lease` 更新它 |
| `finished_at` | 成功/失败/取消的结束时间 | `complete_run`/`fail_run` 写入 |
| `created_at` | 标准审计时间戳 | `reaper.py` 用它找"pending 太久"的 Run |
| `updated_at` | 标准审计时间戳 | 每次 UPDATE 自动更新 |

## 3. processing_spans —— 阶段观测层

一行 = Run 内一个可观测阶段或单次 Worker 执行尝试。Run 是"账本"，Span 是"诊断"。关系是 1 Run : N Spans。

| 字段 | 类型 | 作用 | 说明 |
|---|---|---|---|
| `run_id` | FK | 指向所属 `processing_runs.id` | 如 Span #1 的 `run_id = 100` 说明属于 Run #100 |
| `parent_span_id` | FK | 支持嵌套阶段树 | **当前代码未使用**，预留用于未来 `parse → segment → embed` 嵌套 |
| `span_name` | String | 阶段名 | 当前实际只用了 `worker_attempt`（见 `runtime.py` `start_worker_attempt`） |
| `status` | String | 阶段状态 | 比 Run 多一个 `skipped` 态 |
| `model_key` | String | 模型标识 | 非模型阶段为空，用于 token 用量核算 |
| `input_tokens` | Integer | 输入 token 数 | 非模型阶段为空 |
| `output_tokens` | Integer | 输出 token 数 | 非模型阶段为空 |
| `metrics` | JSONB | 阶段专属数值指标 | 存 `{"attempt": N, "execution_epoch": M}` |
| `error_code` | String | 阶段错误码 | **重试途中的错误写这里**，不是写 Run |
| `error_message` | Text | 阶段错误信息 | 同上 |
| `started_at` | DateTime | 阶段开始时间 | `start_worker_attempt` 写入 |
| `finished_at` | DateTime | 阶段结束时间 | `finish_worker_attempt` 用 `status=="running"` 做谓词，保证不重复关闭 |

### 核心理念

**Run 存终态，Span 存过程。** 自动重试每一轮的诊断都独立保留，排障时能看清"第 2 次尝试在 embed 阶段花了多少 token、报了什么错"。

### worker_attempt 是什么

`start_worker_attempt`（`runtime.py` 第 227-255 行）的逻辑：

```python
async def start_worker_attempt(db, run, lease):
    attempt = (
        await db.execute(
            select(func.count(ProcessingSpan.id)).where(
                ProcessingSpan.run_id == run.id,
                ProcessingSpan.span_name == "worker_attempt",
            )
        )
    ).scalar_one() + 1
    span = ProcessingSpan(
        ...
        span_name="worker_attempt",
        status="running",
        metrics={"attempt": attempt, "execution_epoch": lease.epoch},
    )
```

**每次 Worker 消费一条消息执行一轮，就新增一条 `worker_attempt` Span。** `attempt` 次数是 COUNT 出来的，不是专门字段。

## 4. task_outbox —— 可靠投递层

这是 Transaction Outbox 模式的载体。解决的问题：DB 事务提交和 Redis 投递无法原子化，直接在事务里发消息会丢消息。

| 字段 | 类型 | 作用 | 说明 |
|---|---|---|---|
| `run_id` | FK | 关联的 Run | **只存 run_id 这一个业务字段**，不存业务结果 |
| `task_name` | String | Handler 路由名 | 目前固定 `process_run` |
| `queue_name` | String | 目标队列 | `critical / default / multimodal / low`，对应 `broker.py` 的四条 Redis Stream |
| `available_at` | DateTime | 最早可投递时间 | 正常创建时 = now；`retry_run` 和 `release_outbox_claim` 设成 `now + delay`，实现延迟重投 |
| `publish_attempts` | Integer | 已尝试发布次数 | 退避延迟按 `2**publish_attempts` 算 |
| `lock_token` | UUID | Publisher 的领取锁 | `claim_outbox_batch` 用 `SKIP LOCKED` 领一批，给每条写新 token |
| `locked_until` | DateTime | 领取锁到期时间 | `mark_outbox_published` / `release_outbox_claim` 要求 `lock_token == claim.lock_token` 才能确认 |
| `published_at` | DateTime | 发布成功时间 | NULL = 尚未发布，是 Publisher 判断"可领取"的核心条件 |
| `last_error` | Text | 最近一次发布失败原因 | Text 类型放得下完整错误 |

> **关键设计**：Outbox 只存 `run_id`，不存业务结果。消息只传 Run 身份，Worker 领取后自己去 DB 读 Run 状态。投递成功和业务成功是两回事。

## 5. 这套设计解决了 MQ 的哪些经典问题

### ① 双写原子性问题（dual-write）

这是整套 Outbox 存在的根本理由。数据库 commit 和发消息是两个独立系统，无法原子化：
- 先发后提交 → 事务回滚但消息已发
- 先提交后发 → 消息丢失

`create_run_with_outbox` 把 Run 行和 Outbox 行写进**同一个 DB 事务**，把"发消息意图"也变成可事务化的数据。跟 MQ 选型无关。

### ② 消息丢失（message loss）

- **生产者→broker 丢失**：`publish_outbox_claim` 发送失败就 `release_outbox_claim`，不删行只延后 + 退避
- **broker 自身丢失**：Redis Stream 持久化但不如专业 MQ 可靠，有 `reaper.py` 兜底
- **消费者拿到但崩溃**：`claim_run` 是先领后执行，领取是原子 UPDATE

### ③ 重复投递（duplicate delivery / at-least-once）

Redis Stream 是 at-least-once 语义，重复投递不可避免。`claim_run` 的 WHERE 用 `status in (pending, running+租约过期)` 做 CAS，第二个 Worker 命中 0 行 → `ExecutionOutcome.IGNORED`。这是**消费者侧的幂等去重**。

### ④ 僵尸/慢消费者并发（zombie consumer）—— fencing

`execution_token + execution_epoch + lease_expires_at` 三件套解决。场景：Worker A 领了 Run，GC 停顿导致租约过期，Worker B 接管并已提交。A 醒来想提交 → epoch 不匹配，直接被拒。

### ⑤ 消费者卡死（hang/stuck）

`heartbeat_at` + `_heartbeat_loop`（15s 续租）+ `lease_expires_at`（900s）。租约过期后别的 Worker 能接管。reaper 再兜一层。

### ⑥ 失败处理与毒消息（poison message）

两级重试分类：
- `TransientTaskError`（瞬时，退避重投，`retry_run`）
- `TerminalTaskError`（终态，`fail_run` 不再重试）

`max_auto_retries=3` 封顶，避免毒消息无限重投。每次重试诊断写 `processing_spans`，最终终态错误写 `processing_runs`。

### ⑦ 背压与优先级（backpressure / priority）

四条 Stream（`critical/default/multimodal/low`）+ `queue_name_for_run` 按 `run_type` 路由。

### ⑧ 延迟投递（delayed delivery）

`available_at` 字段。正常 = now；重试时 = `now + delay`。退避用 `2**publish_attempts` + jitter，封顶 300s。

### ⑨ 投递确认（delivery acknowledgment）

`mark_outbox_published` 的 WHERE 要求 `lock_token == claim.lock_token AND locked_until > now`。这是**生产者侧的 fencing**。

### ⑩ 可观测性与审计（observability）

`processing_runs` 是账本（终态），`processing_spans` 是流水（每次尝试的 token 消耗、错误、attempt 编号）。

## 6. 换成 RabbitMQ / Kafka 后：哪些能省，哪些省不掉

### 可以省略 / 大幅简化

| 模块 | 用 RabbitMQ/Kafka 后 | 原因 |
|---|---|---|
| Publisher 轮询循环 + SKIP LOCKED + lock_token 投递级 fencing | 可删大半 | RabbitMQ publisher confirms 同步 ack；Kafka 幂等生产者 + acks=all |
| 多 Stream 手动路由 | 声明式路由 | RabbitMQ exchange + routing key；Kafka topic/partition |

### 职责仍在但可简化

| 模块 | 简化方式 |
|---|---|
| 投递重试 + 指数退避 | 交给 broker 侧或内存重试，`publish_attempts` 字段可省 |
| 消息持久化兜底 | RabbitMQ `durable=true`；Kafka 复制日志 `min.insync.replicas` |
| Reaper 失联补投 | 从"主防线"降级为"保险绳"，但保留更稳 |
| 消费者宕机重投 | RabbitMQ unacked 自动 requeue；Kafka 不 commit offset 重读 |

### 无论用哪种 MQ 都必须自己实现（省不掉）

| 模块 | 为什么省不掉 |
|---|---|
| **Outbox 同事务写入本身** | DB 提交和 publish 永远是两个系统。应用在 commit 后、publish 前崩溃的窗口永远存在，必须有恢复扫描兜底。Outbox 是模式，不是某张表 |
| **claim_run 原子 CAS 去重** | RabbitMQ 和 Kafka 默认都是 at-least-once。重复投递是分布式 MQ 的物理事实。消费者侧业务幂等几乎一定得自己做 |
| **fencing: token + epoch + lease** | RabbitMQ consumer timeout 会 redeliver，制造"两个 consumer 同时处理同一逻辑任务"的窗口。长任务场景下 fencing 是必需补丁 |
| **processing_runs 账本 + processing_spans 流水** | 这是业务状态机和审计，跟 MQ 完全无关。"这个文档解析任务现在到哪了、第几次尝试、花了多少 token"是业务必须知道的 |
| **两级重试 + 错误分类** | 哪些错误该重试、哪些是业务终态是业务语义，MQ 的重试策略是机械的、按次数的 |

### 一句话定性

真正在"重新发明 MQ"的只有 Publisher 轮询、SKIP LOCKED、投递级 lock_token fencing、多 Stream 手动路由——换 RabbitMQ/Kafka 可删大半。但 Outbox 同事务写入、claim_run 去重、fencing、业务账本/流水、错误分类**不是在造 MQ，而是在造可靠的业务处理运行时**——这部分跟"用不用专业 MQ"正交，是 at-least-once 语义 + 业务可审计性的必然要求。

## 7. 核心概念：至少一次投递

### 三种投递语义

| 语义 | 会丢消息吗 | 会重复吗 | 怎么做到的 |
|---|---|---|---|
| 最多一次 (at-most-once) | 会 | 不会 | 发出去就不管了（fire-and-forget） |
| **至少一次 (at-least-once)** | **不会** | **会** | 消费者处理完要回 ack，ack 没到就重投 |
| 恰好一次 (exactly-once) | 不会 | 不会 | 极难，要生产者+消费者+broker 三方事务配合 |

### ack 循环机制

```
Broker                    Consumer
  │                          │
  │──── 投递消息 ────────────▶│
  │                          │
  │                     处理消息
  │                          │
  │◀──── ack（确认）─────────│  ← 处理完了，告诉 broker "收到了"
  │                          │
  │  收到 ack → 删除消息       │
```

问题出在 ack 本身也可能丢——消费者处理完了，但回 ack 之前宕机了、或网络断了。这时 broker 等不到 ack，会判定"投递未完成"，于是**把同一条消息再投一次**。结果：同一条消息被处理了两次。

### 为什么这是工程默认选择

- "最多一次"会丢消息（不可靠）
- "恰好一次"代价极高（Kafka 要配齐幂等生产者+事务消费者+事务隔离级别）
- "至少一次"只要消费者自己做到**幂等**（同一条消息处理多次结果一致），重复就无害了

Redis Stream、RabbitMQ（手动 ack）、Kafka（不 commit offset）默认都是这个语义。

### 回到代码

正因为投递是 at-least-once，Worker 可能收到同一条 `run_id` 消息两次。所以才有 `claim_run` 那个原子 CAS——第一个 Worker 把 `status` 从 pending 改成 running 并写新 token/epoch，第二个 Worker 来的时候 WHERE 条件不匹配，命中 0 行，直接 `IGNORED`。

## 8. 核心概念：Fencing (token + epoch + lease)

### 僵尸 Worker 场景

```
时间轴 →

Worker A:  ├─ 领取 Run #100 (epoch=1, token=xxx, lease=900s) ─┤──── GC 停顿 28 分钟 ────┤─ 醒来，尝试提交 ─→ 被拒！
                                                                          │
Worker B:                                                           ├─ 领取 Run #100 (epoch=2, token=yyy) ─┤─ 执行 ─┤─ 提交成功 ─→
                                                                         ↑ claim_run 发现 lease 过期，接管
```

### 什么是 Fencing

Fencing 是分布式系统里防止 **split-brain**（脑裂）的经典模式。核心思想：**每次令牌转手，都换一把新锁，旧钥匙自动作废。**

打个比方：你给快递员 A 一把钥匙进你家放包裹。A 半路失踪了，你换了一把锁，给快递员 B 新钥匙。A 突然回来拿旧钥匙开门——打不开。这把换掉的锁，就是 fencing。

在代码层面，它体现为每次 `claim_run` 成功后，后续所有操作（complete / fail / renew）都必须通过同一个门禁验证。这个门禁就是 `_current_lease_predicate`（`runtime.py`），所有写操作共用：

```python
def _current_lease_predicate(lease, now):
    return (
        ProcessingRun.id == lease.run_id,
        ProcessingRun.status == "running",
        ProcessingRun.execution_token == lease.token,    # ① 凭证匹配
        ProcessingRun.execution_epoch == lease.epoch,    # ② 代际匹配
        ProcessingRun.lease_expires_at > now,            # ③ 未过期
    )
```

三个条件缺一不可——只要 Worker B 接管后替换了 token 和 epoch，Worker A 手里的旧凭证对不上任何一个条件，UPDATE 返回 0 行，直接抛 `LeaseLostError`。

### 三个字段各自的作用

#### token —— "这一轮执行权的凭证"

`execution_token` 是 `claim_run` 领取时生成的随机 UUID。提交终态时必须带上，WHERE 里写 `execution_token == lease.token`。解决"我是不是当前合法持有者"。

#### epoch —— "第几代执行权"（fencing token 的核心）

`execution_epoch` 是单调递增的整数，每次 `claim_run` 原子领取时 `+1`。它是 token 的"版本号"。A 在 epoch=1 时领的，卡住期间 B 领取把 epoch 推到 2。A 醒来时手里还揣着 epoch=1 的旧凭证，`1 ≠ 2`，提交被拒。

> **为什么 epoch 比 token 更关键？** token 是随机的，理论上存在"旧 token 被新领取复用"的极端概率。epoch 是单调递增的序号，语义是"我是第 N 代执行权，任何比我小的代号都是过期的"。

#### lease —— "执行权的有效期"

`lease_expires_at` = 领取时间 + `lease_seconds`（900 秒）。两个作用：
1. **接管判定**：`claim_run` 的 WHERE 里有 `lease_expires_at < claim_time` 分支
2. **提交校验**：`_current_lease_predicate` 要求 `lease_expires_at > now`

### 为什么三个都需要（互补，不是冗余）

去掉任何一个都有漏洞：
- 去掉 token：无法区分"是不是我领的"
- 去掉 epoch：A 的旧 token 如果碰巧匹配（或逻辑 bug 复用了 token），旧结果能覆盖新结果
- 去掉 lease：卡死的 Worker 永远持有执行权，任务永远卡住

### 三个字段拦截职责速查

| 字段 | 拦截什么 |
|------|---------|
| `execution_token` | 防止"别的 Worker 冒名顶替"。只有当初 claim 成功的那个 Worker 知道这个 UUID |
| `execution_epoch` | 防止"同一 Worker 用旧 token 重放"。即使旧 token 被缓存，epoch 也对不上 |
| `lease_expires_at` | 防止"租约超时后还硬写"。即使 token 和 epoch 都碰巧对上了，过期了也不行 |

### 一句话

**Fencing 就是"每次执行权转手都换锁换钥匙，旧钥匙自动作废"**——它不依赖消息确认、不靠超时回滚、不信任任何 Worker 的自觉，而是用数据库行本身的当前状态作为唯一的真相来源。

## 9. Claim 与原子 CAS 去重详解

### 9.1 什么是 Claim

Claim 是一种**带租约的原子领取协议**。它用一条数据库 UPDATE 同时完成三件事：

1. **检查状态能否接**（前置条件）
2. **标记已被我接**（独占凭证）
3. **给我一个唯一凭证**（fencing token）

在这个项目里，claim 出现了两处，模式完全一致：

| 操作 | 谁 claim 谁 | 凭证 | 过期时间 |
|------|------------|------|---------|
| `claim_run` | Worker 认领一个待执行的 Run | `execution_token` + `execution_epoch` | `lease_expires_at`（默认 900s） |
| `claim_outbox_batch` | Publisher 认领一批待投递的消息 | `lock_token` | `locked_until`（默认 30s） |

本质就是一句话：**"这条活我接了，这是我的工牌（token），我保证在 N 秒内干完。如果我超时没动静，别人可以接管。"**

### 9.2 为什么需要 Claim：read-then-write 竞态

如果没有 claim，直接让 Worker 读取 pending Run 然后改状态为 running：

```
Worker A: 读到 Run#3 status=pending  → 想执行它
Worker B: 读到 Run#3 status=pending  → 也想执行它
Worker A: UPDATE SET status='running' → 做了
Worker B: UPDATE SET status='running' → 也做了
结果: 同一条任务被执行了两次
```

这是经典的 **read-then-write 竞态**。两个并发读取都看到了 `pending`，都决定执行。Claim 用一条 SQL 把"检查 + 领取"原子化，数据库保证两个并发请求中只有一个能拿到返回行。

### 9.3 claim_run 的原子 CAS 实现（代码级解析）

`claim_run` 不靠应用层"先查再改"的两步操作，而是寄生于 **PostgreSQL 行级锁 + UPDATE 原子性** 的一条 SQL（`runtime.py` 第 76-123 行）：

```python
statement = (
    update(ProcessingRun)
    .where(
        # ── CAS 的 "Compare" ──
        ProcessingRun.id == run_id,
        or_(
            # 情况1: 还没人领过
            ProcessingRun.status == "pending",
            # 情况2: 之前有人领过但租约已过期
            and_(
                ProcessingRun.status == "running",
                ProcessingRun.lease_expires_at < claim_time,
            ),
        ),
    )
    .values(
        # ── CAS 的 "Set" ──
        status="running",
        execution_token=token,               # 全新 UUID，每一轮领取都不同
        execution_epoch=ProcessingRun.execution_epoch + 1,  # 数据库原子自增
        lease_expires_at=expires_at,         # 新租约到期时间
        worker_id=worker_id,
        started_at=func.coalesce(ProcessingRun.started_at, claim_time),
        heartbeat_at=claim_time,
        finished_at=None,
    )
    .returning(ProcessingRun.execution_epoch)  # 拿回新 epoch，用于后续验证
)
epoch = (await db.execute(statement)).scalar_one_or_none()
if epoch is None:
    return None  # ← claim 失败：别人已经领了 / 状态不对
```

**为什么这等于 CAS（Compare-And-Swap）？**

| 阶段 | 发生了什么 |
|------|-----------|
| **Compare** | WHERE 条件检查：这行必须处于 `pending`，或者 `running + 租约已到期`。不满足条件 → UPDATE 影响 0 行 → `epoch` 返回 `None` |
| **Swap** | 同一原子操作内，把行从旧状态整体翻转为新状态（running + 新 token + 新 epoch + 新租约） |

PostgreSQL 保证：两个并发的 `UPDATE ... WHERE id=X AND status='pending'`，只会有**一个**获得行锁并成功执行，另一个在等待锁后重读发现 `status='running'` 了，WHERE 条件不满足，返回 0 行。

**后续操作的 fencing 校验**（`_current_lease_predicate`）：

```python
def _current_lease_predicate(lease, now):
    return (
        ProcessingRun.id == lease.run_id,
        ProcessingRun.status == "running",
        ProcessingRun.execution_token == lease.token,    # token 必须完全匹配
        ProcessingRun.execution_epoch == lease.epoch,    # epoch 必须完全匹配
        ProcessingRun.lease_expires_at > now,            # 租约必须还没过期
    )
```

只有当初成功 claim 的那个 Worker，拿着正确的 `(token, epoch)` 组合，在租约有效期内，才能操作这行。任何一个条件不满足，`complete_run` / `renew_lease` / `fail_run` / `retry_run` 的 UPDATE 都命中 0 行，提交失败。

### 9.4 去重解决的三个具体场景

**场景一：Redis at-least-once 重复投递**

Taskiq / Redis Stream 的消费语义是 at-least-once——同一条消息可能被分发给多个 consumer：

```
Worker A: claim_run(run_id=3) → PostgreSQL 行锁 → 拿到 token → 成功 ✓
Worker B: claim_run(run_id=3) → 等 A 释放行锁 → 重读发现 status=running → WHERE 不匹配
Worker B: epoch=None → "别人领过了" → return ExecutionOutcome.IGNORED ✓
```

`executor.py:227` 注释写得很清楚：**"重复投递通过原子领取直接吸收"**。核心逻辑就一行：

```python
lease = await claim_run(db, run_id, ...)
if lease is None:
    return ExecutionOutcome.IGNORED   # ← 去重：没领到就安静跳过
```

**场景二：Reaper 补偿导致的重复消息**

Reaper 每 30 秒扫一次"有 Run 但没对应 Outbox 记录"的漏网之鱼。但在"Publisher 已发送但还没 mark_outbox_published"的窗口里，Reaper 会误判消息丢失并补发：

```
T+0s    Run#3 创建，Outbox#7 创建
T+0.5s  Publisher 把 Outbox#7 发到 Redis
T+0.6s  消息到达 Redis，但 Publisher 还没来得及 mark_outbox_published
T+0.7s  Reaper 扫到 Run#3 status=pending，且 Outbox#7 published_at=NULL
        → Reaper 认为这条消息丢了 → 补了一条 Outbox#8
T+0.8s  Outbox#7 和 Outbox#8 都被发到 Redis
        → 两条消息，同一个 run_id
Worker A 拿到消息 1 → claim 成功
Worker B 拿到消息 2 → claim 失败 → IGNORED ✓
```

**场景三：重试时旧消息仍在 Redis 中**

```
T+0s   消息进入 Redis
T+1s   Worker 执行中 → 瞬时失败 → retry_run → Run 变 pending + 新 Outbox
T+5s   新 Outbox 被 Publisher 发到 Redis
       但！原来的那条消息可能因 Redis 的 pending 机制被重新投递
       → 又出现两条 run_id=3 的消息
Worker A 拿到消息 1 → claim 成功
Worker B 拿到消息 2 → claim 失败 → IGNORED ✓
```

**总结**：不管这条 Run 被投递了多少次（Redis at-least-once、Reaper 补偿、重试叠加），最终只有一次 claim 能成功，其余全是空操作。CAS 去重把"消费者侧幂等"变成了数据库的一条原子 UPDATE。

## 10. 两层重试机制详解

### 关于 "RQ" —— 遗留注释，已过时

代码里**确实已经没有 RQ 了**。`executor.py` 第 1 行写得很清楚：`"""Taskiq 消息执行器"""`——现在用的是 Taskiq。但 `task_runtime.py` 第 37、39 行的注释还写着"RQ 自动重试不使用"/"RQ 自动重试不递增"，这是项目从 redis-rq 迁移到 Taskiq 时**忘了更新的遗留注释**。全代码库搜 `import rq` 一条都没有。

注释里说的"RQ 自动重试"其实指的是 `executor.py` 里 `_handle_failure` → `retry_run` 这套机制——完全是自己写的代码。

### 第一层：自动重试（同一条 Run）

**场景**：用户上传一个文档，触发 document_process 任务。

1. 系统创建 **Run #100**，`retry_of_run_id = NULL`，`attempt_no = 1`，`status = pending`
2. Worker A 领取，`status → running`，创建 **Span #1**（`metrics.attempt = 1`）
3. Handler 调 LLM API 超时，抛 `TransientTaskError`
4. `executor.py` 的 `_handle_failure` 检查：`attempt(1) <= max_auto_retries(3)` → 可以重试
5. 调 `retry_run`：Run #100 的 `status` 回退到 `pending`，新建一条延迟 Outbox（5 秒后可投递）
6. **此时 Run #100 的 `retry_of_run_id` 还是 NULL，`attempt_no` 还是 1，全程没动**
7. Worker B 领取 Run #100，创建 **Span #2**（`metrics.attempt = 2`），又超时
8. 同样回退到 pending，延迟 10 秒重投
9. Worker C 领取，创建 **Span #3**（`metrics.attempt = 3`），这次成功了
10. `complete_run` 把 Run #100 标记为 `succeeded`

整条 Run #100 有 3 条 Span 记录，每条的 `attempt` 值是从 `processing_spans` 表 COUNT 出来的。

### 第二层：业务重跑（新建一条 Run）

假设上面 Run #100 三次自动重试全失败了（`attempt=3 > max_auto_retries`），走 `fail_run` → `status = failed`。

1. 用户在界面上看到"处理失败"，点击"重试"按钮
2. 系统调用 `create_run_with_outbox`，传入 `retry_of_run_id = 100`，`attempt_no = 2`
3. 创建 **Run #101**——这是一条**全新的数据库行**，`status = pending`
4. Run #101 有自己独立的自动重试预算（Span 从 `attempt=1` 重新开始计数）
5. 如果 Run #101 也失败，用户再点重试 → 创建 **Run #102**，`retry_of_run_id = 101`，`attempt_no = 3`

这样 `retry_of_run_id` 形成一条链：`#102 ← #101 ← #100`。

### 对比总结

| | 自动重试 | 业务重跑 |
|---|---|---|
| 谁触发 | `executor.py` 自动 | 人工/调度手动 |
| Run 记录 | **同一条**，回退 pending | **新建一条** |
| `retry_of_run_id` | 不动（NULL） | 指向上一条 Run |
| `attempt_no` | 不动（保持初始值） | +1 |
| 重试计数在哪 | `processing_spans.metrics.attempt` | Run 行的 `attempt_no` 字段 |
| 错误记录在哪 | Span 的 `error_code/message` | Run 的 `error_code/message`（终态时） |

> **注意**：当前代码里**没有任何调用方实际传了 `retry_of_run_id` 或 `attempt_no`**——所有 `create_run_with_outbox` 的调用点都用的默认值 NULL 和 1。这两个字段目前是**预留设计**，业务重跑功能的表结构已就绪，但 API 入口还没实现。

### 11.2 effective_config_version / options_snapshot —— 举个例子

再看 `rag_ingestion.py` 第 144-155 行，`document_process` 派生 `rag_index` 时：

### 11.3 execution_token / epoch / lease / worker_id —— 什么是 claim_run 和 claim_time

**claim_run 是什么**：`runtime.py` 第 76 行的函数 `claim_run(db, run_id, worker_id, lease_seconds)`。它做一条原子 UPDATE：把 Run 的 status 从 pending 改成 running，同时写入 token/epoch/lease_expires_at。可以理解为 Worker"领取"任务。

**claim_time 是什么**：就是 `claim_run` 第一行 `claim_time = now or _utc_now()` 拿到的当前时间。用来算 `lease_expires_at = claim_time + lease_seconds`（900 秒）。

**host:pid:lane 是什么**（`tasks.py` 第 77-80 行）：
```python
def worker_identity(lane: str) -> str:
    host = os.getenv("HOSTNAME") or socket.gethostname()
    return f"{host}:{os.getpid()}:{lane}"
```

比如 `"llm-wiki-task-worker-shared-7f4b:12345:shared"`：
- `host` = Docker 容器名（`HOSTNAME` 环境变量）
- `pid` = 进程 ID（`os.getpid()`）
- `lane` = "shared" 或 "critical"（消费哪条 Stream）

写到 `processing_runs.worker_id` 字段，排障时一眼定位到"哪个容器、哪个进程、哪条 lane 在跑这个 Run"。

### 11.4 heartbeat_at —— 举个例子

**正常场景**：Worker A 在 t=0 领取 Run #100，`heartbeat_at = t=0`。`_heartbeat_loop` 每 15 秒调一次 `renew_lease`（`executor.py` 第 130-143 行）：
- t=15: `heartbeat_at = t=15`，`lease_expires_at += 900s`
- t=30: `heartbeat_at = t=30`
- t=45: `heartbeat_at = t=45`

排障时看 `processing_runs` 行：`heartbeat_at` 是 3 分钟前、`status = running` → 正常。如果 `heartbeat_at` 是 30 分钟前、`status = running` → 租约肯定过期了，reaper 会接管。

### 11.5 ProcessingSpan 的 run_id / parent_span_id / span_name / worker_attempt

- **run_id**：指向 `processing_runs.id`。Span #1 的 `run_id = 100` 说明属于 Run #100
- **parent_span_id**：当前代码**没有使用**（`start_worker_attempt` 没传）。预留用于未来嵌套阶段
- **span_name = "worker_attempt"**：每消费一次消息记一条执行尝试记录。`attempt` 次数存在 `metrics` JSONB 里

**具体例子**：Run #100 被 Worker A 消费 → COUNT `span_name='worker_attempt'` 的行数 = 0，+1 = 1 → 创建 Span #1，`metrics = {"attempt": 1, "execution_epoch": 1}`。A 失败后 `retry_run` 回退 pending。Worker B 消费 → COUNT = 1，+1 = 2 → 创建 Span #2，`metrics = {"attempt": 2, "execution_epoch": 2}`。

### 11.6 attempt 从哪读的 / max_auto_retries 从哪读的 / ProcessingSpan 有没有重试次数字段

**ProcessingSpan 没有专门的重试次数字段**。重试次数存在 `metrics` 这个 JSONB 里，键名是 `"attempt"`。

**读取代码**（`executor.py` 第 252 行）：
```python
attempt = int(attempt_span.metrics["attempt"])
```

**max_auto_retries 从哪读的**（`tasks.py` 第 92 行）：
```python
max_auto_retries=settings.TASK_MAX_AUTO_RETRIES,
```

**配置**（`settings.py` 第 100 行）：
```python
TASK_MAX_AUTO_RETRIES: int = 3
```

**判断逻辑**（`executor.py` 第 173 行 `_handle_failure`）：
```python
should_retry = not terminal and attempt <= max_auto_retries
```

如果 `attempt=4, max_auto_retries=3` → `4 <= 3` 是 False → 不重试，走 `fail_run` 打终态。

## 12. 进程架构与轮询机制

### 三个独立容器（docker-compose.yml）

| 容器 | 命令 | 职责 |
|---|---|---|
| `backend` | `uvicorn` | 收 API 请求，写 Run + Outbox 行到 DB |
| `outbox-publisher` | `python -m app.workers.outbox_worker` | 轮询 DB 的 `task_outbox` 表，发消息到 Redis Stream |
| `task-worker-shared` | `taskiq worker` | 消费 Redis Stream，执行 Run Handler |

**为什么 Outbox 必须独立进程**：
- Outbox Publisher 是个永不退出的 `while not stop.is_set()` 循环（`outbox_service.py` 第 104 行）
- 如果放在 API 进程里，API 重启时投递就停了
- 如果放在 Worker 进程里，Worker 在跑长任务（文档解析几分钟）时 asyncio 事件循环被占住，没法及时扫表
- 独立进程保证投递不中断，也不跟业务 Handler 抢资源

### 心跳轮询机制

**不是轮询**。心跳是 `asyncio.wait_for(stop.wait(), timeout=interval_seconds)`（`executor.py` 第 138 行）——一个带超时的 Event.wait。每 15 秒超时一次，醒来调 `renew_lease`，然后继续等下一个 15 秒。不是 while True 轮询 CPU。

### Outbox Publisher 轮询频率

`TASK_OUTBOX_POLL_SECONDS = 0.5`（`settings.py` 第 99 行）。没领到 Outbox 行时 `asyncio.wait_for(stop.wait(), timeout=0.5)`，等 0.5 秒再扫一轮。有行就立刻处理、立刻再来一轮。reaper 每 30 秒跑一次（`outbox_worker.py` 第 37 行 `reaper_interval_seconds=30`）。

### 为什么 A 还在跑但租约会过期？

**心跳续租是"尽量续"，不是"保证续"。**

`_heartbeat_loop` 是一个 asyncio Task，和 Handler 跑在同一个进程里。如果发生 **GC Stop-the-World**（JVM 的 full GC，或 Python 的 cyclic GC 收集大对象），整个进程被冻住——不只是 Handler 被冻，**心跳线程也被冻**。GC 停了 28 分钟，这 28 分钟里没有一次 `renew_lease` 调用，而 `lease_expires_at` 只给了 900 秒（15 分钟）。等 GC 结束 A 醒来时，租约已经过期了。

同理，网络分区也能造成：心跳的 `renew_lease` 调用发不出去（DB 连不上），连续 15 秒失败 → 租约过期。

> **心跳解决的是"正常情况下的长任务续期"，fencing 解决的是"心跳失败后的兜底保护"。两者互补，不是替代关系。**

## 13. Reaper 兜底机制详解

### 看哪个表的哪个字段

reaper 查的是 **`processing_runs` 表**（`reaper.py` 第 32-49 行）：

```python
or_(
    # 条件 A: pending 太久
    and_(
        ProcessingRun.status == "pending",
        ProcessingRun.created_at <= stale_before,   # created_at 距今超过 900s
    ),
    # 条件 B: running 但租约过期
    and_(
        ProcessingRun.status == "running",
        ProcessingRun.lease_expires_at <= recovery_time,  # lease_expires_at < now
    ),
)
and ~unpublished_exists   # 且 task_outbox 表里没有 published_at IS NULL 的行
```

涉及两个表：
- `processing_runs`：查 `status`、`created_at`、`lease_expires_at`
- `task_outbox`：子查询查 `published_at IS NULL`（有没有未发布的消息）

### 具体例子

**场景 1（pending 太久）**：
Run #200 在 t=0 创建，status=pending。Outbox 行已发布到 Redis Stream（`published_at` 有值）。但 Redis Stream 消息丢了 / Worker 消费后崩了没 ack。t=900s 时 reaper 扫到：`status=pending, created_at < stale_before, task_outbox 里没有 published_at IS NULL 的行` → 补一条新 Outbox。

**场景 2（running 但租约过期）**：
Run #200 被 Worker 领了，status=running，`lease_expires_at = t=900s`。Worker 进程被 OOM Kill 了，租约过期。但 Outbox 行已经发布了（`published_at` 有值）。t=900s reaper 扫到：`status=running, lease_expires_at < now, 没有未发布 Outbox` → 补一条新 Outbox。这条新 Outbox 被 Publisher 发出去后，下一个 Worker 消费时 `claim_run` 会命中 `status=running AND lease_expires_at < now` 分支，接管这个 Run。

### 幂等安全

reaper 是**幂等安全**的——即使补了多条 Outbox，多个 Worker 来领，`claim_run` 的 CAS 只有一个命中，其他返回 IGNORED。

## 15. 五大机制全景回顾

前面各章节从不同切面分析了很多设计细节。本章把这些机制放在一起做一次全景式总结，看清楚它们是如何层层咬合的。

### 15.1 五大机制总览

| 机制 | 哪层负责 | 核心字段/SQL | 容错方式 |
|------|---------|-------------|---------|
| **持久化** | `create_run_with_outbox` | Run + TaskOutbox 同事务写入 | 事务原子性，all-or-nothing |
| **重试** | Publisher 层 + Worker 层 | `publish_attempts` / `attempt_no` + `_retry_delay` | 指数退避 + 20% 随机抖动 |
| **延迟** | `available_at` 字段 | `WHERE available_at <= now()` | Publisher 轮询自然实现，无需额外基础设施 |
| **死信** | `max_auto_retries=3` 上限 | `fail_run` → status='failed' | 持久化终态，API 查询 + 人工介入 |
| **Lease** | Outer (Outbox lock) + Inner (Run lease) | `lock_token/locked_until` / `execution_token/execution_epoch/lease_expires_at` | fencing predicate + token 校验双重防护 |

### 15.2 一条消息的完整生命周期

```
 API ──→ create_run_with_outbox() ──→ task_outbox (持久化)
                                          │
                                          ▼
           ┌─────────────────────────────────────────┐
           │        Outbox Publisher 独立进程          │
           │                                         │
           │  claim_outbox_batch (SKIP LOCKED)       │
           │       │                                  │
           │       ▼                                  │
           │  发送到 Redis Stream ──→ worker 消费      │
           │       │                                  │
           │       ├── 成功 → mark_outbox_published   │
           │       └── 失败 → release_outbox_claim    │
           │                  ↑ 延迟: available_at 后移 │
           │                                           │
           │  Reaper 定时巡检 ──→ 补偿失联 Run           │
           └──────────────────────────────────────────┘
                                          │
                                          ▼
           ┌──────────────────────────────────────────┐
           │          Task Worker 消费消息              │
           │                                          │
           │  claim_run (CAS) → 心跳 15s              │
           │       │                                   │
           │       ├── 成功 → complete_run              │
           │       ├── 瞬时失败 → retry_run (延迟回队)   │
           │       └── 终态/超限 → fail_run (死信)       │
           └──────────────────────────────────────────┘
```

### 15.3 完整时间线：一个任务的一生

以一次"文档解析因网络超时重试后最终成功"为例：

```
T+0s    API → create_run_with_outbox → DB 事务提交
        Run#100 诞生，status=pending，Outbox 行关联

T+0s    Publisher 轮询到 available_at 已到
        → claim_outbox_batch (SKIP LOCKED) → 拿到 lock_token
        → 发送 Redis Stream → 成功 → mark_outbox_published

T+0.1s  Worker 收到 Redis 消息
        → claim_run (CAS) → 拿到 token+epoch+15min lease
        → start_worker_attempt → 建 Span（attempt=1）
        → 启动心跳（15s 间隔）

T+5s    心跳续租 → renew_lease → lease_expires_at 延长 15min

T+10s   Handler 执行中...
        💥 网络超时 → TransientTaskError
        → _handle_failure → 第1次重试
        → retry_run → Run 变 pending + Outbox.available_at = T+15s (延迟5s)

T+15s   Publisher 捡到重试 Outbox → 发送 Redis
        → Worker claim → 第2次 attempt（Span attempt=2）
        💥 又超时了
        → 第2次重试 → available_at = T+35s (5s × 2^1 + jitter = 延迟10s)

T+35s   Worker claim → 第3次 attempt（Span attempt=3）
        ✅ Handler 执行成功 → context.commit_success()
        → complete_run → status='succeeded'
        → finish_worker_attempt(status='succeeded')
```

如果第3次也失败（attempt=4 > max_auto_retries=3），则走 `fail_run` → `status='failed'`（死信）。

### 15.4 两层重试的独立性

这个系统有**两层完全独立的重试**，各自有各自的退避策略和幂等保护：

| | Publisher 层（发消息到 Redis） | Worker 层（消费后执行业务） |
|---|---|---|
| **触发条件** | `publish_outbox_claim` 发送失败 | Handler 抛 `TransientTaskError` / 异常 |
| **重试方式** | `release_outbox_claim`（释放锁 + 延迟 available_at） | `retry_run`（Run 回退 pending + 新 Outbox） |
| **退避策略** | `5s × 2^publish_attempts + jitter`，上限 300s | `5s × 2^(attempt-1) + jitter`，上限 300s |
| **重试上限** | 无硬上限（只要没超过 published_at，Publisher 会一直尝试） | `max_auto_retries=3`，超过走 `fail_run` |
| **失败终态** | `published_at` 保持 NULL，Reaper 兜底 | `status='failed'`，死信 |

### 15.5 为什么不需要分布式协调服务

所有这些机制加起来**不需要任何外部分布式协调服务**——没有 Redis 分布式锁、没有 ZooKeeper、没有 etcd。纯靠 PostgreSQL 原语实现：

| PostgreSQL 能力 | 在本系统中对应 |
|----------------|--------------|
| 事务原子性 (ACID) | Outbox 同事务写入，保证 Run 和消息意图同时落盘 |
| `UPDATE ... WHERE ... RETURNING` | `claim_run` 的原子 CAS，解决并发领取和重复投递 |
| 行级锁 | `SELECT ... FOR UPDATE SKIP LOCKED`，解决多 Publisher 并发抢占 |
| 条件 UPDATE（fencing predicate） | `complete_run` / `renew_lease` / `fail_run` 五条件校验 |

### 15.6 一句话总结

**持久化**保证不丢 → **延迟**实现退避 → **重试**消化瞬时故障 → **Lease** 防止僵尸 Worker → **死信**兜底不可恢复错误 → **CAS 去重**吸收一切重复投递。这五个机制不是独立功能，而是一条链上环环相扣的保险绳——每一条都在为前一个机制补漏洞。
