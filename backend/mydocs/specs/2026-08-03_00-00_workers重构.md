# Workers 模块结构化重构 Spec

> Spec Path: backend/mydocs/specs/2026-08-03_00-00_workers重构.md
> Phase: Plan
> Approval: Pending
> Created: 2026-08-03

## §1 Goal

将 `backend/app/workers/` 从 13 个平铺文件重构为分层子包结构，对标 `parsers/` 模块的组织模式，使 workers 回归"异步执行基础设施"的纯粹定位，业务 handler 迁移到领域模块。

## §2 In Scope

1. workers 内部按 `core/` + `outbox/` + `utils/` 分子包
2. 错误码枚举与异常类从 `executor.py` 拆分到 `core/schemas.py` + `core/errors.py`
3. `rag_ingestion.py` 迁移到 `knowledge_bases/service/`
4. handler 注册机制改为装饰器 + 显式清单（C1 方案）
5. `workers/__init__.py` 提供公开 API 重新导出
6. 更新所有受影响的导入路径（生产代码 + 测试）

## §3 Out of Scope

- 不处理 `parsers/service/document.py` 的反向依赖归属问题（标记后续单独处理）
- 不拆分 `rag_ingestion.py` 为多文件
- 不建 `rag/`、`wiki/` 子包
- 不新增 HTTP 路由
- 不改变任何运行时行为

## §4 Research Findings

### §4.1 workers 现状（13 个平铺文件，依赖图自底向上）

- 叶节点（无内部依赖）：`chunker`、`broker`、`outbox`、`runtime`
- 第一层：`executor`(←broker, runtime)、`publisher`(←outbox)
- 第二层：`reaper`(←executor)、`rag_ingestion`(←broker, chunker, executor, runtime)
- 第三层：`outbox_service`(←outbox, publisher, reaper)
- 第四层：`tasks`(←broker, executor, rag_ingestion)
- 第五层：`outbox_worker`(←outbox_service, tasks)

### §4.2 外部依赖

- 生产代码外部引用：仅 `app/parsers/service/document.py:32-33` 导入 `DEFAULT_QUEUE` + `create_run_with_outbox`
- 测试引用：`test_document_ingestion_runtime.py`、`test_task_runtime.py`、`test_task_executor.py`、`test_taskiq_broker.py`、`test_outbox_service.py`

### §4.3 架构定位问题

- `rag_ingestion.py` 是业务处理逻辑（文档解析、分块、embedding、revision 激活），不属于"执行基础设施"
- workers 独立进程部署时，业务 handler 耦合在基础设施模块内是架构隐患
- `parsers/service/document.py` 反向依赖 workers，形成模块级循环（本次不处理）

### §4.4 parsers 参考模式

- `core/`：纯领域契约（base、chain、document、errors、registry、schemas）
- `implementations/`：具体解析器
- `service/`：编排（dispatch、document、asset）
- `api/`：HTTP 边界
- `utils/`：纯工具
- `__init__.py`：公开 API 重新导出 + `__all__` + `_register_defaults()`

### §4.5 错误类拆分参考

parsers 模式：
- `core/schemas.py`：`ParseErrorCode` 枚举 + 数据契约
- `core/errors.py`：`ParserError` 基类 + 子类（依赖 schemas）

workers 现状：`ExecutionOutcome` 枚举 + 4 个异常类全塞在 `executor.py:34-64`

### §4.6 handler 注册机制现状

- `tasks.py:31-34` 硬编码 `RUN_HANDLERS` 字典，直接 import 两个 handler
- `tasks.py:37-39` `register_run_handlers(handlers)` 批量注册函数
- 测试直接 `from app.workers.tasks import RUN_HANDLERS`

## §5 Design Decisions

| # | 决策点 | 选定方案 | 理由 |
|---|--------|----------|------|
| 1 | 映射原则 | 方案 B：按子系统分组 | workers 是"状态机+可靠投递+业务处理"三个正交子系统，强行套 parsers 的 core 语义会冲突 |
| 2 | broker 归属 | 留在 `core/` | 54 行小文件，提取单文件子包无收益；core 定位为"执行基础设施"而非"纯领域" |
| 3 | chunker 归属 | `utils/chunker.py` | 纯函数无 I/O，对标 parsers utils |
| 4 | outbox 子系统 | 5 文件全进 `outbox/` | 完整可靠投递子系统内聚，跨包依赖单向 outbox->core |
| 5 | handler 位置 | 迁移到 `knowledge_bases/service/` | 业务 handler 回归领域模块，workers 回归纯基础设施 |
| 6 | handler 注册 | C1：装饰器 + 显式清单 | 解耦 workers 与业务模块；显式清单可控、无隐式副作用 |
| 7 | tasks.py 归属 | `core/tasks.py` 整体 | 接受 core 含装配代码；避免拆分过度 |
| 8 | outbox_worker 归属 | 留在 `outbox/` | 子系统自包含入口，内聚性强 |
| 9 | 错误类拆分 | `core/schemas.py` + `core/errors.py` | 完全对标 parsers 模式 |
| 10 | __init__.py | 重新导出公开 API | 对标 parsers，提供稳定 API 面 |
| 11 | 测试导入 | 公开 API 走顶层，原语走全路径 | 与生产代码导入策略一致 |

## §8 Handler 注册机制设计 (C1)

### `core/tasks.py` 新增内容

```python
import importlib
from collections.abc import Callable, Mapping
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from app.workers.core.executor import RunHandler

RUN_HANDLERS: dict[str, "RunHandler"] = {}

# 显式 handler 模块清单（新增 handler 时加一行路径）
HANDLER_MODULES = [
    "app.knowledge_bases.service.rag_ingestion",
    # 未来: "app.knowledge_bases.service.wiki_generate",
]


def register_run_handler(run_type: str):
    """业务 handler 注册装饰器，由各领域 service 模块使用。"""
    def decorator(handler: "RunHandler") -> "RunHandler":
        RUN_HANDLERS[run_type] = handler
        return handler
    return decorator


def register_run_handlers(handlers: Mapping[str, "RunHandler"]) -> None:
    """批量注册（保留，兼容测试与编程式注册）。"""
    RUN_HANDLERS.update(handlers)


def _load_handlers() -> None:
    """启动时加载显式清单中的 handler 模块，触发装饰器注册。"""
    for module_path in HANDLER_MODULES:
        importlib.import_module(module_path)


# 在模块加载末尾或进程启动时调用
_load_handlers()
```

## §10 Risks

| 风险 | 缓解 |
|------|------|
| `_load_handlers()` 在模块加载时触发循环导入 | rag_ingestion import workers 顶层，workers.core.tasks importlib.import_module 延迟加载，避免循环 |
| 测试 mock 路径失效 | 测试改用顶层导入公开 API，mock 目标调整为 `app.knowledge_bases.service.rag_ingestion` |
| `__init__.py` 导出导致 import 链过重 | 导出的都是轻量符号（常量、类定义），无实例化副作用 |
