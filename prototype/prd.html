01 — POSITIONING

产品定位与核心类比

工作知识库是一款知识库管理桌面客户端。知识库本身是一个可插拔、可备份、可迁移的数据包（类似 MySQL 数据库），桌面客户端负责连接、浏览、搜索和管理这个数据包（类似 Navicat / DBeaver）。

一句话定位：知识库管理桌面客户端 — 像 Navicat 管理 MySQL 一样管理你的团队知识库。
核心类比

MySQL 数据库知识库数据包自包含目录：markdown + 向量 + 图谱 + manifest
Navicat / DBeaver本桌面客户端连接、浏览、搜索、管理知识库
localhost / 远程服务器本地目录 / 内网部署连接本地知识库或团队内网共享知识库

数据库备份/导出知识库快照/导出/迁移数据包级别的可移植性

维度v1.0（旧）v2.0（新）原因

模块数量4 个模块5 个模块（+知识库连接管理）客户端需要连接管理作为入口
核心价值主张
  • 数据包可插拔：知识库是一个自包含目录，可挂载/卸载/快照/导出/迁移。和数据库一样独立于客户端存在。
  • 检索优先：向量搜索 + BM25 混合检索 + AI 实时推理。不依赖 AI 编译，直接返回正确答案。
  • 双 AI 通道：可代理本地 CLI 工具（Claude Code、Gemini CLI），也可配置 API Key 使用内置 Mini Agent。灵活适配不同用户习惯。
  • 双用户群体：开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。同一份数据，两种入口。
  • 桌面原生体验：Tauri 打包为轻量桌面应用（~10MB），双击即开，内网也可 Docker 部署。

03 — PRINCIPLES

核心设计原则

检索优先，编译可选

知识库的默认能力是检索：文档导入后自动分块 + 向量嵌入，即可被搜索和 AI 对话消费。不需要 AI 编译即可使用。编译是一个可选的增强工具——对高价值内容做深度结构化整理，但不是知识库运作的前提。这确保了：导入即可用、无黑箱、token 成本可预测。

客户端-数据包分离

桌面应用是客户端，知识库是数据包。两者完全解耦——客户端不存储知识数据，数据包不依赖特定客户端。知识库可以在应用内挂载/卸载/切换，也可以导出为 zip 在实例间迁移。

双通道、一份数据

开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。两条通道共享同一份知识库数据包，看到的数据完全一致。

编辑级视觉语言

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局——给用户"这是一个有沉淀的系统"的感知。

04 — ARCHITECTURE DECISION

架构决策：编译型 vs 检索型

本节记录产品架构的核心决策——为什么选择"检索优先"而非"编译优先"。

两种范式概述
维度编译型（obsidian-wiki 范式）检索型（GBrain 范式）
核心流程导入文档 → AI 编译为结构化 wiki 页面 → 查询时读编译产物导入文档 → 分块 + 嵌入向量 → 查询时检索 chunks + AI 实时推理
写入成本高（每篇 ~7000 tokens LLM）低（分块 + 嵌入 ~200 tokens）
查询成本较低（读 2-3 个 wiki 页面 ≈ 2600 tokens）中等（读 8 个 chunks ≈ 4200 tokens）
可复现性不可复现可复现（确定性代码）
黑箱风险高（编译幻觉被固化）低（AI 只在查询时介入）
成本收益分析
环节检索型（我们的方案）编译型
单次查询总成本~4200 tokens~2600 tokens
编译一篇文档额外成本无~7000 tokens
盈亏平衡点—同一主题需被查询 ≥ 5 次才回本
架构决策结论：对于我们的产品（团队级知识库，几百到几千文档规模），检索型是正确选择。成本更低、风险更小、结果可复现。编译作为可选增强工具保留在 Phase 5。

未来可选的编译增强（Phase 5）
  • 用户手动触发：在文档管理页选中特定文档，点击"编译"按钮
  • 系统建议触发：当某个主题的查询频率超过阈值时，系统建议"是否编译为综合页面？"
  • 编译 Diff 审核：编译完成后展示 diff 对比视图，用户确认后才写入 wiki/
  • 不做默认行为：编译永远是可选操作，不是导入流程的一部分

06 — CONNECTION

模块一：知识库连接

知识库连接是客户端的入口模块。类似 Navicat 的"连接管理"，用户在这里管理所有知识库连接——挂载本地目录、连接内网部署的知识库、切换当前活跃知识库。

功能规格
功能描述
当前连接显示当前活跃的知识库，包括名称、路径、统计信息（页面数、向量数、最后更新时间）
已注册连接列表显示所有已注册的知识库连接，区分本地目录和远程连接
添加本地知识库选择本地目录作为知识库，自动检测 manifest.json，若无则引导创建新知识库
连接远程知识库输入内网地址（如 http://192.168.1.5:3000），连接团队共享的 Docker 部署知识库
切换知识库点击已注册连接切换当前活跃知识库，所有模块自动切换到新数据
快照打包当前知识库为 .zip 文件（含全部数据），完整备份，目标端开箱即用
导出仅导出源数据（manifest + raw + wiki），不含衍生数据。目标端首次打开时自动重建索引

数据分层：源数据（必须迁移）：manifest.json + raw/ + wiki/。衍生数据（可删可重建）：vectors/ + index/ + graph/。

不同导入渠道支持不同内容类型，确保操作安全和便捷：

渠道文件导入URL 导入说明

内容验证管线（v2.2 新增）

文档进入分块流程前，先经过三道验证关卡，确保入库内容的质量和安全性：

GATE 01
幂等检测：计算文件 SHA-256 content_hash，与已有记录比对。若 hash 相同则跳过，避免重复处理
GATE 02
垃圾内容过滤：检测文件是否过短（<50 字符）、纯数字/乱码、重复内容。命中则标记"已跳过"并提示用户
GATE 03
隐私检测：正则扫描 API Key、密码、身份证号、手机号等敏感模式。命中时弹窗提醒用户确认是否脱敏后导入
多层级分块策略（v2.2 增强）

参考 GBrain 的递归分块器，采用 5 层分隔符层级，配合 CJK 语言支持和代码语义分块：

层级分隔符说明
L1\n# / \n## / \n### Markdown 标题边界，最高优先级
L2\n\n（双换行）段落边界，过长标题块按段落细分
L3。！？.!?（句末标点）句子边界，支持中英文混合
L4，；;：（句中停顿）子句边界，进一步细分长句
L5字符级切分最终兜底，确保不超过目标大小
分块参数
参数v2.1 旧值v2.2 新值说明
目标块大小最大 1000 字符300 词（约 600-800 中文字符）更小的块提升检索精度
重叠大小200 字符50 词（约 100-150 中文字符）保持上下文连贯
CJK 支持按字符计CJK 字符单独计数，每个汉字 = 1 词避免中文文本被过度切分
最大块大小1000 字符目标 × 1.5（约 450 词）硬上限，超过则强制切分
代码文件语义分块（v2.2 新增）

对代码文件（.ts / .py / .java / .go 等 36 种语言）使用 Tree-sitter 做语义分块，按 AST 节点边界（函数/类/方法）切分，而非简单的文本分隔符。这确保每个 chunk 是一个完整的语义单元（一个函数或一个类），不会被从中间切断。

设计决策：分块使用确定性代码（不调用 LLM），保证结果可复现、成本低、速度快。5 层递归 + CJK 支持 + 代码语义分块的组合，在"不需要 LLM"的前提下尽可能提升分块质量。

P0纯文本 (.txt)零成本直接读取

编辑 → 重建流程（v2.2 增加幂等检测）

raw/ 和 wiki/ 下的文档都可编辑。编辑保存时先计算新的 content_hash，与旧值比对——若相同则跳过重建（内容未变），若不同则触发增量重建：

STEP 01
用户编辑文档内容，点击"保存"
STEP 02
写回源文件 + 计算新 content_hash
STEP 03
若 hash 变化：删除旧 chunks → 重分块 → 重嵌入 → 更新图谱边（异步）
STEP 04
若 hash 未变：跳过重建，提示"内容未修改"
STEP 05
状态栏提示"已重新嵌入（N chunks）"。失败则标记为"待嵌入"
导入流程（检索优先）
STEP 01
拖拽文件或选择文件夹，经过内容验证管线（幂等/垃圾/隐私检测）
STEP 02
5 层递归分块（标题→段落→句子→子句→字符），代码文件用 Tree-sitter
STEP 03
上下文包裹：为每个 chunk 拼接文档级前缀（仅嵌入时使用）
STEP 04
每个 chunk 调用 embedding API 生成向量，存入 LanceDB + FTS5
STEP 05
提取语义边类型（mentions/relates_to 等），更新知识图谱
08 — AI DIALOGUE

模块三：AI 对话

AI 对话是知识库的智能问答入口。用户提问时，系统自动从当前知识库中检索相关文档片段，注入为 AI 上下文，由 AI 实时综合后生成带引用标注的回答。

检索优先原则：AI 对话基于"向量搜索 + AI 实时推理"，而非"读取预编译的 wiki 页面"。即使知识库没有任何编译产物，AI 对话也能正常工作——它直接检索原始文档的 chunks。

意图分类规则（v2.2 新增）

零 LLM 调用的轻量意图分类器，通过关键词匹配和正则模式实现：

意图类型匹配模式示例权重调整

后融合 Boost 详解（v2.2 新增）
Boost 类型公式说明默认系数
标题匹配score × title_factor查询词命中文档标题时加分title_factor = 1.25
显著性score × (1 + 0.05 × salience)高 salience 节点（被频繁引用/查询）加分salience ∈ [0, 1]
时效性score × (1 + recency_factor)基于 effective_date 的指数衰减，半衰期 30 天half_life = 30d
图谱信号score × (1 + 0.05 × log(1 + backlinks))被引用次数多的文档加分（类似 PageRank 简化版）系数 = 0.05
来源类型score × source_weight不同来源目录有不同基础权重synthesis=1.1, raw=1.0, compiled=0.9
为什么后融合 Boost 重要：纯 RRF 融合只考虑了"在两路检索中的排名"，没有考虑文档本身的质量信号。后融合 Boost 将文档的标题匹配度、显著性、时效性、图谱引用等元信息注入排序，让"好的文档"排在前面。这是 GBrain 检索质量高于普通 RAG 的关键因素之一。
上下文检索（v2.2 新增）

在嵌入（embedding）阶段，为每个 chunk 拼接文档级上下文前缀，让向量编码时包含更多语义信息。这个上下文只在嵌入时使用，不存储——用户看到的 chunk 内容仍然是原文，但向量空间中的表示更丰富。

嵌入时的上下文包裹格式： "本文档: {document_title} 本章: {section_heading} --- {chunk_text}" 效果：向量编码时"知道"自己属于哪个文档、哪个章节 存储：只存原始 chunk_text，上下文前缀不写入数据库 查询：查询文本不做上下文包裹（因为查询本身不包含文档上下文）
为什么上下文检索有效：一个 chunk "退款必须在 7 天内发起" 单独编码时语义模糊——退什么款？哪个系统？拼接上"本文档: IAP退款流程 / 本章: 退款规则"后，向量编码能更准确地表达语义，检索精度显著提升。
