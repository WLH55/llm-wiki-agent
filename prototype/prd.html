01 — POSITIONING

产品定位与核心类比

工作知识库是一款知识库管理桌面客户端。知识库本身是一个可插拔、可备份、可迁移的数据包（类似 MySQL 数据库），桌面客户端负责连接、浏览、搜索和管理这个数据包（类似 Navicat / DBeaver）。

一句话定位：知识库管理桌面客户端 — 像 Navicat 管理 MySQL 一样管理你的团队知识库。

核心价值主张
  • 数据包可插拔：知识库是一个自包含目录，可挂载/卸载/快照/导出/迁移。和数据库一样独立于客户端存在。
  • 检索优先：向量搜索 + BM25 混合检索 + AI 实时推理。不依赖 AI 编译，直接返回正确答案。
  • 双 AI 通道：可代理本地 CLI 工具（Claude Code、Gemini CLI），也可配置 API Key 使用内置 Mini Agent。灵活适配不同用户习惯。
  • 双用户群体：开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。同一份数据，两种入口。
  • 桌面原生体验：Tauri 打包为轻量桌面应用（~10MB），双击即开，内网也可 Docker 部署。

v2.3 路线重排（本次更新）CHANGED

v2.2 引入了 9 项 GBrain 增强但 Phase 分配有依赖隐患。v2.3 基于逐项"收益 vs 复杂度 vs 依赖"评估，做 3 处调整，避免重嵌入陷阱和数据冷启动问题：

#调整点v2.2 安排v2.3 调整原因
1 上下文检索 Phase 3 → Phase 1 代码量极小，但若 P1/2 不做、P3 才开启，已入库向量会全部过时（同文本有/无上下文语义不同），需全量重嵌入。必须和分块一起一次到位
2 后融合 Boost Phase 3 一次全上 拆两步：P3 上无依赖项，P5 上数据依赖项 5 个 Boost 里 3 个需要前置数据（salience/时效/图谱 backlinks），P3 刚上线时数据为空 Boost 不生效。先上"标题+来源类型"两个零依赖项，数据积累后再启其余
3 元数据字段精简 4 个新字段全 P1 分级：P1 只必需 2 个，P5 按需 3 个 salience 需定期重算、last_retrieved_at 每次检索写回、effective_date 多数文档没有明确生效日——隐藏维护成本高。P1 只做 content_hash(幂等必需) + generation(写入时确定零成本)
未动的 6 项增强保持 v2.2 原安排：5 层分块(P1)、内容验证(P1)、导入渠道(P1)、语义边(P2)、意图分类(P3)、代码语义分块(P4)、重排序(P5)。调整只涉及上面 3 项。
v2.4 架构转向（本次更新）MAJOR

v2.3 之前选 LanceDB + SQLite FTS5 双库方案，前提假设是"桌面单机、无并发"。深入调研 gbrain 源码 + 确认"团队实时多人并发访问同一知识库"是核心需求后，该假设不成立。v2.4 转向 PGLite（个人）+ Postgres（团队）双引擎架构，跟随 gbrain 的成熟范式：

#议题v2.3 旧方案v2.4 新方案转向理由
1 向量数据库 LanceDB pgvector 团队并发要求 MVCC + 行级锁 + 跨表事务，LanceDB 不支持跨库事务、SQLite 多人写会锁冲突
2 全文检索 SQLite FTS5 Postgres tsvector + GIN 与向量同库，可 JOIN；中文加 zhparser 解决
3 个人形态 纯文件（.lance + .sqlite） PGLite（嵌入式 Postgres WASM） 零配置，与团队形态同一套 SQL 同一套 schema，零代码分叉
4 团队形态 未明确 外部 Postgres + 服务端 + thin 客户端 多客户端并发、实时共享、source 级权限
5 事务一致性 需 outbox 模式补偿 原生 ACID 导入/编辑 = 一个事务，原子性天然保证
6 代码组织 双库拼接（LanceDB + SQLite） BrainEngine 接口，一套 SQL 两引擎 避免检索层 SQL 分叉（FTS5 vs ts_rank 差异是根本性的）
7 图谱遍历 JS BFS + edges 表 SQL 递归 CTE WITH RECURSIVE + 数组环检测，多跳路径原生支持
转向决策依据（gbrain 源码实证）：深入 gbrain 源码发现——① 它的向量表 JOIN 关系表（pages/sources）在 HNSW 内层做 WHERE 下推，是多人并发 + source 权限隔离的必要条件；② 它的所有 boost（backlink/salience/recency）最终乘法在 JS 层，与单库/双库无关；③ 它的图遍历用 SQL 递归 CTE，LanceDB 的 DataFusion SQL 不支持。结论：单库 JOIN 的真正价值是"并发 + 权限 + 事务"，团队场景下这是硬约束。
付出的代价（已知并接受）：PGLite WASM 体积 ~30MB（Tauri 包从 ~10MB 增至 ~40MB）；冷启动 2-10s（WASM 初始化）；中文 FTS 需配置 zhparser；PGLite 在 Windows 的成熟度待验证。这些代价换取"团队实时并发 + 一套 SQL + 原生事务"，ROI 划算。

v2.8 OKF 互操作层（本次更新）NEW

调研 Google Cloud 发布的 Open Knowledge Format（OKF）v0.1（2026-06-12 开源规范），发现它把 Karpathy 的 LLM Wiki 模式标准化成了"知识文档该长什么样"的开放规范。核心思想："缺的不是又一个知识服务，而是一个格式（format, not platform）"。v2.8 采纳 OKF 作为我们的导出/导入互操作格式——不改数据库架构，只让知识库 bundle 可被任何 OKF 工具消费。

v2.8 核心价值：我们的数据模型（page=文档+frontmatter+slug+图谱互连）天然符合 OKF 规范——type/title/tags 字段、markdown 正文、slug 寻址都是 OKF 超集。导出时只需把 pages 表导成 OKF bundle，零翻译成本。声明 OKF 兼容 = 知识库能被任何 OKF 消费者（Google 工具/其他 agent/未来工具）读取，不被锁定在自有格式里。详见 §12 OKF 互操作层。

03 — PRINCIPLES

核心设计原则

检索优先，编译可选

知识库的默认能力是检索：文档导入后自动分块 + 向量嵌入，即可被搜索和 AI 对话消费。不需要 AI 编译即可使用。编译是一个可选的增强工具——对高价值内容做深度结构化整理，但不是知识库运作的前提。这确保了：导入即可用、无黑箱、token 成本可预测。

客户端-数据包分离

桌面应用是客户端，知识库是数据包。两者完全解耦——客户端不存储知识数据，数据包不依赖特定客户端。知识库可以在应用内挂载/卸载/切换，也可以导出为 zip 在实例间迁移。

双通道、一份数据

开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。两条通道共享同一份知识库数据包，看到的数据完全一致。

编辑级视觉语言

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局——给用户"这是一个有沉淀的系统"的感知。

04 — ARCHITECTURE DECISION

架构决策：编译型 vs 检索型

本节记录产品架构的核心决策——为什么选择"检索优先"而非"编译优先"。

两种范式概述
维度编译型（obsidian-wiki 范式）检索型（GBrain 范式）
核心流程导入文档 → AI 编译为结构化 wiki 页面 → 查询时读编译产物导入文档 → 分块 + 嵌入向量 → 查询时检索 chunks + AI 实时推理
写入成本高（每篇 ~7000 tokens LLM）低（分块 + 嵌入 ~200 tokens）
查询成本较低（读 2-3 个 wiki 页面 ≈ 2600 tokens）中等（读 8 个 chunks ≈ 4200 tokens）
可复现性不可复现可复现（确定性代码）
黑箱风险高（编译幻觉被固化）低（AI 只在查询时介入）
成本收益分析
环节检索型（我们的方案）编译型
单次查询总成本~4200 tokens~2600 tokens
编译一篇文档额外成本无~7000 tokens
盈亏平衡点—同一主题需被查询 ≥ 5 次才回本
架构决策结论：对于我们的产品（团队级知识库，几百到几千文档规模），检索型是正确选择。成本更低、风险更小、结果可复现。编译作为可选增强工具保留在 Phase 5。

06 — CONNECTION v2.6 一应用两模式

模块一：知识库连接

知识库连接是客户端的入口模块，类似 Navicat 的"连接管理"。这是同一个应用的两个配置选项，不是两个产品（v2.6 澄清）：

  • 本地连接（个人模式）：启用进程内 PGLite，数据存本地目录。无需服务端，单人使用。
  • 远程连接（团队模式）：填服务端 URL + access_token，thin 连内网 Postgres。多人并发协作。

用户在连接页面二选一，应用据此装载 PgliteEngine 或 RemoteEngine。两种模式背后是同一套 schema 同一套 SQL，UI 和业务逻辑无感知。详见 §13 双引擎架构。

代码文件语义分块（v2.2 新增）

对代码文件（.ts / .py / .java / .go 等 36 种语言）使用 Tree-sitter 做语义分块，按 AST 节点边界（函数/类/方法）切分，而非简单的文本分隔符。这确保每个 chunk 是一个完整的语义单元（一个函数或一个类），不会被从中间切断。

设计决策：分块使用确定性代码（不调用 LLM），保证结果可复现、成本低、速度快。5 层递归 + CJK 支持 + 代码语义分块的组合，在"不需要 LLM"的前提下尽可能提升分块质量。

STEP 01 · 事务外
拖拽文件或选择文件夹，经过内容验证管线（幂等/垃圾/隐私检测）
STEP 02 · 事务外
5 层递归分块（标题→段落→句子→子句→字符），代码文件用 Tree-sitter
STEP 03 · 事务外
上下文包裹：为每个 chunk 拼接文档级前缀（仅嵌入时使用）
STEP 04 · 事务外
每个 chunk 调用 embedding API 生成向量（慢网络调用，必须在事务外）
STEP 05 · ★事务内

v2.5 事务约定：STEP 01-04 是事务外准备阶段（解析、分块、embedding），STEP 05 是事务内原子写入（一次 BEGIN...COMMIT 包住所有 DB 操作）。这样既保证"导入要么全成要么全失败"，又不会因 embedding 慢而长时间持锁。
08 — AI DIALOGUE

模块三：AI 对话

AI 对话是知识库的智能问答入口。用户提问时，系统自动从当前知识库中检索相关文档片段，注入为 AI 上下文，由 AI 实时综合后生成带引用标注的回答。

12 — DATA MODEL v2.4 重写

数据模型

v2.4 架构转向后，数据模型从"目录结构 + frontmatter"升级为"数据库 schema 为权威，文件系统为快照"。所有结构化数据（文档、chunks、向量、图谱边、来源）都存数据库，磁盘文件只是可重建的 raw 原文 + 可读快照。

存储分层：数据库 vs 文件系统
层存什么形态可重建？
数据库（权威 source of truth） pages / content_chunks（含向量+tsvector） / links / sources / ingest_log / users / access_tokens PGLite（个人，一个目录）/ Postgres（团队，一个库） 部分（chunks/向量可从 raw 重建，pages/links 也可重建）
raw/ 文件 原始文档源文件（md/pdf/txt...） 磁盘目录 ❌ 不可重建（人类创作内容）
manifest.json 身份证 + 引擎配置 + 统计 磁盘文件 可从数据库统计重建
wiki/ 文件 沉淀知识（synthesis/notes）的 markdown 快照 磁盘目录 可从 pages 表导出
v2.4 核心变化：数据库成为 source of truth。raw/ 文件是不可重建的源数据（必须备份），其余全部可从 raw + 数据库重建。这和 gbrain 的"brain repo（git markdown）是源头，Postgres 是检索镜像"哲学一致——只是我们的 raw 对应它的 brain repo，我们的数据库对应它的 Postgres。
核心表 Schema（v2.4）

以下表结构同时跑在 PGLite 和 Postgres 上（同一套 DDL），是 BrainEngine 接口的契约基础。参考 gbrain schema 精简而来。

sources 表（数据源 / 权限分区）
CREATE TABLE sources ( id TEXT PRIMARY KEY, -- 如 'iap' / 'ads' / 'dingtalk' name TEXT NOT NULL, kind TEXT DEFAULT 'team', -- team | personal | shared archived BOOLEAN DEFAULT FALSE, -- 归档隔离（visibility 过滤） created_at TIMESTAMPTZ DEFAULT now(), stats JSONB -- 缓存的统计（文档数/chunk数） );
pages 表（文档 = 知识库写入/寻址最小单位）v2.5

page = 一篇文档，是知识库的写入/读取/寻址最小单位（slug 唯一寻址）。原始文档、沉淀综合、笔记、实体（人/公司/概念）都是 page，靠 type 区分。注意：page 不是"检索最小单位"——检索按 chunk 匹配（见下表）。

CREATE TABLE pages ( id SERIAL PRIMARY KEY, slug TEXT NOT NULL, -- 如 'iap/refund-flow'、'people/zhang-san' source_id TEXT NOT NULL REFERENCES sources(id), type TEXT NOT NULL, -- source|synthesis|note|compiled|person|company|concept -- （实体也是独立 page，靠 type 区分，非仅 mention） title TEXT NOT NULL, body_md TEXT, -- ★ 解析清洗后的 markdown 正文（非原始字节！） -- raw/ 存原始文件(PDF/DOCX原样)，body_md 存可检索可渲染的 markdown -- body_md 可从 raw 重建，raw 不可从 body_md 重建 summary TEXT, -- frontmatter.summary（图谱节点摘要用） tags TEXT[] DEFAULT '{}', content_hash TEXT, -- SHA-256，幂等检测（P1 必需） generation INT DEFAULT 1, -- 知识代次：原始=1 综合=2 编译=3 source_file TEXT, -- raw/ 路径（source 类型）或 wiki/ 路径 search_vector TSVECTOR, -- Postgres FTS（触发器维护） effective_date DATE, -- P5：时效 Boost salience REAL DEFAULT 0, -- P5：显著性 Boost owner_id TEXT, -- 归属用户（团队权限） version BIGINT DEFAULT 1, -- P3：乐观锁 CAS（防 lost-update） deleted_at TIMESTAMPTZ, -- 软删（visibility 过滤） created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now(), UNIQUE (source_id, slug) -- slug 在 source 内唯一 ); CREATE INDEX idx_pages_search ON pages USING GIN(search_vector); CREATE INDEX idx_pages_source ON pages(source_id) WHERE deleted_at IS NULL; CREATE INDEX idx_pages_effdate ON pages ((COALESCE(effective_date, updated_at)));
v2.5 澄清 body_md 语义：不要把 body_md 当成 raw 文件的副本——它存的是解析清洗后的 markdown 正文（PDF 提取文本、Word 转 markdown、URL 抓取清洗后的结果）。raw/ 保留原始字节（保真存档、可重新解析），body_md 是可检索可渲染的统一格式。两者关系：body_md 可从 raw + 解析器重建，raw 不可从 body_md 重建。这正是 §12 存储分层"raw 是源头、DB 是镜像"的体现。
content_chunks 表（分块 + 向量 = 检索最小单位）v2.5

chunk = 检索/匹配的最小单位。一个 page 在写入时同步切成多个 chunk（1:N），向量（embedding）存在 chunk 级而非 page 级。检索返回 chunk（附所属 page 元数据），AI 对话默认注入 chunk 片段。

CREATE TABLE content_chunks ( id SERIAL PRIMARY KEY, page_id INT NOT NULL REFERENCES pages(id) ON DELETE CASCADE, chunk_index INT NOT NULL, body TEXT NOT NULL, -- 原始 chunk 文本（用户看到） chunk_source TEXT DEFAULT 'body', -- v2.5 新增：body | timeline | code -- 区分 chunk 来自正文/时间线/代码块，便于来源过滤和溯源 char_start INT, char_end INT, token_count INT, section_path TEXT, -- 如 '## 退款流程' embedding vector(1536), -- pgvector 向量（嵌入时含上下文包裹） -- ★ 向量在 chunk 级，pages 表无 embedding 列 search_vector TSVECTOR, -- chunk 级 FTS content_hash TEXT, -- 幂等 embedding_model TEXT, -- 用哪个模型嵌入的 UNIQUE (page_id, chunk_index) ); CREATE INDEX idx_chunks_embedding ON content_chunks USING hnsw (embedding vector_cosine_ops); -- 余弦 HNSW CREATE INDEX idx_chunks_search ON content_chunks USING GIN(search_vector); CREATE INDEX idx_chunks_page ON content_chunks(page_id);

写入事务边界（必须遵守的工程约定）

一次文档写入（导入/编辑/沉淀）涉及多张表（pages/chunks/links），必须保证原子性。参考 gbrain 踩坑后的最佳实践——embedding 在事务外，DB 写入在一个短事务内：

事务外（无锁，可慢）───────────────────────── ├── 解析 markdown / 内容验证 / 算 content_hash ├── 读旧 page（getPage） └── embedBatch() ← 调 embedding API，可能几秒（慢！必须放事务外） │ ▼ 事务内（engine.transaction，BEGIN...COMMIT，毫秒级短事务） ├── putPage() INSERT...ON CONFLICT DO UPDATE（原子 upsert） ├── addTag() × N ├── upsertChunks() 写 content_chunks（含向量） └── addLink() × N 写图谱边 │ ▼ 事务后（fail-soft，失败不回滚主流程） └── 更新 aliases / 缓存
为什么 embedding 必须在事务外：embedding 是网络调用，可能耗时几秒。如果放事务内，会长时间持有行锁，阻塞其他写入。gbrain 源码注释明确："Embed BEFORE the transaction (external API call)"——这是踩过坑的修正。事务只包纯 DB 写入（毫秒级），锁持有时间极短。
同文档并发编辑冲突策略（分两步）
阶段策略机制用户体验
Phase 1 last-write-wins（抄 gbrain） ON CONFLICT DO UPDATE 无条件覆盖 后写覆盖前写，前者存进 page_versions 可手动 revert
Phase 3 乐观锁 CAS（兜底） pages.version 列 + 写入带 expected_version + WHERE version=? 比对 冲突时报"文档已被他人修改，请刷新"
为什么分两步：团队知识库不是 Google Docs，"两人同改同一篇技术文档的同一句话"极罕见。Phase 1 用 last-write-wins 快速跑通（gbrain 就是这么做的，接受这个风险）；Phase 3 加 CAS 兜底——成本仅一个 version 列 + 一处 WHERE 比对，但能避免最伤人的"静默丢失"。真实高频场景是"改不同文档"（行级锁无冲突）和"读写并发"（MVCC 无冲突），这两个 Postgres 原生解决。

seekdb 是什么（关键澄清）
常见误解实际

向量表 JOIN 关系表（v2.4 核心能力）

v2.4 单库方案的最大优势：向量检索时直接 JOIN 关系表，把权限/source/软删/归档等过滤下推进 HNSW 候选集，避免"取一堆看不见的候选再过滤"导致召回率掉。参考 gbrain searchVector 的两阶段 CTE 模式：

-- Stage 1 向量路：HNSW 候选集 + 关系过滤下推 WITH hnsw_candidates AS ( SELECT p.slug, p.title, p.type, p.source_id, cc.id AS chunk_id, cc.body, 1 - (cc.embedding <=> $1::vector) AS raw_score -- 余弦相似度 FROM content_chunks cc JOIN pages p ON p.id = cc.page_id -- 向量表 JOIN 关系表 JOIN sources s ON s.id = p.source_id WHERE cc.embedding IS NOT NULL AND p.source_id = ANY($visible_sources) -- 权限/source 下推 AND p.deleted_at IS NULL -- 软删过滤下推 AND NOT s.archived -- 归档过滤下推 AND p.type = ANY($types) -- 类型过滤下推 ORDER BY cc.embedding <=> $1::vector -- 纯距离排序，保住 HNSW LIMIT 30 ), scored AS ( SELECT *, raw_score * source_factor(slug) AS score -- source-tier boost FROM hnsw_candidates ), best_per_page AS ( -- 每页取最高分 chunk SELECT DISTINCT ON (source_id, slug) * FROM scored ORDER BY source_id, slug, score DESC ) SELECT * FROM best_per_page ORDER BY score DESC LIMIT $top_k;
为什么这个 JOIN 重要：团队场景下，某客户端只该看自己 source 的 10% 数据。如果先向量取 top-100 再过滤，可能 90 个是别人的、过滤后只剩 10 个有效候选，召回率从 ~100% 掉到 ~10%。WHERE 下推让 HNSW 只在合格行上扫描，召回率不掉。这是单库方案相对双库的真正护城河。
图谱遍历用 SQL 递归 CTE（v2.4）

多跳最短路径、邻域展开用 Postgres 的 WITH RECURSIVE，无需 JS BFS。同一套 SQL 跑在 PGLite 和 Postgres 上：

-- 从 seed 页出发的 N 跳邻域（带最短路径） WITH RECURSIVE walk AS ( SELECT id, slug, source_id, 0::int AS depth, ARRAY[id] AS visited, ARRAY[slug] AS path FROM pages WHERE slug = ANY($seeds) AND deleted_at IS NULL UNION ALL SELECT p2.id, p2.slug, p2.source_id, w.depth + 1, w.visited || p2.id, w.path || p2.slug FROM walk w JOIN links l ON (l.from_page_id = w.id OR l.to_page_id = w.id) JOIN pages p2 ON p2.id = CASE WHEN l.from_page_id = w.id THEN l.to_page_id ELSE l.from_page_id END WHERE w.depth < $max_depth AND NOT (p2.id = ANY(w.visited)) -- 数组做环检测 AND p2.deleted_at IS NULL ) SELECT slug, MIN(depth) AS hop, array_agg(DISTINCT link_type) AS via_types FROM walk WHERE depth > 0 GROUP BY slug ORDER BY hop ASC;
后融合 Boost：SQL 取信号 + JS 乘分

backlink/salience/recency 的信号用 SQL 聚合查询（GROUP BY/COUNT/JOIN），boost 乘法在 JS 层（与 gbrain 一致）。这是软依赖，与单库/双库无关：

// 1. SQL 取 backlink 计数 SELECT to_page_id, COUNT(DISTINCT from_page_id) AS backlinks FROM links WHERE to_page_id = ANY($page_ids) AND link_source IS DISTINCT FROM 'mentions' GROUP BY to_page_id; // 2. JS 乘 boost for (const r of results) { const count = backlinks[r.page_id] ?? 0; r.score *= 1 + 0.05 * Math.log(1 + count); }

为什么后融合 Boost 重要：纯 RRF 融合只考虑了"在两路检索中的排名"，没有考虑文档本身的质量信号。后融合 Boost 将文档的标题匹配度、显著性、时效性、图谱引用等元信息注入排序，让"好的文档"排在前面。这是 GBrain 检索质量高于普通 RAG 的关键因素之一。
上下文检索（v2.3 提前到 Phase 1）v2.3 重排

在嵌入（embedding）阶段，为每个 chunk 拼接文档级上下文前缀，让向量编码时包含更多语义信息。这个上下文只在嵌入时使用，不存储——用户看到的 chunk 内容仍然是原文，但向量空间中的表示更丰富。

为什么 v2.3 把它从 Phase 3 提前到 Phase 1：上下文检索的代码量极小（只改 embedding 调用），但它影响已入库向量的语义。如果 Phase 1/2 不做、Phase 3 才开启，那么之前所有 chunks 的向量都"过时"了（同文本有/无上下文语义不同），必须全量重嵌入整个知识库。因此必须和分块、首次嵌入一起在 Phase 1 一次到位。
嵌入时的上下文包裹格式： "本文档: {document_title} 本章: {section_heading} --- {chunk_text}" 效果：向量编码时"知道"自己属于哪个文档、哪个章节 存储：只存原始 chunk_text，上下文前缀不写入数据库 查询：查询文本不做上下文包裹（因为查询本身不包含文档上下文）
为什么上下文检索有效：一个 chunk "退款必须在 7 天内发起" 单独编码时语义模糊——退什么款？哪个系统？拼接上"本文档: IAP退款流程 / 本章: 退款规则"后，向量编码能更准确地表达语义，检索精度显著提升。
