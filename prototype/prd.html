01 — POSITIONING

产品定位与核心类比

工作知识库是一款知识库管理桌面客户端。知识库本身是一个可插拔、可备份、可迁移的数据包（类似 MySQL 数据库），桌面客户端负责连接、浏览、搜索和管理这个数据包（类似 Navicat / DBeaver）。

一句话定位：知识库管理桌面客户端 — 像 Navicat 管理 MySQL 一样管理你的团队知识库。

03 — PRINCIPLES

核心设计原则

检索优先，编译可选

知识库的默认能力是检索：文档导入后自动分块 + 向量嵌入，即可被搜索和 AI 对话消费。不需要 AI 编译即可使用。编译是一个可选的增强工具——对高价值内容做深度结构化整理，但不是知识库运作的前提。这确保了：导入即可用、无黑箱、token 成本可预测。

客户端-数据包分离

桌面应用是客户端，知识库是数据包。两者完全解耦——客户端不存储知识数据，数据包不依赖特定客户端。知识库可以在应用内挂载/卸载/切换，也可以导出为 zip 在实例间迁移。同一份知识库可以被多个客户端同时连接（内网部署场景）。

双通道、一份数据

开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。两条通道共享同一份知识库数据包，看到的数据完全一致。AI 能力可由本地 CLI 代理（Claude Code 等）或内置 Mini Agent 提供，用户自选。

编辑级视觉语言

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局——给用户"这是一个有沉淀的系统"的感知，而非"又一个 AI 产品"。

04 — ARCHITECTURE DECISION

架构决策：编译型 vs 检索型

本节记录产品架构的核心决策——为什么选择"检索优先"而非"编译优先"。这个决策直接影响导入流程、token 成本模型、知识可信度和系统复杂度。

两种范式概述
维度编译型（obsidian-wiki 范式）检索型（GBrain 范式）
核心流程 导入文档 → AI 编译为结构化 wiki 页面 → 查询时读编译产物 导入文档 → 分块 + 嵌入向量 → 查询时检索 chunks + AI 实时推理
写入成本 高（每篇文档需要 LLM 调用，约 7000 tokens） 低（分块 + 嵌入，不需要 LLM，约 200 tokens embedding）
查询成本 较低（读 2-3 个编译页面 ≈ 2600 tokens） 中等（读 8 个 chunks ≈ 4200 tokens）
可复现性 不可复现（同一文档编译两次产出不同页面） 可复现（分块和嵌入是确定性代码）
黑箱风险 高（AI 编译可能产生幻觉并固化到 wiki 页面中） 低（AI 推理在查询时实时进行，不会固化错误）
依赖 AI 理解力 重度依赖（编译质量完全取决于 LLM 能力） 轻度依赖（AI 只在查询推理时介入）
澄清：obsidian-wiki 和 GBrain 的关系

obsidian-wiki 明确引用了 Andrej Karpathy 的 "compile, don't retrieve" 理念——认为传统 RAG 每次查询都在"重新发现知识"，而编译型只编译一次、查询时直接消费编译产物。但 GBrain 并不遵循这个理念，它是纯粹的检索型系统。两者走的是完全不同的路。

关键澄清："compile, don't retrieve" 是一个哲学立场，不是工程定律。它描述了一种理想状态（知识被预处理为最佳消费形态），但在实践中，编译的成本、风险和可维护性需要严格评估。我们的产品不盲从这个理念，而是基于成本收益分析做出决策。
成本收益分析

"重新发现知识"的成本到底高不高？用具体数字算一下：

环节检索型（我们的方案）编译型
单次查询的 AI 输入 tokens ~3200（8 个 chunks × 400 tokens） ~1600（2 个 wiki 页面 × 800 tokens）
单次查询的 AI 输出 tokens ~1000 ~1000
单次查询总成本 ~4200 tokens ~2600 tokens
每次查询节省 — ~1600 tokens
编译一篇文档的额外成本 无 ~7000 tokens（读原文 + 提取 + 写入）
盈亏平衡点 — 同一主题需被查询 ≥ 5 次才回本

每次查询编译型省约 1600 tokens，但当前 LLM 的上下文窗口动辄 128k-200k tokens，3200 tokens 的上下文对模型来说微不足道。省的绝对成本很小（几厘钱），但引入的风险（编译幻觉、不可复现、额外复杂度）却很大。

编译型的固有风险
风险一：编译幻觉被固化

如果 AI 在编译时产生幻觉（比如把"退款 7 天内"编译成了"退款 30 天内"），这个错误会被写入 wiki 页面。之后所有查询都会基于这个错误页面回答，形成系统性的错误传播。而检索型每次查询都从原始文档出发，即使某次推理出错，下次查询还会重新从原文推理，错误不会被固化。

风险二：编译产物本身也需要被检索

编译型并没有省掉"嵌入向量"这一步——编译好的 wiki 页面同样需要被分块和嵌入到向量数据库才能被搜索。所以编译型在检索链路上并没有本质简化，只是把"多个原始 chunks"变成了"几个编译页面的 chunks"。

风险三：编译结果不可复现

同一篇文档编译两次会产出不同的 wiki 页面（LLM 固有的随机性）。在团队场景下，这导致知识库内容不可预测、不可审计。而分块 + 嵌入是确定性代码，结果完全可复现。

什么时候编译才有价值

编译的额外 token 成本只在以下三个条件同时满足时才值得投入：

条件说明我们的场景
同一主题被反复查询 编译一次花 7000 tokens，每次查询省 1600 tokens，需查询 ≥ 5 次才回本 大多数主题只被查询 1-3 次，不满足
原始信息分散在多个来源 5 个文档的碎片信息综合成 1 个结构化页面，查询效率确实更高 大多数知识集中在 1-3 个文档中，检索型够用
知识库规模大到检索质量下降 5000+ chunks 时向量搜索精度下降，编译后的高密度页面更好 初期规模几百到一两千文档，不满足
架构决策结论：对于我们的产品（团队级知识库，几百到几千文档规模），检索型（分块 + 嵌入 + 混合搜索 + AI 实时推理）是正确选择。成本更低、风险更小、结果可复现。编译作为可选的增强工具保留在 Phase 5——当知识库规模真的膨胀到检索质量下降时，可以对高频主题做选择性编译。
我们的导入流程（无编译）
原始文档 (raw/) │ ▼ ① 文档解析（确定性代码） ├── Markdown → 直接读取 ├── PDF → 提取文本 + 结构 └── HTML/JSON/CSV → 解析内容 │ ▼ ② 分块（确定性代码，不调用 LLM） ├── 按标题分块（H1/H2/H3 边界） ├── 按段落分块（过长的标题块再细分） └── 按字符数限制（单块最大 1000 字符，重叠 200 字符） │ ▼ ③ 嵌入向量（embedding API，非 LLM） ├── 每个 chunk 调用 embedding API 生成 1536 维向量 └── 存入 LanceDB（本地文件） │ ▼ ④ 图谱提取（确定性代码） ├── 提取 [[wikilink]] 引用 ├── 正则匹配实体引用 └── 更新 graph.json │ ▼ ⑤ 完成 — 文档立即可搜索、可被 AI 对话引用 全程不消耗 LLM tokens（embedding API 成本约 200 tokens/文档，约 ¥0.001）
未来可选的编译增强（Phase 5）

如果知识库规模增长到检索质量下降的程度，可以引入选择性编译：

  • 用户手动触发：在文档管理页选中特定文档，点击"编译"按钮
  • 系统建议触发：当某个主题的查询频率超过阈值时，系统建议"是否编译为综合页面？"
  • 编译 Diff 审核：编译完成后展示 diff 对比视图，用户确认后才写入 wiki/
  • 不做默认行为：编译永远是可选操作，不是导入流程的一部分

设计决策：知识库连接管理是 v2.0 新增的核心模块。它使得"一个客户端管理多个知识库"成为可能，也让团队场景下"桌面客户端连接内网知识库"有了清晰的入口。

STEP 01
用户编辑文档内容，点击"保存"
STEP 02
写回源文件（raw/xxx.md 或 wiki/xxx.md）
STEP 03
删除该文件对应的所有旧 chunks（LanceDB + FTS5 + meta）

08 — AI DIALOGUE

模块三：AI 对话

AI 对话是知识库的智能问答入口。用户提问时，系统自动从当前知识库中检索相关文档片段，注入为 AI 上下文，由 AI 实时综合后生成带引用标注的回答。

raw/ vs wiki/ 的区别（v2.1 重新定义）： raw/ 存储原始文档（PDF、MD、TXT 等），是知识的"一手来源"，导入时进入。可编辑——编辑后自动触发增量重建。 wiki/ 存储所有沉淀知识（不再是狭义的"编译产物"），包含三类：synthesis/（AI 对话沉淀）、notes/（手写笔记）、compiled/（Phase 5 可选的编译产物）。 检索引擎同时搜索 raw/ 和 wiki/，结果用来源 badge 区分，让用户知道"这条是原文，那条是沉淀的综合"。
数据分层（v2.1 澄清）
分类包含特性
源数据 manifest.json + raw/ + wiki/ 必须迁移，丢失不可恢复。导出时必带
衍生数据 vectors/ + index/ + graph/ 由代码从源数据生成，可删可重建。导出时可选（带了即开即用，不带则目标端首次打开重建）

检索引擎

检索引擎是产品的核心能力层。采用混合检索架构，确保在各种查询场景下都能返回准确结果。

用户查询 │ ▼ ┌───────────────────────────────────────────────────┐ │ Step 1: 关键词检索 (BM25) │ │ · 引擎：SQLite FTS5（index/bm25.sqlite） │ │ · 对 raw/ 和 wiki/ 的全文做 BM25 匹配 │ │ · 返回 top-30 候选 chunks │ ├───────────────────────────────────────────────────┤ │ Step 2: 向量语义检索 (LanceDB) │ │ · 引擎：LanceDB（vectors/chunks.lance） │ │ · 查询 embedding → 近似最近邻搜索 │ │ · 返回 top-30 候选 chunks │ ├───────────────────────────────────────────────────┤ │ Step 3: RRF 融合排序 │ │ · Reciprocal Rank Fusion 融合两路结果 │ │ · 综合分数 = 1/(k+rank_bm25) + 1/(k+rank_vec) │ │ · 去重 + 按分数排序 │ │ · 返回 top-K（默认 8） │ ├───────────────────────────────────────────────────┤ │ Step 4 (可选): 交给 AI 通道做推理综合 │ │ · AI 对话模块注入 top-K 结果作为上下文 │ │ · 全局搜索模块直接返回结果（不调 AI） │ └───────────────────────────────────────────────────┘
