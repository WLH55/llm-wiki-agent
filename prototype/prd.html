01 — POSITIONING

产品定位与愿景

工作知识库是一款面向团队知识沉淀与检索的桌面应用。它将散落在各处的文档、笔记、技术方案统一收纳为结构化的 Wiki 页面，通过 AI 自动提取实体关系构建知识图谱，并提供基于语义的智能检索和问答能力。

一句话定位：本地优先的 AI 知识管理系统——把团队的隐性知识变成可检索、可对话、可视化的知识图谱。
核心价值主张
  • 本地优先：所有数据以 Markdown 文件形式存储在本地，零云服务依赖，可 Git 版本管理，可离线使用
  • AI 增强：自动从原始文档编译为结构化 Wiki 页面，自动提取实体关系构建知识图谱，对话式知识问答
  • 可插拔知识库：一个知识库即一个自包含目录（manifest + wiki + graph + vectors），可挂载/卸载/快照/迁移
  • 桌面原生体验：通过 Tauri 打包为轻量桌面应用（~10MB），双击即开，无浏览器地址栏
与竞品的差异化
维度 Notion / Confluence Obsidian / Logseq 工作知识库（本产品）
知识结构化 人工组织，手动分类 双向链接，手动维护 AI 自动编译 + 图谱构建
检索方式 全文搜索 关键词 + 图谱导航 混合检索（关键词 + 向量 + RRF）
知识问答 无 插件支持 原生 AI 对话 + 引用溯源
数据存储 云端 本地 Markdown 本地 Markdown + LanceDB 向量

用户画像

需要快速了解团队技术积累和业务知识的分布。关注"我们有什么知识、知识之间的关系是什么、知识质量如何"。主要通过知识图谱浏览和 AI 对话来消费知识，偶尔直接搜索特定文档。

日常产生大量技术文档、方案、排障记录。需要便捷地将这些原始内容导入系统，由 AI 自动编译为结构化知识。也通过 MCP 协议在 IDE 中直接查询知识库。

03 — PRINCIPLES

核心设计原则

编辑级知识档案，不是 AI 工具

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局（01/02/03/04）——给用户"这是一个有沉淀的系统"的感知，而非"又一个 AI 产品"。

对话与检索职责分离

AI 对话（模块一）负责智能问答：调用 AI 综合能力，回答慢但有深度，带引用溯源。全局搜索（模块四）负责纯检索：直接查询 wiki 页面，不调用 AI，延迟低、结果精确。两者在界面上有明确的 banner 引导，用户不会混淆。

编辑-编译工作流

文档编辑不直接生效到知识库。用户编辑文档后保存，系统提示"编译知识"——编译过程包括：解析文档结构 → 提取实体关系 → 更新知识图谱 → 重建向量索引。这个两步设计让用户对"知识库状态"有明确感知，避免静默更新造成的不确定性。

本地优先，可插拔

每个知识库是一个自包含目录，包含 manifest.json、wiki/、graph/、raw/、vectors/ 五个部分。知识库可以在应用内挂载/卸载/切换，也可以导出为 zip 在实例间迁移。数据存储完全脱离应用本身。

06 — DOCUMENTS

07 — AI DIALOGUE

模块三：AI 对话

AI 对话是知识库的智能问答入口。用户提问时，系统自动从当前知识库中检索相关页面，注入为 AI 上下文，生成带有引用标注的回答。回答中的引用编号可点击跳转到对应文档。

08 — SEARCH

模块四：全局搜索

全局搜索是知识库的精确检索入口。支持混合搜索（关键词 + 向量语义），不调用 AI，延迟极低。搜索结果按相关度排序，每条结果显示文档标题、摘要片段（关键词高亮）、文件路径和相关度评分。

12 — MCP TOOLS

MCP 工具集成（开发者接口）

通过 MCP（Model Context Protocol）标准协议，将知识库能力暴露给外部 AI 编程工具（Claude Code、Cursor、Qoder 等）。开发者在日常编码过程中可以直接查询知识库、沉淀开发经验、保存问答到知识库，无需切换到桌面应用操作。

核心价值：让知识库"活"在开发者的工作流中——写代码时随手查、随手存，知识自然生长，而不是"写完文档再去维护"。
注册方式

开发者在支持 MCP 的 AI 工具中注册知识库服务，一行命令即可接入：

# Claude Code / Cursor / Qoder 中注册 claude mcp add llm-wiki -- node app/dist/mcp-server.js # 注册后，AI 工具即可调用知识库的全部 MCP 工具
MCP 工具清单
search_wiki — 语义检索知识库
参数类型必填说明
querystring是自然语言查询或关键词
modeenum否hybrid（默认） / keyword / vector
top_knumber否返回结果数量，默认 5
type_filterstring[]否按类型过滤：source / entity / concept / synthesis

返回：匹配的 wiki 页面列表，每项含标题、摘要、类型、相关度评分、文件路径。

示例场景：开发者在写退款功能时，让 AI 查一下知识库里已有的退款相关文档 → AI 调用 search_wiki("退款流程", top_k=3) → 返回 IAP退款流程(0.91)、PaymentSystem(0.74)、RefundPolicy(0.55)
get_page — 获取指定页面内容
参数类型必填说明
page_idstring是页面 ID 或文件名（如 "iap-refund-flow"）
include_graphboolean否是否包含该节点的图谱关联信息，默认 false

返回：完整的 Markdown 内容 + frontmatter 元信息 + 可选的图谱关联数据（入边/出边节点列表）。

示例场景：开发者需要了解 PaymentSystem 的完整架构 → AI 调用 get_page("PaymentSystem", include_graph=true) → 返回完整文档内容 + 关联节点：IAP退款、AdChannelSelection、支付网关...
update_page — 更新或创建知识页面
参数类型必填说明
page_idstring是页面 ID（已存在则更新，不存在则创建）
contentstring是Markdown 内容（含 frontmatter）
typeenum否source / entity / concept / synthesis，默认 source
tagsstring[]否标签列表
auto_compileboolean否是否自动触发知识编译（更新图谱+向量），默认 true

返回：操作结果（创建/更新）、页面路径、编译状态。

示例场景：开发者在解决一个支付 bug 后，把经验沉淀到知识库 → AI 调用 update_page("payment-gateway-timeout-fix", content="...", type="source", tags=["支付","排障"]) → 页面创建成功，自动编译到知识库，图谱和向量索引同步更新
save_qa — 保存问答到知识库
参数类型必填说明
questionstring是问题原文
answerstring是回答内容（Markdown）
source_pagesstring[]否引用的 wiki 页面 ID 列表
tagsstring[]否标签列表
auto_compileboolean否是否自动编译，默认 true

返回：生成的页面 ID、路径、编译状态。

示例场景：开发者问了一个很好的技术问题，AI 给了详细回答，想把这组 QA 保存下来 → AI 调用 save_qa(question="IAP退款超时如何处理？", answer="...", source_pages=["iap-refund-flow"]) → 自动生成 synthesis 类型页面，编入知识库，下次搜索可命中
list_pages — 列出知识库页面
参数类型必填说明
typeenum否按类型过滤
tagstring否按标签过滤
limitnumber否返回数量上限，默认 20

返回：页面列表（ID、标题、类型、标签、更新时间）。

build_graph — 手动触发图谱构建
参数类型必填说明
scopeenum否full（全量重建，默认）/ incremental（仅处理变更页面）

返回：构建结果（节点数、边数、耗时、是否有异常）。

13 — COMPILATION INTEGRITY

编译质量保障机制

AI 将原始文档编译为结构化 Wiki 页面的过程中，存在信息丢失的风险：AI 可能过度摘要、遗漏细节、或"自作聪明"地改写原文意图。本章节定义一套多层保障机制，确保编译过程可追溯、可验证、可回退。

设计原则：编译是"给原始内容加结构化外壳"，不是"把整篇文档压缩成摘要"。原文的丰富度不丢，结构化是增量而非替代。
行业参考：obsidian-wiki 的三层防丢机制

obsidian-wiki 是目前在"AI 编译知识库"方向上做得最完整的开源项目。它的核心架构是三层分离：Tier 1（原始文档，不可变）/ Tier 2（编译后 Wiki，AI 维护）/ Tier 3（Schema，处理规则）。在防止编译信息丢失方面，它建立了多层重叠的保障机制，对我们的项目有直接的借鉴价值。

obsidian-wiki 的机制具体做法对我们的借鉴
原始文档不可变 Raw sources 存储在独立目录，永远不修改不删除，wiki 页面通过 sources 字段指回原文 ✅ 采纳：我们的 raw/ 目录 + source_file 字段已实现同等设计
Manifest 增量追踪 .manifest.json 记录每个原始文档的内容 hash、摄入时间、创建了哪些 wiki 页面。编译不是一次性黑箱，而是可追溯的增量过程 ✅ 采纳：新增 manifest.json 到知识库结构，记录每次编译的输入输出
溯源标记（Provenance） wiki 页面中每条信息标注来源状态：无标记 = 直接来自原文，^[inferred] = AI 推理，^[ambiguous] = 不确定。frontmatter 记录比例（extracted: 0.7, inferred: 0.2, ambiguous: 0.1） ✅ 采纳：在 wiki 页面 frontmatter 中增加 provenance 字段
Staging 审核流程 AI 编译产物先进 _staging/ 目录，人工审核后才进入主 wiki。用 diff 格式（+ 新增 - 删除）展示变更 ✅ 采纳：编译后先展示 diff 对比视图，用户确认后再生效
结构健康度检测 wiki-status 分析知识图谱空洞、孤岛页面、分类连接度。wiki-lint 检查孤立页面、断裂链接、过期内容、推断比例超标 ✅ 采纳：编译完成后输出结构健康报告
Rebuild 能力 随时可快照当前 wiki，从原始文档重新全量编译。保证编译过程完全可逆 ✅ 采纳：提供全量重建入口，支持回退到任意历史快照
置信度评分 根据来源数量和质量自动计算 base_confidence（同行评审论文 = 0.9，博客 = 0.4），页面有 lifecycle 状态流转 ⚠️ 延后：v2 再实现，v1 先用 provenance 比例
去重合并 wiki-dedup 用多信号评分检测重复页面，合并时选"幸存者"，失败方变为重定向占位符（不删除） ⚠️ 延后：v2 再实现
我们采纳的五层保障机制
第一层：原文不可变 + 溯源链接

所有原始文档存储在 raw/ 目录，编译后永不修改、不删除。每个 wiki 页面的 frontmatter 通过 source_file 字段指回原文。用户可以随时点击"查看原文"对照确认。这是我们架构的基础保障，已在当前设计中实现。

第二层：Manifest 编译追踪

知识库根目录新增 .manifest.json，记录每次编译的完整轨迹。这使得编译过程从黑箱变为白箱——可以回答"这篇 wiki 页面是从哪些原始文档编译来的""上次编译是什么时候""原始文档有没有更新过"。

{ "version": 1, "compilations": { "iap-refund-flow": { "source_hash": "sha256:a1b2c3...", "source_file": "raw/IAP系统/refund.md", "compiled_at": "2026-06-16T10:30:00Z", "pages_created": ["wiki/iap-refund-flow.md"], "pages_updated": ["wiki/PaymentSystem.md"], "coverage": 0.92, "provenance": { "extracted": 0.78, "inferred": 0.15, "ambiguous": 0.07 } } } }
第三层：Provenance 溯源标记

wiki 页面中的每一条信息都标注其来源状态，让用户一眼区分"原文说了什么"和"AI 推断出什么"。

标记含义视觉表现
无标记 直接从原始文档中提取的信息 正常文字，无特殊样式
^[inferred] AI 从多个来源综合推理得出的结论 淡琥珀色背景 + 虚线下划线，hover 显示推理来源
^[ambiguous] 存在矛盾或不确定的信息 淡红色背景 + 波浪下划线，hover 显示冲突来源

frontmatter 中增加 provenance 字段记录整体比例：

--- title: IAP退款流程 type: source provenance: extracted: 0.78 # 78% 内容直接来自原文 inferred: 0.15 # 15% 为 AI 推理 ambiguous: 0.07 # 7% 存在不确定性 ---

编译后的 lint 检查会自动校验：如果 inferred 比例超过 40% 或 ambiguous 超过 15%，发出警告提示用户审查。

第四层：编译结果 Diff 审核

编译完成后不直接生效，而是展示一个对比视图供用户审核。这个流程参考了 obsidian-wiki 的 _staging/ → wiki-stage-commit 模式。

审核视图布局
┌─────────────────────────┬─────────────────────────┐ │ 原始文档 (raw/) │ 编译结果 (wiki/) │ │ │ │ │ IAP 系统退款流程包括 │ ## 摘要 │ │ 用户发起、系统校验、 │ IAP 系统退款流程包括... │ │ 退款执行三个核心步骤， │ │ ← 绿色高亮：已覆盖 │ 需在 7 天退款期内完成。 │ ## 核心论点 │ │ │ - 退款必须在 7 天内发起 │ ← 绿色高亮：已覆盖 │ 退款金额不超过原支付 │ │ │ 金额的 100%，特殊情况 │ │ ← 红色标记：未覆盖 │ 需人工审批。 │ (此段未被纳入编译结果) │ │ │ │ │ │ ## AI 补充 │ │ │ - 退款流程建议增加... ^[inferred] │ ← 琥珀色：AI 推理 ├─────────────────────────┴─────────────────────────┤ │ 覆盖率: 92% (23/25 段已覆盖) │ │ ⚠ 2 段未被覆盖，请检查是否需要手动补充 │ │ │ │ [✓ 确认编译] [✏ 手动补充] [← 回退到原文] │ └────────────────────────────────────────────────────┘

用户可以逐项确认、手动补充未覆盖的段落，或者直接回退。确认后编译结果才正式生效到 wiki 和图谱。

第五层：结构健康度检测

每次编译完成后自动运行结构检测，输出一份健康报告。参考 obsidian-wiki 的 wiki-status 和 wiki-lint 机制。

检测项说明告警阈值
信息覆盖率 原始文档中有多少段落被编译结果覆盖 < 80% 时警告
推断比例 wiki 页面中 AI 推理内容的占比 > 40% 时警告
模糊比例 wiki 页面中不确定/矛盾信息的占比 > 15% 时警告
孤岛页面 没有任何入链的 wiki 页面 存在时提示
断裂链接 [[wikilink]] 指向不存在的页面 存在时警告
过期内容 原始文档更新时间晚于 wiki 页面编译时间 存在时提示需要重新编译
知识空洞 经常共现但缺少桥接文档的概念对 存在时建议创建综合页面
编译完整流程图
原始文档 (raw/) │ ▼ ① AI 编译引擎 ├── 提取结构化信息（frontmatter / 摘要 / 核心论点） ├── 标注 provenance（extracted / inferred / ambiguous） ├── 提取实体关系（[[wikilink]] / 图谱边） └── 计算覆盖率（原文段落 vs 编译段落） │ ▼ ② Manifest 记录 ├── 写入 .manifest.json（hash / 时间 / 输入输出映射） └── 标记编译状态为 "pending_review" │ ▼ ③ Diff 审核视图 ├── 左栏：原始文档 ├── 右栏：编译结果（provenance 颜色标记） ├── 底部：覆盖率 + 未覆盖段落高亮 └── 用户操作：确认 / 手动补充 / 回退 │ ▼ ④ 确认后生效 ├── 写入 wiki/ 目录 ├── 更新向量索引（LanceDB） ├── 更新知识图谱（graph/） ├── 运行结构健康检测 └── 输出健康报告 │ ▼ ⑤ 知识就绪 — 搜索和对话可命中新知识
可逆性保障
操作说明
单页面回退 任何 wiki 页面可回退到编译前的原始文档，删除结构化信息，还原为原文
全量重建 从 raw/ 目录重新编译全部 wiki 页面。编译前先快照当前 wiki（带时间戳），可随时恢复
增量重建 根据 manifest 中的 hash 对比，仅重新编译内容有变更的原始文档，适合日常维护
