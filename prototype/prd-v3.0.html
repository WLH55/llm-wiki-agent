01 — POSITIONING

产品定位与核心类比

一句话定位

工作知识库是一款知识库管理桌面客户端。知识库本身是一个可插拔、可备份、可迁移的数据包（类似 MySQL 数据库），桌面客户端负责连接、浏览、搜索和管理这个数据包（类似 Navicat / DBeaver）。

一句话定位：知识库管理桌面客户端 — 像 Navicat 管理 MySQL 一样管理你的团队知识库。

03 — PRINCIPLES

核心设计原则

检索优先，编译可选

知识库的默认能力是检索：文档导入后自动分块 + 向量嵌入，即可被搜索和 AI 对话消费。不需要 AI 编译即可使用。编译是一个可选的增强工具——对高价值内容做深度结构化整理，但不是知识库运作的前提。这确保了：导入即可用、无黑箱、token 成本可预测。

客户端-数据包分离

桌面应用是客户端，知识库是数据包。两者完全解耦——客户端不存储知识数据，数据包不依赖特定客户端。知识库可以在应用内挂载/卸载/切换，也可以导出为 zip 在实例间迁移。

双通道、一份数据

开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。两条通道共享同一份知识库数据包，看到的数据完全一致。

一个应用两种模式

同一个 Tauri 应用支持本地连接（PGLite 个人模式）和远程连接（Postgres 团队模式）。用户无需安装两个产品，本地积累的知识库可随时"升级"为团队共享。

编辑级视觉语言

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局——给用户"这是一个有沉淀的系统"的感知。

04 — ARCHITECTURE DECISION

架构决策：检索优先

两种范式对比
维度编译型（obsidian-wiki 范式）检索型（GBrain 范式）· 我们的方案
核心流程导入文档 → AI 编译为结构化 wiki 页面 → 查询时读编译产物导入文档 → 分块 + 嵌入向量 → 查询时检索 chunks + AI 实时推理
写入成本高（每篇 ~7000 tokens LLM）低（分块 + 嵌入 ~200 tokens）
查询成本较低（读 2-3 个 wiki 页面 ≈ 2600 tokens）中等（读 8 个 chunks ≈ 4200 tokens）
可复现性不可复现可复现（确定性代码）
黑箱风险高（编译幻觉被固化）低（AI 只在查询时介入）
成本收益分析
环节检索型（我们的方案）编译型
单次查询总成本~4200 tokens~2600 tokens
编译一篇文档额外成本无~7000 tokens
盈亏平衡点—同一主题需被查询 ≥ 5 次才回本
架构决策结论：对于团队级知识库（几百到几千文档规模），检索型是正确选择。成本更低、风险更小、结果可复现。编译作为可选增强工具保留在 Phase 5。

06 — CONNECTION

模块一：知识库连接

知识库连接是客户端的入口模块，类似 Navicat 的"连接管理"。同一个应用支持两种使用模式，用户在连接页面二选一：

  • 本地连接（个人模式）：启用进程内 PGLite，数据存本地目录。无需服务端，单人使用。
  • 远程连接（团队模式）：填服务端 URL + access_token，thin 连内网 Postgres。多人并发协作。

两种模式背后是同一套 schema 同一套 SQL，UI 和业务逻辑无感知。个人版积累的知识库可随时 dump 上传到团队服务端共享。

内容验证管线

文档进入分块流程前，先经过三道验证关卡，确保入库内容的质量和安全性：

GATE 01
幂等检测：计算文件 SHA-256 content_hash，与已有记录比对。若 hash 相同则跳过，避免重复处理
GATE 02
垃圾内容过滤：检测文件是否过短（<50 字符）、纯数字/乱码、重复内容。命中则标记"已跳过"并提示用户
GATE 03
隐私检测：正则扫描 API Key、密码、身份证号、手机号等敏感模式。命中时弹窗提醒用户确认是否脱敏后导入
多层级分块策略

采用 5 层分隔符层级递归分块，配合 CJK 语言支持和代码语义分块：

层级分隔符说明
L1\n# / \n## / \n### Markdown 标题边界，最高优先级
L2\n\n（双换行）段落边界，过长标题块按段落细分
L3。！？.!?（句末标点）句子边界，支持中英文混合
L4，；;：（句中停顿）子句边界，进一步细分长句
L5字符级切分最终兜底，确保不超过目标大小
分块参数
参数值说明
目标块大小300 词（约 600-800 中文字符）更小的块提升检索精度
重叠大小50 词（约 100-150 中文字符）保持上下文连贯
CJK 支持CJK 字符单独计数，每个汉字 = 1 词避免中文文本被过度切分
最大块大小目标 × 1.5（约 450 词）硬上限，超过则强制切分
代码文件语义分块

对代码文件（.ts / .py / .java / .go 等 36 种语言）使用 Tree-sitter 做语义分块，按 AST 节点边界（函数/类/方法）切分，而非简单的文本分隔符。确保每个 chunk 是一个完整的语义单元。

设计决策：分块使用确定性代码（不调用 LLM），保证结果可复现、成本低、速度快。

编辑 → 重建流程

raw/ 和 wiki/ 下的文档都可编辑。编辑保存时先计算新的 content_hash，与旧值比对：

STEP 01
用户编辑文档内容，点击"保存"
STEP 02
写回源文件 + 计算新 content_hash
STEP 03
若 hash 变化：删除旧 chunks → 重分块 → 重嵌入 → 更新图谱边（异步）
STEP 04
若 hash 未变：跳过重建，提示"内容未修改"
STEP 05
状态栏提示"已重新嵌入（N chunks）"。失败则标记为"待嵌入"
导入流程（事务约定）

STEP 01-04 在事务外（含慢 embedding 调用），DB 写入在一个短事务内：

STEP 01 · 事务外
拖拽文件或选择文件夹，经过内容验证管线（幂等/垃圾/隐私检测）
STEP 02 · 事务外
5 层递归分块（标题→段落→句子→子句→字符），代码文件用 Tree-sitter
STEP 03 · 事务外
上下文包裹：为每个 chunk 拼接文档级前缀（仅嵌入时使用）
STEP 04 · 事务外
每个 chunk 调用 embedding API 生成向量（慢网络调用，必须在事务外）
STEP 05 · ★事务内
BEGIN → 写 pages/content_chunks/links（含向量+tsvector+图谱边）→ COMMIT。短事务，毫秒级
为什么 embedding 必须在事务外：embedding 是网络调用，可能耗时几秒。如果放事务内，会长时间持有行锁，阻塞其他写入。事务只包纯 DB 写入（毫秒级），锁持有时间极短。
08 — AI DIALOGUE

模块三：AI 对话

AI 对话是知识库的智能问答入口。用户提问时，系统自动从当前知识库中检索相关文档片段，注入为 AI 上下文，由 AI 实时综合后生成带引用标注的回答。

12 — DATA MODEL

数据模型

数据模型采用"数据库 schema 为权威，文件系统为快照"的架构。所有结构化数据（文档、chunks、向量、图谱边、来源）都存数据库，磁盘文件只是可重建的 raw 原文 + 可读快照。

存储分层
层存什么形态可重建？
数据库（权威 source of truth） pages / content_chunks（含向量+tsvector） / links / sources / ingest_log / users / access_tokens PGLite（个人） / Postgres（团队） 部分（chunks/向量可从 raw 重建）
raw/ 文件 原始文档源文件（md/pdf/txt...） 磁盘目录 ❌ 不可重建（人类创作内容）
manifest.json 身份证 + 引擎配置 + schema + 统计 磁盘文件 可从数据库统计重建

核心表 Schema

以下表结构同时跑在 PGLite 和 Postgres 上（同一套 DDL），是 BrainEngine 接口的契约基础。

sources 表（数据源 / 权限分区）
CREATE TABLE sources ( id TEXT PRIMARY KEY, -- 如 'iap' / 'ads' / 'dingtalk' name TEXT NOT NULL, kind TEXT DEFAULT 'team', -- team | personal | shared archived BOOLEAN DEFAULT FALSE, -- 归档隔离（visibility 过滤） created_at TIMESTAMPTZ DEFAULT now(), stats JSONB -- 缓存的统计（文档数/chunk数） );
pages 表（文档 = 知识库写入/寻址最小单位）

page = 一篇文档，是知识库的写入/读取/寻址最小单位（slug 唯一寻址）。原始文档、沉淀综合、笔记、实体（人/公司/概念）都是 page，靠 type 区分。注意：page 不是"检索最小单位"——检索按 chunk 匹配。

CREATE TABLE pages ( id SERIAL PRIMARY KEY, slug TEXT NOT NULL, -- 如 'iap/refund-flow'、'people/zhang-san' source_id TEXT NOT NULL REFERENCES sources(id), type TEXT NOT NULL, -- source|synthesis|note|compiled|person|company|concept title TEXT NOT NULL, body_md TEXT, -- ★ 解析清洗后的 markdown 正文（非原始字节） summary TEXT, -- frontmatter.summary（图谱节点摘要用） tags TEXT[] DEFAULT '{}', content_hash TEXT, -- SHA-256，幂等检测 generation INT DEFAULT 1, -- 知识代次：原始=1 综合=2 编译=3 source_file TEXT, -- raw/ 路径（source 类型）或 wiki/ 路径 search_vector TSVECTOR, -- Postgres FTS（触发器维护） effective_date DATE, -- P5：时效 Boost salience REAL DEFAULT 0, -- P5：显著性 Boost owner_id TEXT, -- 归属用户（团队权限） version BIGINT DEFAULT 1, -- P3：乐观锁 CAS deleted_at TIMESTAMPTZ, -- 软删（visibility 过滤） created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now(), UNIQUE (source_id, slug) ); CREATE INDEX idx_pages_search ON pages USING GIN(search_vector); CREATE INDEX idx_pages_source ON pages(source_id) WHERE deleted_at IS NULL; CREATE INDEX idx_pages_effdate ON pages ((COALESCE(effective_date, updated_at)));
body_md 语义：不要把 body_md 当成 raw 文件的副本——它存的是解析清洗后的 markdown 正文（PDF 提取文本、Word 转 markdown、URL 抓取清洗后的结果）。raw/ 保留原始字节（保真存档），body_md 是可检索可渲染的统一格式。body_md 可从 raw 重建，raw 不可从 body_md 重建。
content_chunks 表（分块 + 向量 = 检索最小单位）

chunk = 检索/匹配的最小单位。一个 page 在写入时同步切成多个 chunk（1:N），向量（embedding）存在 chunk 级而非 page 级。

CREATE TABLE content_chunks ( id SERIAL PRIMARY KEY, page_id INT NOT NULL REFERENCES pages(id) ON DELETE CASCADE, chunk_index INT NOT NULL, body TEXT NOT NULL, -- 原始 chunk 文本（用户看到） chunk_source TEXT DEFAULT 'body', -- body | timeline | code（区分 chunk 来源） char_start INT, char_end INT, token_count INT, section_path TEXT, -- 如 '## 退款流程' embedding vector(1536), -- pgvector 向量（嵌入时含上下文包裹） search_vector TSVECTOR, -- chunk 级 FTS content_hash TEXT, -- 幂等 embedding_model TEXT, -- 用哪个模型嵌入的 UNIQUE (page_id, chunk_index) ); CREATE INDEX idx_chunks_embedding ON content_chunks USING hnsw (embedding vector_cosine_ops); CREATE INDEX idx_chunks_search ON content_chunks USING GIN(search_vector); CREATE INDEX idx_chunks_page ON content_chunks(page_id);
page / chunk / 文档 / 实体 四者关系
知识库 (source_id = 'iap') │ └── PAGE = 写入/寻址最小单位 = 一篇文档 │ slug: iap/refund-flow │ body_md: "# IAP退款流程\n退款必须在7天内..." (解析后的 markdown) │ raw/: iap/refund-spec.pdf (原始字节，源头) │ └── 写入时同步切分 1:N │ ├── CHUNK = 检索/匹配最小单位 │ chunk_index: 0 chunk_source: 'body' │ body: "退款必须在7天内发起" │ embedding: vector(1536) ← 向量在 chunk 级 │ ├── CHUNK │ chunk_index: 1 chunk_source: 'body' │ body: "系统校验订单状态..." │ embedding: vector(1536) │ └── ... (更多 chunks) 检索返回 → chunk（附 page 的 slug/title/type 元数据） AI 注入 → chunk 片段（截断 ~600 字符） 图谱关系 → links 表（实体 page ↔ 引用 page）
概念是什么最小单位角色
page一篇文档（markdown 正文 + 元数据）写入/寻址最小单位（slug 唯一）

向量表 JOIN 关系表（核心能力）

单库方案的最大优势：向量检索时直接 JOIN 关系表，把权限/source/软删/归档等过滤下推进 HNSW 候选集，避免召回率掉。

-- 向量路：HNSW 候选集 + 关系过滤下推 WITH hnsw_candidates AS ( SELECT p.slug, p.title, p.type, p.source_id, cc.id AS chunk_id, cc.body, 1 - (cc.embedding <=> $1::vector) AS raw_score FROM content_chunks cc JOIN pages p ON p.id = cc.page_id JOIN sources s ON s.id = p.source_id WHERE cc.embedding IS NOT NULL AND p.source_id = ANY($visible_sources) -- 权限下推 AND p.deleted_at IS NULL -- 软删下推 AND NOT s.archived -- 归档下推 AND p.type = ANY($types) -- 类型下推 ORDER BY cc.embedding <=> $1::vector LIMIT 30 ), best_per_page AS ( SELECT DISTINCT ON (source_id, slug) * FROM hnsw_candidates ORDER BY source_id, slug, raw_score DESC ) SELECT * FROM best_per_page ORDER BY raw_score DESC LIMIT $top_k;
为什么这个 JOIN 重要：团队场景下，某客户端只该看自己 source 的 10% 数据。如果先向量取 top-100 再过滤，可能 90 个是别人的、过滤后只剩 10 个有效候选，召回率从 ~100% 掉到 ~10%。WHERE 下推让 HNSW 只在合格行上扫描。

在嵌入（embedding）阶段，为每个 chunk 拼接文档级上下文前缀，让向量编码时包含更多语义信息。这个上下文只在嵌入时使用，不存储。

嵌入时的上下文包裹格式： "本文档: {document_title} 本章: {section_heading} --- {chunk_text}" 效果：向量编码时"知道"自己属于哪个文档、哪个章节 存储：只存原始 chunk_text，上下文前缀不写入数据库 查询：查询文本不做上下文包裹
必须 Phase 1 一次到位：上下文检索的代码量极小，但它影响已入库向量的语义。如果后续才开启，之前所有 chunks 的向量都"过时"了，必须全量重嵌入。因此必须和分块、首次嵌入一起一次到位。
