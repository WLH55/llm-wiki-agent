01 — POSITIONING

产品定位与核心类比

一句话定位

工作知识库是一款知识库管理桌面客户端。知识库本身是一个可插拔、可备份、可迁移的数据包（类似 MySQL 数据库），桌面客户端负责连接、浏览、搜索和管理这个数据包（类似 Navicat / DBeaver）。

一句话定位：知识库管理桌面客户端 — 像 Navicat 管理 MySQL 一样管理你的团队知识库。
核心类比
数据库世界工作知识库说明
MySQL 数据库知识库数据包自包含目录：markdown + 向量 + 图谱 + manifest
Navicat / DBeaver本桌面客户端连接、浏览、搜索、管理知识库
localhost / 远程服务器本地目录 / 内网部署连接本地知识库或团队内网共享知识库
SQL 查询混合搜索 + AI 对话精确检索和智能问答两种消费模式
数据库备份/导出知识库快照/导出/迁移数据包级别的可移植性
核心价值主张
  • 数据包可插拔：知识库是一个自包含目录，可挂载/卸载/快照/导出/迁移。和数据库一样独立于客户端存在。
  • 检索优先：向量搜索 + BM25 混合检索 + AI 实时推理。不依赖 AI 编译，直接返回正确答案。
  • 多知识库 + 多租户：一个客户端管理多个知识库数据包；团队模式下支持 source 分区 + token 权限隔离。
  • 多模型可插拔：嵌入、重排、对话模型均可配置切换（在线 / 本地 / 多供应商）。
  • 双 AI 通道：可代理本地 CLI 工具（Claude Code、Gemini CLI），也可配置 API Key 使用内置 Mini Agent。
  • 双用户群体：开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。同一份数据，两种入口。
  • 桌面原生体验：Tauri 打包为轻量桌面应用（~40MB），双击即开，内网也可 Docker 部署。
  • 一个应用两种模式：本地连接（PGLite，个人模式）和远程连接（Postgres，团队模式）是同一个安装包，用户在连接页面二选一。

03 — PRINCIPLES

核心设计原则

检索优先，编译可选

知识库的默认能力是检索：文档导入后自动分块 + 向量嵌入，即可被搜索和 AI 对话消费。不需要 AI 编译即可使用。编译是一个可选的增强工具——对高价值内容做深度结构化整理，但不是知识库运作的前提。这确保了：导入即可用、无黑箱、token 成本可预测。

客户端-数据包分离

桌面应用是客户端，知识库是数据包。两者完全解耦——客户端不存储知识数据，数据包不依赖特定客户端。知识库可以在应用内挂载/卸载/切换，也可以导出为 zip 在实例间迁移。

双通道、一份数据

开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过桌面 UI 浏览和对话。两条通道共享同一份知识库数据包，看到的数据完全一致。

一个应用两种模式

同一个 Tauri 应用支持本地连接（PGLite 个人模式）和远程连接（Postgres 团队模式）。用户无需安装两个产品，本地积累的知识库可随时"升级"为团队共享。

编辑级视觉语言

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局——给用户"这是一个有沉淀的系统"的感知。

能力对齐，定位不漂

v4.0 吸收 WeKnora 等项目的工程能力（多租户、数据源、可观测性），但坚持桌面客户端定位：不抄服务端常驻运行模型（cron 守护、WebSocket 长连接、分布式去重），用桌面应用的方式实现（setInterval、sidecar、Rust 命令）。

04 — ARCHITECTURE DECISION

架构决策：检索优先

两种范式对比
维度编译型（obsidian-wiki 范式）检索型（GBrain 范式）· 我们的方案
核心流程导入文档 → AI 编译为结构化 wiki 页面 → 查询时读编译产物导入文档 → 分块 + 嵌入向量 → 查询时检索 chunks + AI 实时推理
写入成本高（每篇 ~7000 tokens LLM）低（分块 + 嵌入 ~200 tokens）
查询成本较低（读 2-3 个 wiki 页面 ≈ 2600 tokens）中等（读 8 个 chunks ≈ 4200 tokens）
可复现性不可复现可复现（确定性代码）
黑箱风险高（编译幻觉被固化）低（AI 只在查询时介入）
架构决策结论：对于团队级知识库（几百到几千文档规模），检索型是正确选择。成本更低、风险更小、结果可复现。编译作为可选增强工具保留在 Phase 5。
导入流程（检索优先）

导入全过程不消耗 LLM tokens。embedding API 成本约 200 tokens/文档，约 ¥0.001。

未来可选的编译增强（Phase 5）
  • 用户手动触发：在文档管理页选中特定文档，点击"编译"按钮
  • 系统建议触发：当某个主题的查询频率超过阈值时，系统建议"是否编译为综合页面？"
  • 编译 Diff 审核：编译完成后展示 diff 对比视图，用户确认后才写入
  • 不做默认行为：编译永远是可选操作，不是导入流程的一部分

07 — DOCUMENTS

模块二：文档管理（解析升级 + 异步任务） v4 升级

文档解析：从 npm 库升级为 Rust sidecar 关键变更

v3.0 的 PDF 解析方案（pdf-parse / unpdf）对扫描版 PDF、复杂排版 PDF 基本无效。v4.0 将文档解析升级为独立的 Rust sidecar，通过 Tauri command 调用，在 Rust 线程跑重解析，不阻塞前端事件循环。

PDFpdf-parse（npm）pdfium-render（Rust 绑定 Chrome PDF 引擎）支持布局分析、扫描版渲染
Word (.docx)mammoth（npm）docx-rs（Rust 原生）结构化解析 + 图片提取
Word (.doc)不支持调用 LibreOffice headless 转换需系统装 LibreOffice
HTML / URL@mozilla/readabilityreqwest + readability（Rust）不依赖 Playwright 那么重
Markdown / TXT直接读取TS 直接解析（保留）P1 零成本

架构借鉴：参考 WeKnora 的 docreader 设计——文档解析独立成服务，不塞进主进程。Tauri 架构天然支持：Rust 侧重计算通过 tauri::command 暴露给前端。混合方案：Markdown/TXT 用 TS 直接解析（零成本），重格式走 Rust 命令。

08 — AI DIALOGUE

模块三：AI 对话（会话管理 + 多模型） v4 增强

会话管理 明确

AI 对话支持多轮上下文。每个会话绑定一个知识库，支持上下文 rewrite（查询改写）。会话可新建、列表、删除、继续。

能力描述
新建会话绑定知识库，设置 max_rounds（上下文窗口轮数，默认 5）

-- 一条 LLM 调用记录 { "ts": "2026-06-28T10:30:00Z", "model": "claude-3-5-sonnet", "channel": "mini-agent", // mini-agent / cli-proxy "prompt_tokens": 4200, "completion_tokens": 380, "latency_ms": 2300, "status": "ok", // ok / error "error": null }

13 — IM NOTIFICATION

模块八：IM 通知与集成 v4 新增

重新定位：通知推送，而非双向对话

WeKnora 的 IM 子系统是最重的部分（~12,884 行），依赖服务端常驻进程（WebSocket 长连接、Redis 领导选举、QA 工作池）。这与桌面客户端定位冲突。v4.0 将 IM 重新定义为单向通知推送。

方案WeKnora（双向对话）本产品（单向通知）
代码量~12,884 行 + 8 平台适配器~200 行（一个 webhook 调用）
运行要求服务端常驻 + Redis 领导选举桌面端触发时发一个 HTTP 请求
用户场景在钉钉里和 Bot 对话查知识库知识库有新沉淀 → 群里收到卡片通知
定位匹配❌ 与桌面应用冲突（关了收不到消息）✅ 符合桌面应用模式
通知触发场景
  • 文档沉淀：AI 对话回答被沉淀为 synthesis 文档 → 推送通知
  • 批量导入完成：50 篇文档导入完成 → 推送汇总
  • 数据源同步：RSS 更新了 3 篇新文章 → 推送
  • 图谱变更：高 salience 节点新增关联 → 推送（Phase 5）
实现：飞书/钉钉 Incoming Webhook
// 飞书自定义机器人 webhook POST https://open.feishu.cn/open-apis/bot/v2/hook/{bot_id} { "msg_type": "interactive", "card": { "header": { "title": { "tag": "plain_text", "content": "📖 知识库更新" }}, "elements": [ { "tag": "div", "text": { "tag": "lark_md", "content": "**新沉淀：IAP 退款流程综述**\n来源：AI 对话沉淀\n引用：3 篇文档" }} ] } } // 钉钉自定义机器人 webhook POST https://oapi.dingtalk.com/robot/send?access_token={token} { "msgtype": "actionCard", "actionCard": { "title": "知识库更新", "text": "..." } }

19 — MCP TOOLS

MCP 工具集成（8 个工具） v4 扩充

v3.0 仅 2 个工具（search_wiki + update_wiki），缺少"看全文""了解知识库有什么""图谱关联"等关键环节。v4.0 扩充到 8 个工具，覆盖完整的"发现 → 检索 → 深读 → 关联 → 对话 → 沉淀"闭环。

设计原则：不暴露管理类操作（创建租户/配置模型/管理凭据）——这些是 UI 的职责，不是 IDE 里 AI 该做的。WeKnora 27 个工具里相当一部分（tenant/model CRUD）是过度暴露。判断标准：这件事让 IDE 里的 AI 做，比让用户去 UI 点一下，更合理吗？

session_idstring否会话 ID，不传则新建一次性会话
kb_idstring否指定库，覆盖默认

带历史的多轮问答。返回 answer + references + session_id（可用于继续对话）。

参数类型必填说明

写入 wiki/synthesis/，自动分块 + 嵌入 + 提取图谱边。

三个工程质量要点（参考 WeKnora）
① 名称自动解析（必须抄）

所有接受 slug/title/kb_id 的参数都同时支持 UUID 和人类可读名称。AI 在 IDE 里会说"读一下 IAP 退款流程那篇"，不会记 slug。

② 工具描述里的"引导链"（必须抄）

每个工具 description 里告诉 AI 什么时候该换工具。例：search_wiki 描述写"片段不够用 read_page；了解全貌用 list_pages；查关联用 get_related"。比堆工具数量有效得多。

③ 快速失败 + 有用提示（可选抄）

update_wiki 的 references slug 不存在时，返回"slug 'xxx' 不存在，可用的有 ..."，而非写入悬空引用。

20 — RETRIEVAL ENGINE

检索引擎

全部检索 SQL 化——向量、全文、图谱、boost 都在一个 Postgres（PGLite）里用 SQL 完成。

完整检索管线
Stage 0: 意图分类（零 LLM）→ entity/temporal/event/general → 调权重 Stage 1: 双路召回（SQL，WHERE 下推） · BM25: tsvector + GIN + ts_rank → top-30 · 向量: HNSW + 余弦，权限/软删 WHERE 下推 → top-30 Stage 2: RRF 融合（k=60） Stage 3: 后融合 Boost（分两步） · 标题匹配 ×1.25 / 来源类型 ── Phase 3 · 显著性 / 时效 / 图谱信号 ── Phase 5 Stage 4（可选）: Cross-encoder 重排序 ── Phase 5 Stage 5: 输出 top-K（默认 8）
向量表 JOIN 关系表（核心能力）
-- 向量路：HNSW 候选集 + 关系过滤下推 WITH hnsw_candidates AS ( SELECT p.slug, p.title, p.type, p.source_id, cc.id AS chunk_id, cc.body, 1 - (cc.embedding <=> $1::vector) AS raw_score FROM content_chunks cc JOIN pages p ON p.id = cc.page_id JOIN sources s ON s.id = p.source_id WHERE cc.embedding IS NOT NULL AND p.source_id = ANY($visible_sources) -- 权限下推 AND p.deleted_at IS NULL -- 软删下推 AND NOT s.archived -- 归档下推 ORDER BY cc.embedding <=> $1::vector LIMIT 30 ) SELECT * FROM hnsw_candidates ORDER BY raw_score DESC LIMIT $top_k;
为什么这个 JOIN 重要：团队场景下某客户端只该看自己 source 的 10% 数据。先向量取 top-100 再过滤，可能 90 个是别人的，召回率从 ~100% 掉到 ~10%。WHERE 下推让 HNSW 只在合格行上扫描。

上下文检索

嵌入时为每个 chunk 拼接文档级上下文前缀，向量编码时"知道"自己属于哪个文档、章节。上下文只在嵌入时用，不存储。必须 Phase 1 一次到位，否则后续全量重嵌入。
