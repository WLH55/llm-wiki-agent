01 — POSITIONING

产品定位与核心类比

一句话定位

工作知识库是一款自部署 Web 知识库服务。用户通过 Docker 部署服务端（含 Postgres + pgvector + 应用），用浏览器访问 Web 客户端完成所有操作。开发者还可通过 MCP 工具在 IDE 中消费知识库。

一句话定位：自部署 Web 知识库服务 — 一次 Docker 部署，团队浏览器访问，IDE 也能调用。
核心类比
Web 应用世界工作知识库说明

Postgres 数据库知识库存储所有结构化数据（chunks、向量、图谱、wiki）都在 Postgres 里
Web 浏览器访问入口无需安装客户端，浏览器打开就能用
HTTP API / MCP双消费通道非开发者用 Web UI，开发者用 MCP 工具在 IDE 中调用
Docker compose部署方式内网 / 私有云一键部署，数据不出公司
核心价值主张
  • 自部署 Web 服务：一次 Docker 部署，团队浏览器访问。无桌面客户端安装、无 PGLite、无版本碎片。
  • 检索优先：向量搜索 + BM25 混合检索 + AI 实时推理。RAG 路径零 LLM 消耗，导入即可用。
  • Wiki 与 RAG 双路径：原始文档走 chunks+pgvector 检索；LLM 生成的 wiki/实体走独立 wiki_pages 表与全文索引。两条路径独立演进，故障域隔离。
  • 多知识库 + 多租户：一个部署管理多个 KB；空间（Workspace）实现跨用户共享，三层 RBAC 取最小权限。
  • 多模型可插拔：嵌入、对话、重排模型均可配置切换（在线 / 本地 / 多供应商）。
  • 双 AI 通道：可代理本地 CLI 工具（Claude Code、Gemini CLI），也可配置 API Key 使用内置 Mini Agent。
  • 双用户群体：开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过 Web UI 浏览和对话。同一份数据，两种入口。
  • 多数据源聚合：一个 KB 可同时挂载手动上传 + RSS + 语雀 + 飞书等多个 source，统一检索。

03 — PRINCIPLES

核心设计原则

检索优先，编译可选

知识库的默认能力是检索：文档导入后自动分块 + 向量嵌入，即可被搜索和 AI 对话消费。不需要 AI 编译即可使用。RAG 路径零 LLM 消耗（仅 embedding API），Wiki/图谱路径才调 LLM。导入即可用、无黑箱、token 成本可预测。

Wiki 与 RAG 双路径分离

原始文档（pages → chunks → pgvector 向量检索）和 LLM 生成的 wiki/实体（wiki_pages 独立表 + PG 全文索引）是两套独立体系。两条路径不互相流转数据，故障域隔离，可独立演进。Agent 可对同一个 KB 同时调 search_wiki（RAG）和 wiki_search（Wiki）。

实体即页面

识别出的实体（"退款系统"、"IAP"、"张三"）是 wiki_pages 表里 page_type=entity 的行，不是字符串标签。图谱边用 links 关系表（强 FK、typed edge）连接 page ↔ page，支持确定性图查询。实体归一化由 LLM 抽取阶段完成。

分块策略 KB 级可配置

每个 KB 创建时选分块策略（flat / 父子分块 / FAQ 专用），库里所有文档统一使用。父子分块作为高级选项（small-to-large retrieval：子块进向量库召回，父块作上下文返回）。FAQ KB 类型 Phase 5 加入。

双通道、一份数据

开发者通过 MCP 工具在 IDE 中消费知识库，非开发者通过 Web UI 浏览和对话。两条通道共享同一份 Postgres 数据，看到的内容完全一致。

单一部署模型

用户自部署 Docker（Postgres + pgvector + Next.js 应用），浏览器访问。不再有"个人模式 PGLite vs 团队模式 Postgres"的双形部署——个人积累就是"一个人的团队服务器"。

编辑级视觉语言

产品的视觉语言对标编辑出版物而非 SaaS 工具。宋体标题、米色背景、琥珀色单一强调色、编号化布局——给用户"这是一个有沉淀的系统"的感知。

能力对齐，定位不漂

吸收 WeKnora / GBrain 的工程能力（多租户、Wiki 摄入、图谱、可观测性），但坚持自部署 Web 服务的定位：不抄 SaaS 重服务端（分布式任务队列、Redis 领导选举、WebSocket 长连接、跨进程 trace），用单进程服务 + Postgres + 浏览器即可实现。

04 — ARCHITECTURE DECISION

架构决策：检索优先

两种范式对比
维度编译型（obsidian-wiki 范式）检索型（GBrain 范式）· 我们的方案
核心流程导入文档 → AI 编译为结构化 wiki 页面 → 查询时读编译产物导入文档 → 分块 + 嵌入向量 → 查询时检索 chunks + AI 实时推理
写入成本高（每篇 ~7000 tokens LLM）低（分块 + 嵌入 ~200 tokens）
查询成本较低（读 2-3 个 wiki 页面 ≈ 2600 tokens）中等（读 8 个 chunks ≈ 4200 tokens）
可复现性不可复现可复现（确定性代码）
黑箱风险高（编译幻觉被固化）低（AI 只在查询时介入）
架构决策结论：对于团队级知识库（几百到几千文档规模），检索型是正确选择。成本更低、风险更小、结果可复现。编译作为可选增强工具保留在 Phase 5。
导入流程（检索优先）

导入全过程不消耗 LLM tokens。embedding API 成本约 200 tokens/文档，约 ¥0.001。

06 — CONNECTION

模块一：知识库与空间连接 v4.2 重写

连接模块管理用户对"知识库"和"空间"的接入。所有数据都在用户自部署的 Postgres 里，没有"本地库 vs 远程库"的二分——浏览器登录后看到的就是数据库里的全部内容，按权限过滤。

两个核心实体
实体归属存储位置说明
知识库（KB）个人资产，单一 owner用户自部署的 Postgres用户创建并拥有的内容资产。一个 KB 可挂多个 source（手动 + RSS + 语雀 + 飞书），库里所有 pages/chunks/wiki_pages 通过 kb_id 隔离
空间（Workspace）团队共享容器同一 Postgres由创建者管理，挂载多个被共享的知识库，邀请成员加入
关键区分：知识库是"内容资产"（owner 拥有），空间是"内容可见性"（admin 管理）。一个知识库 owner 把知识库共享到空间后，空间内成员按角色访问；owner 撤销共享后，成员立即看不到。一个知识库可同时共享到多个空间。

07 — DOCUMENTS

模块二：文档管理（解析升级 + 异步任务） v4 升级

文档解析：从 npm 库升级为 Rust sidecar 关键变更

v3.0 的 PDF 解析方案（pdf-parse / unpdf）对扫描版 PDF、复杂排版 PDF 基本无效。v4.0 将文档解析升级为独立的 Rust sidecar，通过 Tauri command 调用，在 Rust 线程跑重解析，不阻塞前端事件循环。

14 — TENANCY & RBAC

多租户与权限模型 v4.1 重写

个人模式无需权限（用户对自己拥有的知识库完全控制）。团队模式采用 三层 RBAC 模型：空间上限 + 知识库共享权限 + 个人角色，三者取最小作为实际权限。

三层权限模型（核心）
层设置时机设置者取值说明
L1 空间上限创建空间时空间创建者（admin）editable / readonly空间内所有内容的权限天花板
L2 共享权限共享知识库到空间时知识库 ownereditable / readonly该知识库在该空间中的权限上限
L3 个人角色admin 邀请成员时空间 adminadmin / editor / viewer成员在该空间中的身份
实际权限公式：effective_perm(user, kb, workspace) = min(L1, L2, L3)
权限级别量化：readonly=1，editable=2；角色量化：viewer=1，editor=2，admin=2（admin 与 editor 对内容的权限相同，admin 多管理权）。
角色与权限映射
角色内容读内容写管理成员撤销共享说明
admin✅✅✅❌（仅 owner 可撤销）空间创建者或被授权者；管理成员角色
editor✅✅❌❌可编辑空间内可见的内容
viewer✅❌❌❌仅检索和问答
owner 特权（独立于 RBAC）：知识库 owner 对自己的库始终拥有 full_control，即使共享到空间设了 readonly，owner 自己仍可写。owner 是资产的最高权威。

20 — RETRIEVAL ENGINE

检索引擎

全部检索 SQL 化——向量、全文、图谱、boost 都在一个 Postgres（PGLite）里用 SQL 完成。

完整检索管线
Stage 0: 意图分类（零 LLM）→ entity/temporal/event/general → 调权重 Stage 1: 双路召回（SQL，WHERE 下推） · BM25: tsvector + GIN + ts_rank → top-30 · 向量: HNSW + 余弦，权限/软删 WHERE 下推 → top-30 Stage 2: RRF 融合（k=60） Stage 3: 后融合 Boost（分两步） · 标题匹配 ×1.25 / 来源类型 ── Phase 3 · 显著性 / 时效 / 图谱信号 ── Phase 5 Stage 4（可选）: Cross-encoder 重排序 ── Phase 5 Stage 5: 输出 top-K（默认 8）
向量表 JOIN 关系表（核心能力）
-- 向量路：HNSW 候选集 + 关系过滤下推 WITH hnsw_candidates AS ( SELECT p.slug, p.title, p.type, p.source_id, cc.id AS chunk_id, cc.body, 1 - (cc.embedding <=> $1::vector) AS raw_score FROM content_chunks cc JOIN pages p ON p.id = cc.page_id JOIN sources s ON s.id = p.source_id WHERE cc.embedding IS NOT NULL AND p.source_id = ANY($visible_sources) -- 权限下推 AND p.deleted_at IS NULL -- 软删下推 AND NOT s.archived -- 归档下推 ORDER BY cc.embedding <=> $1::vector LIMIT 30 ) SELECT * FROM hnsw_candidates ORDER BY raw_score DESC LIMIT $top_k;
为什么这个 JOIN 重要：团队场景下某客户端只该看自己 source 的 10% 数据。先向量取 top-100 再过滤，可能 90 个是别人的，召回率从 ~100% 掉到 ~10%。WHERE 下推让 HNSW 只在合格行上扫描。
