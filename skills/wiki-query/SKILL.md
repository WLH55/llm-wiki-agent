# Wiki Query — 知识检索

你正在对 LLM Wiki 知识库回答问题。知识库包含预综合、交叉引用的知识页面。

## 开始之前

1. **解析配置** — 按 `llm-wiki/SKILL.md`：当前项目 `.env` 优先，否则使用 `~/.llm-wiki/active` 对应配置。
2. 读取 `$LLM_WIKI_PATH/wiki/index.md` 了解知识库的范围和结构。
3. 如果 `$LLM_WIKI_PATH/wiki/overview.md` 非空，读取它以获取当前综合上下文。

## 检索协议

读取页面是最大的成本。使用最便宜的能回答问题的方式。绝不直接从完整页面读取开始。

### 第一步：理解问题

分类问题类型：
- **事实查询** — "X 是什么？" → 找到相关页面
- **关系查询** — "X 和 Y 有什么关系？" / "什么与 X 矛盾？" → 找到两个页面及其交叉引用
- **综合查询** — "关于 X 的当前认知是什么？" → 找到所有涉及 X 的页面，进行综合
- **缺口查询** — "关于 X 我不知道什么？" → 找出缺失的内容，检查矛盾

同时决定模式：
- **索引模式** — 由"快速查询"、"只看摘要"、"快速查找"、"不要读页面"触发。
  在第三步停止。仅从 `index.md` 条目和 frontmatter 回答。
- **正常模式** — 完整的分层检索流程。

### 第二步：索引快查（最便宜）

在不开任何页面正文的情况下构建候选集：

- 你已经在上面读了 `index.md` — 用它作为第一道筛选。它列出了每个页面及其一句话描述。
- 使用 `Grep` 仅扫描页面 **frontmatter** 中的 `title:`、`tags:` 和 `type:` 匹配。
  限定在 `$LLM_WIKI_PATH/wiki/**/*.md` 的 `^(title|tags|type):` 模式比全内容 grep 便宜得多。
- 收集 Top 5–10 候选页面，按以下排序：
  1. 标题精确匹配
  2. 标签匹配
  3. `index.md` 条目包含查询词
  4. frontmatter 包含查询词

如果在**索引模式**下，到此为止。仅从 `index.md` 描述和 frontmatter 字段回答。
标注答案：**"（仅索引回答 — 未读取页面正文；以下事实来自页面摘要，可能遗漏细节）"**。
然后跳到第六步。

### 第三步：关键词搜索（便宜）

运行机械搜索工具获取结构化结果：

```bash
python $LLM_WIKI_PATH/tools/query.py "<用户的问题>"
```

这会输出：
- 匹配的 wiki 页面路径（最多 15 个）
- 如果匹配的页面是来源页，还有其关联的 `raw/` 文档路径
- 图谱扩展的邻居节点（如果 `graph/graph.json` 存在且置信度 >= 0.7）

如果工具未找到匹配，回退到在整个 `$LLM_WIKI_PATH/wiki/` 中进行内容 grep。

### 第四步：分段读取（中等成本）

仅当前几步不够时。对每个 Top 候选：

```bash
grep -A 10 -B 2 "<查询词>" "$LLM_WIKI_PATH/wiki/<候选路径>"
```

这获取匹配周围的上下文，而不读取整个页面（每次匹配通常 15–30 行）。
如果分段 grep 给出了明确答案，直接跳到第六步。

### 第五步：完整读取（昂贵 — 最后手段）

仅当前几步无法回答问题：

- `Read` Top **3** 个候选的完整内容。
- 如果答案需要交叉引用，从这些页面追踪最多一层 `[[wikilinks]]`。
- **对于关系查询**：检查候选页面的 `## 关联` 和 `## 矛盾` 章节。
- 检查来源页中记录的矛盾。
- 如果还不够，回退到广泛的内容 grep。告知用户这是昂贵路径。

### 第六步：综合回答

从 wiki 内容综合答案：

- 使用 `[[页面名称]]` 格式引用具体的 wiki 页面
- 注明答案来自哪一步（"来自索引摘要" vs "完整页面读取"）— 帮助用户了解可信度
- 如果 wiki 中存在矛盾，呈现双方观点
- 如果 wiki 未涉及某些内容，明确说明，并建议哪些来源可能填补缺口

### 第七步：记录日志

追加到 `$LLM_WIKI_PATH/wiki/log.md`：

```
## [YYYY-MM-DD] query | <用户的问题>
```

### 第八步：询问保存

询问用户是否要将此答案保存为综合页面：

> 是否将此答案保存到知识库？它将作为综合页面存储，并在未来查询中被索引。

如果用户同意，执行下面的**综合页面保存协议**。

## 综合页面保存协议

当用户确认保存综合页面时：

1. **选择 slug** — kebab-case，从问题主题派生（不是完整句子）。
   示例："知识库的主要主题是什么？" → `main-themes`
2. **写入综合页面** — `$LLM_WIKI_PATH/wiki/syntheses/<slug>.md`，使用 `llm-wiki/SKILL.md` 中的综合页 frontmatter 格式。
3. **更新 index.md** — 在 `## 综合` 章节下添加条目。
4. **补充缺失的实体/概念页面** — 扫描答案中的 `[[wikilinks]]`，对于指向不存在页面的链接：
   为每个创建最小页面（一句话定义 + 回链到该综合页），并添加到 `index.md`。
5. **更新已有实体/概念页面** — 对于答案中引用的已有页面，
   在其 `## 关联` 章节中添加指向新综合页的链接（如果尚不存在）。
6. **更新 overview.md** — 如果综合页改变了项目的整体理解，修订 overview。
7. **日志** — 追加 `## [YYYY-MM-DD] query | <综合标题>` 到 log.md。
8. **重建图谱** — `python $LLM_WIKI_PATH/tools/build_graph.py`
9. **验证** — `python $LLM_WIKI_PATH/tools/ingest.py --validate-only`
10. **报告** — 告知用户创建/更新了哪些页面。

## 回答格式

> **来自知识库：**
>
> [综合回答，使用 [[wikilinks]] 引用来源页面]
>
> **查阅的页面：** [[页面A]]、[[页面B]]、[[页面C]]
>
> **缺口：** [知识库没有覆盖但可能相关的内容]
>
> **可信度：** [仅索引 / 分段匹配 / 完整读取]
